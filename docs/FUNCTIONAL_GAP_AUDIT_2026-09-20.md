## 왜 이전 검증을 통과해도 이런 구멍이 남는가

독립 교차검토로 F01의 범위를 **현재 권한은 있지만 오래된 확인 대상이 바뀌는 경우**로 한정했다. F04도 서버 중복 방지가 없는 것이 아니라 UI가 재시도를 새 ID·revision의 다른 명령으로 만드는 문제다. F07은 **기존 원장 claim의 미확인/처리 중/판독 불가 결과**에 대한 표시 결함이다. 현재 승인 atomic 저장의 응답 유실은 별도 상위 오류 경로이므로 그것이 곧 해당 카드로 이어진다는 초기 설명은 제외했다.

컴포넌트별 정상 저장, 서버의 권한 검사, 같은 요청의 중복 방지는 이미 존재한다. 하지만 **입력 시작→소유자 변경→저장**, **서버 저장→응답 유실→정본 갱신→사용자 재시도**, **저장 영수증→후속 조회 멈춤**처럼 여러 상태를 잇는 시나리오가 빠졌다. 버튼 하나나 SQL 함수 하나의 통과만으로 이 연결을 보장할 수 없다.

또한 일부 실패 경로는 “미확인”, “확정 실패”, “정상 빈 결과”를 하나로 취급한다. 이는 문구만의 문제가 아니라 재시도·중복·동의 상태 오인으로 이어지는 행동 계약의 문제다.

## 권장 수정 순서와 완료 기준

1. **대상 고정:** F01/F02/F03. 입력·확인 시작 시 계정/커플/연결 세대를 고정하고 변경 뒤의 클릭·늦은 완료를 거절한다. 파괴적 작업은 서버 실행 직전에도 같은 대상인지 확인한다.
