# 웨딩한방 모바일 제품 완료 기준 — 2026-08-03

> 상태: `AUTHORITATIVE MOBILE RELEASE STANDARD`
>
> 모바일 앱은 웨딩한방의 주 제품이다. 이 문서는 코드가 존재하거나 로컬 테스트가
> 통과했다는 사실과 소비자가 실제 기기에서 안심하고 사용할 수 있다는 사실을 구분한다.
> 아래 필수 증거가 모두 없으면 앱을 “완성” 또는 “출시 준비 완료”라고 부르지 않는다.

## 1. 채널 계약

### 모바일 앱

- 커플이 처음 가치를 경험하고 매일 다시 돌아오는 주 제품이다.
- 홈, 아모라, 커플 동기화, 예산·할 일·일정 반영이 최우선 품질 범위다.
- 짧은 세션, 한 손 조작, 알림 진입, 앱 중단 후 복귀, 불안정한 네트워크를 기본 환경으로
  가정한다.

### 웹

- 유입, 제품 설명, 정책·고객지원, 관리자 운영과 데스크톱 연속성을 담당한다.
- 앱과 같은 Supabase 및 서버 계약을 사용한다.
- 웹 화면 코드는 네이티브 화면에 자동 반영되지 않는다. 데이터·API 변경은 공유되지만,
  네이티브 UI 변경은 Expo Update 또는 앱 빌드가 필요하다.

## 2. 소비자 핵심 여정

### A. 첫 10분

1. 앱 설치와 첫 실행이 오류 없이 끝난다.
2. 사용자는 이메일 또는 출시 대상으로 승인된 소셜 로그인으로 들어온다.
3. 예식일과 현재 준비 상황의 최소 정보만 입력한다.
4. 홈에서 지금 할 한 가지를 5초 안에 이해한다.
5. 아모라의 제안 하나를 확인·수정·승인한다.
6. 승인 결과가 예산·체크리스트·일정 중 한 곳에 실제로 남는다.
7. 앱을 종료하고 다시 열어도 같은 결과와 다음 행동이 보인다.

### B. 매일 사용

1. 홈은 긴 기능 목록보다 오늘 할 일, 지연된 일, 변경 대기와 파트너 진행을 먼저 보여준다.
2. 사용자는 세 번 이내의 주요 행동으로 다음 일을 완료하거나 아모라에게 물을 수 있다.
3. 읽음, 완료, 승인 상태는 화면 이동과 재실행 뒤에도 일관된다.
4. 빈 상태는 막다른 화면이 아니라 다음 행동을 제공한다.

### C. 아모라에서 실행 도구로

1. AI의 제안과 확인된 사실을 구분한다.
2. 변경 전 대상, 이전 값, 새 값과 영향을 보여준다.
3. 사용자가 승인한 뒤에만 서버에 반영한다.
4. 서버 결과가 실패하면 성공 표시, 완료 애니메이션, 낙관적 확정 상태를 남기지 않는다.
5. 재시도와 중복 탭은 같은 변경을 두 번 실행하지 않는다.
6. AI 호출은 `ai_interactions_log`, 커플 결정은 `decision_nodes`에 남는다.

### D. 커플과 여러 기기

1. 두 실제 계정이 초대와 수락을 완료한다.
2. 한 기기의 예산·할 일·일정 변경이 파트너 기기와 웹에 반영된다.
3. 동시에 같은 항목을 수정했을 때 오래된 revision이 최신 결정을 덮지 않는다.
4. 로그아웃·로그인, 네트워크 단절·재연결, 앱 강제 종료 뒤에도 다른 계정 데이터가 섞이지
   않는다.
5. 커플 해제와 계정 삭제 뒤 캐시·알림·딥링크가 이전 관계를 다시 노출하지 않는다.

## 3. 모바일 품질 게이트

### G0 — 소스 품질

- mobile lint, typecheck, test가 같은 commit에서 통과한다.
- `mobile:release-check`와 Expo Doctor가 통과한다.
- iOS·Android 정적 export가 성공한다.
- 비밀값, 서비스 역할 키와 provider 키가 모바일 번들에 없다.

### G1 — 승인된 Preview와 백엔드

- 웹/API와 앱이 같은 승인된 Supabase project ref를 선언한다.
- 배포된 `/api/mobile/runtime-contract`가 200을 반환하고 앱 검증을 통과한다.
- staging migration, RLS 공격 테스트, Storage, backup·restore 증거가 commit과 연결된다.
- 아모라의 live provider, 실패 복구와 승인 도구 호출을 테스트 계정에서 확인한다.

### G2 — 실제 기기

- 지원할 최소·최신 iOS와 Android 실제 기기 조합에서 확인한다.
- 작은 화면, 큰 글자, 다크 모드 지원 여부, 키보드, Safe Area, 화면 회전을 정책대로 확인한다.
- 느린 네트워크, 오프라인, 백그라운드 복귀, 강제 종료, 토큰 만료를 확인한다.
- VoiceOver/TalkBack으로 로그인, 홈의 다음 행동, 아모라 승인, 주요 폼을 완료할 수 있다.
- 주요 탭과 홈의 첫 상호작용 지연, crash-free session, API 실패율을 내부 배포에서 측정한다.
  목표값은 측정 도구와 표본을 정한 뒤 릴리스 문서에서 승인하며 추정값을 성과처럼 쓰지 않는다.

### G3 — 두 계정·두 기기 E2E

- 신규 커플과 기존 커플을 각각 검증한다.
- 초대, 수락, 아모라 승인, 예산·할 일·일정 반영, 충돌, 재연결, 로그아웃·재로그인을 한
  시나리오로 끝까지 수행한다.
- 중복 실행, 잘못된 상대 데이터, 영구 로딩, 복구 불가능한 오류가 없어야 한다.
- 실패 화면은 사용자가 재시도하거나 지원을 요청할 수 있는 경로를 제공한다.

### G4 — 내부 배포와 스토어

- EAS iOS production build와 Android production build가 실제로 성공한다.
- Apple·Google 로그인과 출시 대상으로 승인된 다른 로그인 제공자를 실제 빌드에서 확인한다.
- Universal Link와 App Link가 실제 Team ID·서명 SHA-256으로 검증된다.
- 푸시 권한 거부·허용·토큰 갱신·로그아웃 후 차단을 확인한다.
- TestFlight와 Play 내부 테스트의 설치·업데이트·롤백 경로를 확인한다.
- 스토어 설명, 스크린샷, 개인정보 표시와 앱 안의 실제 기능이 일치한다.

### G5 — 운영 출시

- 운영 DB release controller, backup·restore, RLS, Storage와 finalizer 증거가 승인된다.
- Sentry 또는 승인된 오류 수집 도구에 release와 source commit이 연결된다.
- 고객지원 메일과 개인정보·계정 삭제 요청의 담당자·응답 절차를 실제로 시험한다.
- 점진 배포, 중단 기준, rollback 또는 kill switch와 담당자가 기록된다.
- 출시 후 첫 24시간과 7일 canary 관찰 계획이 있다.

## 4. 출시 차단 결함

다음 중 하나라도 있으면 출시하지 않는다.

- 로그인, 계정 삭제 또는 커플 경계에서 다른 사용자 데이터가 보인다.
- 승인하지 않은 예산·할 일·일정 변경이 저장된다.
- 서버 실패를 성공으로 표시하거나 중복 변경을 만든다.
- 운영 runtime contract가 없거나 웹과 앱의 Supabase 목적지가 다르다.
- 마이그레이션·RLS·백업·복구 증거가 없다.
- 실제 production EAS build와 내부 배포 증거가 없다.
- AI가 확인되지 않은 가격·사실을 확정적으로 저장하거나 위기 안전 경계를 우회한다.
- 필수 개인정보 고지, 삭제, 지원 경로가 실제 운영과 일치하지 않는다.

## 6. 다음 실행 순서

1. 현재 source를 승인된 Preview 웹/API와 staging Supabase에 배포한다.
2. 운영 전용 runtime contract, migration, RLS, backup·restore 증거를 만든다.
3. 모바일 내부 build를 같은 commit과 staging 환경에 연결한다.
4. 실제 두 계정·두 기기로 첫 10분과 커플 동기화 E2E를 수행한다.
5. 실제 AI·소셜 로그인·딥링크·푸시·오프라인 복구를 검증한다.
6. 접근성·성능·오류 관찰 결과로 앱 결함을 고친다.
7. TestFlight·Play 내부 테스트를 통과한 뒤 운영 배포 승인을 진행한다.

새 기능은 위 순서를 늦출 정도라면 추가하지 않는다. 앱 완성도는 화면 수가 아니라 첫 가치,
안전한 승인, 커플 동기화, 복구 가능성과 실제 기기 증거로 판단한다.
