## 0. 이 문서를 쓰는 법

지금까지 반복된 실패는 기능 부족이 아니라 **방향 상실**이었다. 매 세션 다른 것을 고치고,
"비슷한 게 있으니 됐다"고 넘어가고, 화면에 보이는 것과 실제가 다른 채로 다음을 얹었다.

그래서 규칙을 셋만 둔다.

1. **작업 시작 전** — 이 문서에서 해당 항목을 찾는다. 없으면 그 일은 지금 하지 않는다.
   정말 필요하면 먼저 이 문서에 항목으로 추가하고 단계·완료기준을 적은 뒤에 시작한다.
2. **작업 끝** — 완료기준(DoD)을 전부 만족했을 때만 `[x]`로 바꾼다.
   테스트가 없으면 완료가 아니다. "동작하는 걸 봤다"는 완료가 아니다.
3. **상태 표기는 실측으로만 바꾼다** — 부록 A의 상태는 코드 근거가 바뀌었을 때만 갱신한다.
   추정으로 올리지 않는다.

### 상태 표기

| 표기 | 뜻 |
|---|---|
| `없음` | 코드에 구조가 없다 |
| `부분` | 비슷한 게 있으나 2.0이 요구하는 구조가 아니다 |
| `있음(도달불가)` | 구현돼 있으나 플래그 뒤에 있거나 진입점이 없다 |
| `있음(라이브)` | 오늘 사용자가 실제로 만난다 |

## 1. 우리가 만드는 것

> **웨딩한방은 결혼 준비 도구를 제공하는 서비스가 아니다.
> 아모라가 두 사람의 기준을 이해하고, 지금 필요한 한 결정을 쉽게 끝내며,
> 그 결과를 실제 계획에 남겨주는 서비스다.**

### 제품 DNA — 모든 화면·기능이 통과해야 하는 6원칙

- **① 다음 행동이 먼저다** — 첫 화면은 현황판이 아니라 "지금 할 한 가지"
- **② 기준을 만들고 나서 검색한다** — 업체·상품을 먼저 보여주지 않는다
- **③ 모르는 것도 유효한 답이다** — 모든 질문에 모르겠어요/추천해주세요/나중에
- **④ 결혼은 정답이 아니라 선택의 조합이다** — 예단·예물·폐백·한복·스드메를 기본값으로 만들지 않는다
- **⑤ 말로 끝내지 않고 계획에 남긴다** — 대화의 결정이 승인 후 일정·예산에 반영된다
- **⑥ 불안보다 통제감을 준다** — `2/132 완료`, 빨간 지연 숫자로 압박하지 않는다

### 미션 = 제품의 기본 단위

메뉴가 아니라 **미션**이다. 미션은 결정 하나를 끝내는 짧은 과정이고, 모든 영역에서 같은 5단계다.

```
① 짧게 이해   이 결정이 무엇이고 왜 지금 필요한지
② 우리 기준   쉬운 질문과 선택으로 선호를 구체화
③ 현실 확인   공시가, 실제 사례, 계약 주의점
④ 행동        후보 저장, 방문 예약, 예산 조정
⑤ 반영 확인   무엇이 바뀌었고 다음에는 무엇을 하는지
```

**승인→실행→영수증 한 축만 끝까지 살아 있고, 나머지는 조각으로 흩어져 있다.**
특히 2.0의 출발점인 "기준"과 "미션"은 데이터 구조 자체가 없다.

### 지금 잘 되어 있는 것 (건드리지 말 것)

- **승인 흐름** — 제안 → 승인 카드(예산 영향 미리보기 포함) → 실행 → 영수증이 서버 봉인

- **모델은 어떤 턴에도 변경 도구를 직접 받지 않는다** — 아모라가 혼자 뭘 바꿀 물리적 경로가 없음
- **승인 카드는 한 턴에 정확히 1개** — 2개 이상이면 파싱 무효
- **예식일·예산이 없으면 문자열 생성 단계에서 빈 값** — 모델이 지어낼 수 없음

- **현실 확인 재료 4종 라이브** — `get_market_price` `simulate_guest_guarantee` `analyze_quote`

## 4. 단계 1 — 첫 완성형 세로 흐름

> **범위**: 가입 → 시작 코스 → 우리 기준 카드 → 웨딩홀 기준 미션 → 후보 비교 → 투어 일정·예산 반영
> **원칙**: 전 기능을 동시에 다시 만들지 않는다. **하나의 여정을 끝까지 연결**하는 것이 먼저다.

### 1-1. 데이터 모델: 기준(Criterion) `부분`

지금 있는 것: `set_amora_core_criterion_v1`(2026-08-14) — 자유 텍스트 **1줄 120자 하나**.
커플 합의 상태기계(제안→양측 수락→confirmed)는 제대로 있다.
없는 것: 항목별 기준을 여러 개 보관하는 구조.

- [ ] 기준 카드 스키마 설계 — 축: 시기 / 지역 / 하객 / 예산상한 / 우선순위 / 분위기
- [ ] 각 축의 값 상태: `정함` / `미정(이유)` / `추천받음` / `해당없음`
- [ ] 기존 커플 합의 상태기계를 축 단위로 확장 (제안·수락 구조 재사용)
- [ ] 마이그레이션 + RLS + 서비스 전용 ACL
- [ ] 기준 카드 읽기 API + 화면

**DoD** — 6축이 각각 독립적으로 정해지고, 각 축의 미정 사유가 저장·표시된다.
커플 두 사람이 각자 제안하고 합의하는 흐름이 축 단위로 동작한다.

### 1-2. 지역 기준 신설 `없음`

`region` enum은 견적 진단 1건마다 붙는 **일회성 입력**이고 커플의 지속 기준이 아니다.
`wedding_journeys`에는 식장 이름 TEXT만 있고 지역 필드가 없다.
**지역이 없으면 미션 3단계(현실 확인)의 공시가·지역 중위가 비교가 성립하지 않는다.**

- [ ] 커플 단위 지역 기준 필드 신설 (다중 선택 허용: "강남권 또는 수도권")
- [ ] 기존 `amora_quote_checks.region`과의 관계 정리 (기준 → 기본값 제공)
- [ ] 공시가·시세 조회가 이 기준을 읽도록 배선

**DoD** — 기준에 지역을 정하면 이후 모든 현실 확인이 그 지역으로 자동 조회된다.

### 1-3. 시작 코스 `없음`

**현재 실태 (반박 검증됨)**: 모바일 온보딩의 기본 경로는 폼이 아니다.
스텝2의 주 버튼이 `아모라와 지금 시작하기` → `handleSubmit("quick_start")` →
**날짜·장소·예산 전부 null, progress `{}`** → 곧장 채팅.
스텝3·4(시기·예산·하객·우선순위·분위기)는 보조 텍스트 버튼을 누른 사람만 본다.
웹 join 경로도 스텝2 직후 제출해 3·4·5를 통째로 건너뛴다 — **합류하는 파트너에게는
총예산을 한 번도 묻지 않는다.**

즉 시작 코스는 백지에서 만드는 게 아니라, **이미 존재하는 `quick_start` → 채팅 진입점 위에 얹는다.**

- [ ] 아모라 인테이크 대화 설계 — 한 화면 한 결정, 설명 2~3문장, 선택지 3~5개
- [ ] 9개 축 질문: 시기·지역·하객·총예산·우선순위·분위기·문화선택·가족변수·참여방식
- [ ] 모든 질문에 `모르겠어요` / `추천해주세요` / `나중에 정할게요`
- [ ] 답을 바꾸면 영향받는 일정·예산을 즉시 보여준다
- [ ] 민감한 가족·관계 질문은 **비공개 여부를 먼저 설명**한다
- [ ] 산출물 5종 생성: 기준 카드 / 선택 지도 / 첫 4주 계획 / 예산 초안 / 첫 미션
- [ ] 종료 문구: "설정이 완료되었습니다" ❌ → "우리 결혼의 첫 계획이 생겼어요" ✅

**DoD** — 가입 후 15분 안에 위 5종 산출물이 생기고, 사용자가 한 번도 빈 화면을 만나지 않는다.
`quick_start`로 들어와도 코스가 이어진다.

### 1-4. "모르겠어요"를 1급 값으로 `없음`

현재 선택지 상수 4종(스타일·우선순위·예산성향·하객수) 어디에도 모름 값이 없고,
서버 검증이 화이트리스트라 그 값이 오면 **400**이 된다.
필드를 비우는 건 가능하지만 그건 "모른다"가 아니라 "무응답"으로 저장돼 아모라가 구분할 수 없다.

- [ ] 선택지 상수 4종에 `unknown` / `recommend_me` / `later` 추가
- [ ] 서버 화이트리스트 확장 + 검증 테스트
- [ ] `decision_type`에 미정 상태 추가 (현재 exploring/considering/decided/scheduled/booked/completed)
- [ ] 미정 사유 필드 (`reasoning`은 있으나 AI 추출기만 채움)
- [ ] 아모라가 "모르겠어요"를 받으면 **설명 → 추천 → 재질문** 순서로 대응

**DoD** — "모르겠어요"를 고른 축이 기준 카드에 이유와 함께 남고,
아모라가 그 축을 다음 대화에서 먼저 설명한다.

### 1-5. 미션 엔티티 신설 `없음`

`mission` 식별자가 저장소 전체에 0건. 조각은 있다:

| 미션 단계 | 현재 존재하는 조각 | 상태 |
|---|---|---|
| ① 짧게 이해 | `todayOneCare.whyNow` | 있음(도달불가) |
| ② 우리 기준 | `amoraCoreCriterion` (1줄) | 부분 |
| ③ 현실 확인 | `confirmed[]` / `unknown[]` + 도구 4종 | 부분 |
| ④ 행동 | `nextAction` + 승인 흐름 | 있음(라이브) |
| ⑤ 반영 확인 | `amoraActionFollowUp` (completed/blocked/changed/not_sure) | 있음(도달불가) |

**조각을 하나의 미션 인스턴스로 묶는 식별자·진행 상태·단계 전이가 없다.**

- [ ] 미션 스키마: id, 종류, 대상 결정, 현재 단계, 산출물, 시작·완료 시각
- [ ] 5단계 전이 규칙 (건너뛰기·되돌아오기 허용)
- [ ] `todayOneCare` 계약을 미션 ①③ 단계 공급자로 재사용
- [ ] `amoraActionFollowUp`을 미션 ⑤ 단계로 연결
- [ ] 첫 미션 1종만 구현: **웨딩홀 기준 세우기**

**DoD** — 웨딩홀 기준 미션 하나가 ①→⑤까지 끊김 없이 진행되고,
중간에 나갔다 돌아와도 같은 단계에서 이어진다.

### 1-6. 진행률의 새 의미 `없음`

- [ ] `기준 6개 중 n개 정함` 계산
- [ ] `이번 주 결정 n개 · 약속 n개`
- [ ] `아직 안 정해도 되는 것 n개` (시기상조 상태값 신설 필요)
- [ ] `확인이 필요한 위험 n개`
- [ ] 웹 대시보드의 `n/132개 직접 체크` 제거
- [ ] 모바일 `준비 진행 N%` 바 교체

**DoD** — 어느 화면에도 `n/132` 형태가 남지 않는다(테스트로 고정).

### 1-7. 첫 미션 검증 질문

이 흐름이 끝나면 **실제 커플 3~5쌍**에게 물어 확인한다.

- [ ] 사용자가 질문 없이도 다음 단계로 갈 수 있는가?
- [ ] 아모라의 질문으로 유용한 기준이 만들어지는가?
- [ ] 결정이 실제 일정·예산에 일관되게 반영되는가?
- [ ] 사용자가 현재보다 덜 복잡하다고 느끼는가?

## 5. 단계 2 — 코스 확장

> 단계 1의 검증 질문 4개가 전부 예가 된 뒤에 시작한다.

### 2-1. 선택 지도 (유지·축소·대체·생략·미정) `없음`

현재 `not_applicable`은 **카테고리 단위 on/off 토글 하나**이고
왜 뺐는지·대안이 뭔지 적는 자리가 없다. 항목 단위 생략도 불가.
"축소"·"대체"라는 상태값은 코드 어디에도 없다.

- [ ] 5분류 상태값 신설 + 사유·대안 필드
- [ ] 항목(item) 단위 적용
- [ ] 문화 항목(예단·예물·폐백·한복) 우선 적용
- [ ] 선택 지도 화면

### 2-2. 예산 범위형 배분 `없음`

총예산·카테고리 예산 모두 **단일 정수**다. min/max·범위 필드가 스키마에도 타입에도 없다.
모바일 예산 화면은 이 단일값으로 사용률 %와 초과액을 계산 — **범위가 아니라 정답 대비 초과로 보인다.**

- [ ] 범위형 필드 신설 (하한·상한·신뢰도)
- [ ] 예산 초안 생성기 (기준 → 항목별 범위 배분)
- [ ] "초과" 표현을 "범위 밖" 표현으로 교체

### 2-3. 나머지 미션

- [ ] 스드메·본식 촬영 미션
- [ ] 문화 항목 유지·축소·대체·생략 미션
- [ ] 가족 논의와 보류 관리

### 2-4. 아모라 4역할 재정의 `없음`

프롬프트의 현재 4역할은 **곁에 있기 / 탐색 / 결정 / 실행**으로 2.0과 다르다.
겹치는 건 실행뿐이고, 해설자·계획자에 해당하는 역할 이름이 없다.
게다가 이 4개는 턴마다 하나만 고르는 **대화 모드**이지 지속적 능력 축이 아니다.

- [ ] 4역할을 안내자·해설자·계획자·실행자로 재정의
- [ ] 해설자: 용어 설명을 하드코딩에서 **도구**로 (현재 프롬프트 정적 주입)
- [ ] 계획자: 대화 중 구조화 저장 경로 신설 (현재 라이브 쓰기는 폼 4곳뿐)

### 2-5. 되돌리기 `부분`

일반 undo가 없다. `restore_schedule_event` 1종만 있고
예산·체크리스트·행동카드 변경에는 되돌리기 도구도 UI 버튼도 없다.
채팅 화면 전체에 undo 식별자 0건.

- [ ] 승인된 변경의 되돌리기 경로 설계 (승인과 같은 수준의 안전장치)
- [ ] 영수증에 되돌리기 안내 포함

## 8. 하지 않을 것

전략 문서의 금지 목록에 코드 실측으로 확인된 것을 더한다.

- 기존 기능을 그대로 둔 채 홈 화면만 예쁘게 바꾸지 않는다
- 긴 체크리스트를 새 카드 디자인으로 포장하지 않는다
- 아모라를 별도 채팅 탭에 가두지 않는다
- AI가 승인 없이 일정·예산을 바꾸지 않는다
- 모든 커플이 같은 항목을 해야 한다고 가정하지 않는다
- 업체 수와 콘텐츠 수를 첫 화면의 가치로 내세우지 않는다
- 진행률을 불안 자극 장치로 쓰지 않는다
- 첫 출시에서 모든 기존 기능의 재구현을 목표로 삼지 않는다
- **업체 추천·예약·검색을 공급 확보 전에 켜지 않는다** (파운더 확정)
- **계약·위약금·환불·법률 자문 영역에 들어가지 않는다** (파운더 확정)
- **`deployment_blocked`와 증거 5종 missing을 우회하지 않는다**
- **점수·등급·"최고"·"보장"으로 업체·가격·품질을 판정하지 않는다**

## 9. 성공 지표

### 북극성

**주간 완료된 의미 있는 결정 수.** 단순 체크가 아니라 셋을 모두 만족해야 한다.

1. 사용자의 기준 또는 선택이 구조화됨
2. 필요한 경우 일정·예산·후보에 반영됨
3. 다음 행동 또는 **명시적 보류**가 남음

### 핵심 지표

- [ ] 가입 후 24시간 내 시작 코스 완료율
- [ ] 시작 코스에서 첫 계획 생성까지 걸린 시간
- [ ] 추천된 다음 단계의 7일 내 완료율
- [ ] 아모라 제안 → 승인 → 실행 성공률
- [ ] 동일 예산·일정 값의 화면 간 불일치율 ← **0단계 검증 지표**
- [ ] 모르겠어요 선택 후 추천을 받아 결정한 비율
- [ ] 업체 검색 전 기준 카드 생성률
- [ ] "다음에 무엇을 해야 할지 안다" 동의율
- [ ] "결혼 준비가 전보다 정돈되고 쉬워졌다" 동의율

> 페이지 체류시간과 채팅 횟수는 성공 지표가 아니다.
> 빨리 이해하고 결정했다면 짧은 사용 시간이 더 좋은 결과다.

### 지금 측정할 수 없는 것 (계측 먼저)

- 로그인 없는 데모 대화는 로그를 남기지 않는다 — 가장 중요한 첫 10분이 가장 안 보인다
- 승인 카드 수명(제안·승인·만료) 이벤트 없음

- [ ] `question_scope` 로깅 추가 (조건문 한 줄)

- [ ] 승인 카드 수명 이벤트
