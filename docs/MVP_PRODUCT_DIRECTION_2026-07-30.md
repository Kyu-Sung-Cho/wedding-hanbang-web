## 1. 한 줄 정의

**웨딩한방은 아모라에게 결혼 준비를 말하면, 예산·체크리스트·일정이 함께 정리되는
서비스입니다.**

더 짧게 말할 때:

**결혼 준비, 아모라와 정리하세요.**

첫 방문자가 이 두 문장만 읽어도 다음을 알아야 한다.

- 아모라는 단순 질문 답변 챗봇이 아니다.
- 대화한 내용이 실제 준비 도구로 이어진다.
- 이 서비스의 중심은 업체 탐색이나 게시판이 아니라 내 결혼 준비다.

## 2. 제품 위계

### 제품: 아모라

아모라는 사용자의 예식일, 준비 단계, 예산과 확인된 결정을 바탕으로 지금 할 일을
정리한다. 변경이 필요하면 바뀔 내용을 먼저 보여주고, 사용자가 승인한 뒤에만 반영한다.

### 실행 도구: 예산·체크리스트·일정

세 도구는 각각 별개의 생산성 앱이 아니다. 아모라가 대화에서 확인한 결혼 준비를
지속적으로 관리하는 실행 화면이다.

- 예산: 얼마를 계획했고 실제로 얼마를 쓰는지
- 체크리스트: 무엇을 해야 하고 무엇을 끝냈는지
- 일정: 언제까지 해야 하고 어떤 약속이 잡혀 있는지

### 경험 보조 축: 커뮤니티

커뮤니티는 제품의 첫 설명이 아니다. AI가 직접 경험할 수 없는 실제 후기와 사례를
사용자가 찾고 질문하는 곳이다. 커뮤니티에서 얻은 정보는 그대로 사실로 확정하지 않고,
필요한 경우 아모라 대화와 내 체크리스트·예산·일정으로 다시 가져온다.

## 3. MVP 범위

모바일 우선 MVP의 전면 기능은 아래 다섯 가지뿐이다.

1. 아모라
2. 예산 관리
3. 체크리스트
4. 일정 관리
5. 커뮤니티

화면 내비게이션에서는 체크리스트와 일정을 `할 일·일정`으로 묶을 수 있다. 사용자가
해야 할 일과 마감 날짜를 분리된 제품처럼 배울 이유가 없기 때문이다.

필수 설정, 로그인, 커플 연결, 개인정보·AI 정책은 기능 목록이 아니라 제품 운영 기반이다.

## 4. 핵심 사용 흐름

1. 사용자가 아모라에게 예식일과 지금 상황을 말한다.
2. 아모라가 지금 먼저 처리할 한 가지와 필요한 후속 항목을 짧게 제안한다.
3. 사용자가 확인하거나 수정하고 반영을 승인한다.
4. 승인된 내용이 예산·체크리스트·일정에 남는다.
5. 실제 경험이 필요하면 커뮤니티에서 찾거나 질문한다.
6. 확인한 내용을 다시 아모라와 정리해 다음 행동으로 남긴다.

이 흐름에 연결되지 않는 기능은 MVP 우선순위가 아니다.

## 5. 첫 화면과 내비게이션

### 모바일 앱

- 모바일 앱이 소비자의 주 제품이다.
- 첫 실행의 첫 성과는 예식일 입력과 아모라 제안 하나의 승인·반영이다.
- 로그인 후 홈은 D-day 장식보다 `지금 할 한 가지`, 변경 대기, 커플 진행 상황을 먼저
  보여주는 실행 화면이다.
- 하단 내비게이션은 `홈`, `아모라`, `커뮤니티`, `마이`를 유지한다. 예산과 할 일·일정은
  홈과 아모라의 실행 결과에서 자연스럽게 진입한다.
- 네이티브 화면은 좁은 웹 복사본이 아니라 짧은 세션, 한 손 조작, 중단 후 복귀와
  커플 동기화를 기준으로 완성한다.

### `/landing`

- 웹 랜딩은 앱 설치·가입 전 제품을 이해시키는 유입 표면이다.
- 첫 문장은 아모라의 한 줄 정의다.
- 첫 행동은 `아모라와 시작하기`다.
- 예산·체크리스트·일정이 아모라와 연결된다는 사실을 바로 보여준다.
- 공시가격과 신뢰 근거는 아모라 설명 뒤에 둔다.

### `/wedding`

- 웹에서 계속 준비하려는 사용자를 위한 데스크톱 연속성 표면이다.
- 첫 블록은 아모라다.
- 그 아래에서 예산·체크리스트·일정의 연결을 보여준다.
- 커뮤니티 검색과 피드는 그다음에 둔다.
- 공시가격이나 견적 도구는 필요한 맥락에서 연결하되 첫 약속을 차지하지 않는다.

### 주요 내비게이션

주요 항목은 다음 네 개로 정리한다.

- 아모라
- 할 일·일정
- 예산
- 커뮤니티

로그인 후 `오늘 할 일` 화면은 요약 홈 역할을 한다. 설정은 보조 메뉴로 둔다.

## 6. 전면에서 내릴 범위

다음 기능은 삭제하지 않지만 MVP의 첫 화면, 주요 내비게이션, 핵심 소개에서 내린다.

- 업체 탐색
- 예약 관리
- 축의금 관리
- 공시가격을 독립 제품처럼 소개하는 구성
- 저장한 이야기의 독립 메뉴
- WeddingCode
- 오늘 한 마디
- 견적 체크의 독립 제품화
- 웹을 모바일과 경쟁하는 별도 주 제품으로 확장하는 구성
- 결제·정산·전자계약
- 드레스 가상 피팅

공시가격과 견적 체크는 아모라 또는 커뮤니티에서 근거가 필요한 순간에 사용하는
보조 기능으로 유지할 수 있다. 별도 성장 축으로 확장하지 않는다.

## 7. 모바일 아모라 MVP 완료 조건

아모라는 대답을 잘하는 것만으로 완료되지 않는다. 아래 흐름이 실제로 이어져야 한다.

- 예식일과 준비 상황을 읽는다.
- 사용자가 말한 금액을 예산에 반영할 수 있다.
- 해야 할 일을 체크리스트에 남길 수 있다.
- 날짜가 있는 일은 일정에 남길 수 있다.
- 변경 전에 정확히 무엇이 바뀌는지 보여준다.
- 승인된 결과와 실패 결과를 구분한다.
- 다음 대화에서 이미 확인한 사실을 불필요하게 다시 묻지 않는다.
- 실제 경험이 필요한 질문은 커뮤니티 확인이 필요하다고 구분한다.
- 앱을 종료했다가 다시 열어도 승인된 결과와 다음 행동이 일관되게 보인다.
- 파트너 기기와 웹에서 같은 변경이 중복 없이 반영된다.
- 네트워크 단절, 재시도, 오래된 revision에서 성공처럼 보이는 거짓 상태를 만들지 않는다.

모바일 출시 완료 증거는 `docs/MOBILE_PRODUCT_COMPLETION_STANDARD_2026-08-03.md`를
따른다. 로컬 테스트와 정적 export만으로 앱 출시 완료를 주장하지 않는다.

## 8. MVP 지표

첫 번째 활성화 기준:

**모바일 가입 후 한 세션 안에 예식일을 입력하고, 아모라의 제안 하나를 승인해
예산·체크리스트·일정 중 하나에 남긴 커플**

웹에서 같은 활성화를 마친 경우도 연속 사용 데이터에는 포함할 수 있지만, 모바일 앱의
첫 활성화와 실제 기기 재방문 지표를 별도로 본다.

핵심 사용 지표:

- 아모라 제안 승인 후 도구 반영 성공률
- 첫 세션 내 첫 행동 완료율
- 일주일 안에 아모라 또는 오늘 할 일로 다시 돌아온 커플 비율
- 체크리스트 완료 또는 일정·예산 갱신으로 끝난 대화 비율
- 커뮤니티 글을 본 뒤 아모라 또는 내 준비 도구로 돌아온 비율

페이지 조회 수, 대화 수, 게시글 수만으로 제품 성공을 판단하지 않는다.

## 9. 출시 전 질문

새 기능이나 화면을 추가하기 전에 아래 질문에 답한다.

1. 이 기능이 아모라의 핵심 흐름을 더 잘 이어주는가?
2. 예산·체크리스트·일정 중 어디에 실제 결과가 남는가?
3. 사용자가 한 줄 정의를 이해하는 데 방해가 되지 않는가?
4. 기존 MVP 기능 하나를 더 깊게 만드는 것보다 우선인가?
5. 실제 사용자 행동으로 효용을 검증할 수 있는가?
6. 실제 iOS·Android 기기에서 중단·재시도·파트너 동기화까지 안전한가?

하나라도 설명하지 못하면 MVP 이후로 미룬다.

## 10. 채널 역할과 배포 계약

### 모바일 앱

- 소비자의 주 사용 채널이자 제품 완성도의 최우선 기준이다.
- 홈, 아모라, 커플 동기화, 예산·할 일·일정 반영의 품질을 먼저 깊게 만든다.
- 네이티브 UI 변경은 Expo Update 또는 새 앱 빌드가 필요하다.

### 웹

- 유입, 제품 설명, 정책·고객지원, 관리자 운영과 데스크톱 연속성을 담당한다.
- 웹에서 바뀐 서버 데이터와 계약은 앱과 공유하지만 React/Next.js 화면 코드가
  React Native 화면으로 자동 복사되지는 않는다.
- 웹 단독 기능 수를 늘리는 일은 모바일 핵심 흐름의 완성보다 우선하지 않는다.

### 공유 백엔드

- 웹과 앱은 같은 Supabase Auth, 커플 데이터, 승인 결과와 Realtime 계약을 사용한다.
- 호환 계약을 바꿀 때는 `웹/API 배포 → runtime contract 확인 → 모바일 내부 배포 →
  실제 두 계정·두 기기 확인` 순서를 지킨다.
- 운영 배포와 실제 기기 증거가 없으면 “웹과 앱이 완전히 연결됐다”고 말하지 않는다.
