# 개인·팀·업체 참여와 승인 후 직접 게시

> 이후 검색·관리자 목록·서비스 철회·편집 상태·모바일 진입을 보완했다.
> 최신 구현·검증·운영 경계는 [2026-09-29 결과](PROVIDER_DELIVERY_2026-09-29.md)를 우선한다.

## 이번 구현의 제품 계약

한방이 등록과 관리 권한을 승인하면 제공자는 소개글, 공개 링크와 작업 사진을 직접 저장한다. 이미 공개한 프로필에는 곧바로 반영된다. 첫 공개와 공개 중단은 제공자가 선택한다. 등록 승인으로 자동 공개하거나 추천 자격까지 부여하지 않는다.

서비스 가격·포함 항목·추가 비용·이용 조건은 서비스별 검토를 받는다. 해당 조건을 바꾸면 그 서비스는 공개·추천에서 빠지고 재검토를 기다린다. 소개글과 사진은 계속 직접 관리한다. 한방 관리자는 사유를 남겨 프로필 전체 노출을 중지할 수 있고, 복구 후에는 제공자가 다시 공개한다.

개인, 팀, 업체가 같은 절차를 사용한다. 팀도 활동명으로 참여할 수 있으며 이번 버전의 관리 계정은 대표 담당자 한 명이다. 팀원 초대와 여러 계정의 공동 편집은 포함하지 않는다.

## 실제 화면과 연결

| 경로 | 동작 |
|---|---|
| `/business` | 참여 안내, 서비스·공간 등록과 비즈니스 문의 진입 |
| `/business/register` | 활동 형태·분야·지역·담당자와 참여 내용 제출 |
| `/business/inquiry` | 협업·미디어·데이터·기타 문의, 별도 접수 |
| `/provider` | 심사 상태·보완 요청·소개글·사진·공개 상태·서비스·문의 답변 관리 |
| `/discover` | 공개를 선택한 승인 제공자 탐색 |
| `/providers/[id]` | 제공자가 작성한 소개·사진·검토된 서비스 조건과 공개 채널 |
| `/admin/providers` | 등록 심사, 서비스 검토, 추천 자격, 노출 정지·복구, 문의 답변 |

실제 랜딩 푸터에 참여 안내·서비스 등록·비즈니스 문의·제공자 센터와 탐색 링크를 연결했다. 제공자 가입·로그인은 신청 목적지를 유지하며 커플 온보딩을 요구하지 않는다. 계정의 서버 검증 동의 기록과 확인된 이메일이 필요하다. 문의 답변은 제공자 센터에서 확인하며 이메일 발송을 주장하지 않는다.

`standard_terms` 동의 키는 공개한 서비스 조건 준수와 실제 적용 약관·취소 기준 안내의 확인이다. 특정 계약서에 서명하거나 고객과 계약을 체결했다는 의미가 아니다. 개인정보 처리방침·이용약관과 실제 입력 화면에 목적·항목·보유·공개 범위·삭제 경로를 반영했다.

## 공개·추천·사진의 경계

- 신규 제공자 정보는 기존 한국소비자원 공시 가격·legacy 업체 승인 데이터와 구분한다. 가격은 제공자가 작성한 기본 조건이며 희망일 예약 가능 여부는 확인하지 않았다.
- 개인·팀·업체라는 활동 형태, 광고나 제휴 여부가 추천 순위를 높이지 않는다. 아모라는 별도로 추천 자격을 검토한 공개 서비스만 조건에 맞춰 조회한다.
- 연락 담당자 이름·계정 이메일·심사 메모는 공개 카탈로그에서 제거한다. 자기 소개·사진은 제공자가 공개를 선택한 범위다.
- JPG·PNG·WebP 사진은 실제 디코딩 후 WebP로 다시 만들어 EXIF 등 원본 메타데이터를 보관하지 않는다. 최대 12장, 장당 입력 5 MiB 제한을 적용한다.
- 사진은 `provider-portfolio` 비공개 버킷에 저장한다. 공개 또는 소유자 미리보기 권한을 매번 검사한 API를 통해 전달하고 브라우저·CDN 캐시를 사용하지 않는다. 공개 중단·정지·삭제 접수 후에는 새 요청에 bytes를 제공하지 않는다. 이미 내려받은 사본까지 회수할 수 있다는 뜻은 아니다.
- 공개 철회와 저장소 파일 삭제를 구분한다. 저장소 장애 시 철회는 유지하고, 미완료 파일은 별도 정리 작업으로 재시도한다. 계정 삭제에는 등록 중 파일까지 포함하고 업로드 종료 유예 후 저장소 목록을 다시 확인한다.
- 모든 쓰기는 현재 계정·소유권 또는 관리자 권한을 서버와 DB에서 검사한다. 승인·심사 변경에는 버전을 대조한다. 접수 재시도에는 요청 식별자를 사용한다.

과거 릴리스 성공 테스트는 고정된 Git 원문 fixture로 분리했다. 신규 SQL이 들어간 현재 checkout은 과거 owner 서명을 넣어도 차단됨을 검증했다. 운영 guard·manifest·마이그레이션 허용 목록은 완화하지 않았다.

웹 전체 테스트도 한 차례 끝까지 실행했다. 결과는 1,131개 파일 중 1,123개 통과·8개 실패, 개별 테스트 18,247개 통과·17개 실패·33개 expected fail, 소요 1,747.40초였다. 실행 도중 최종 수정이 겹쳤으므로 이 결과를 현재 코드 전체의 일괄 통과로 보고하지 않는다. 실패한 8개 파일은 위 기록처럼 수정·재실행했다. `productionBuildBudgetFollowup.test.ts`는 영향받는 12개만 다시 실행했고, 나머지 7개 파일은 파일 단위로 재실행해 통과했다. 현재 코드로 전체 1,131개 파일을 두 번째 실행한 기록은 없다.

운영 적용에는 Storage 제한 정책과 신규 SQL을 같은 검토된 릴리스 단위로 적용한 뒤 웹을 배포해야 한다. 현재 저장소의 운영 규칙은 [AGENTS.md](../AGENTS.md)의 `운영 DB·Storage·배포 규칙`이며, 허용된 `supabase:release:apply` 경로와 사전 운영 증거를 요구한다. 이 변경용 운영 릴리스 컨트롤러·hosted 사후조건·실제 사진 bytes 검증을 완료하기 전에는 운영 사용 가능으로 보고하지 않는다. 다른 릴리스의 과거 통과 기록을 새 변경의 증거로 재사용하지 않는다.

배포 전 확인 순서:

1. Storage 제한 정책, participation, account deletion, media cleanup SQL 순서를 새 릴리스 계약에 고정한다.
2. 승인된 환경에서 기존 manifest 함수와 비대상 자원 보존, 실제 Storage 정책 권한, rollback·복구 증거를 확인한다.
3. 운영 변경 규칙의 fence·백업·복구 조건을 충족한 허용 컨트롤러로 적용하고 사후조건을 검증한다.
4. 웹 배포 후 시험 계정으로 신청 → 관리자 승인 → 소개/사진 저장 → 공개 → 수정 즉시 반영 → 중단 → 정지/복구를 검증한다.
5. 별도 서비스 심사·추천 제외/복구와 사진 삭제·계정 삭제의 실제 저장소 정리를 확인한다.
