## 1. 최종 제품 결정

### 사용자에게는 아모라 입구 하나를 유지한다

사용자는 질문할 때마다 “예산 건”, “상견례 건”, “갈등 건”을 먼저 만들거나 고르지
않는다. 아모라를 열고 자연어로 말한다. 제품의 첫 인상과 주요 내비게이션도 계속
`아모라` 하나다.

### 그러나 내부를 하나의 무한 원문 채팅으로 유지하지 않는다

사용자에게는 한 대화처럼 자연스럽게 보이되, 모델이 읽는 원문 맥락은 범위별
`conversation segment`로 끊는다. 이전 세그먼트의 원문을 새 세그먼트에 자동으로
가져오지 않는다. 대신 사용자가 확정한 결정, 실제 도구 상태, 실행 영수증만 정본으로
이어간다.

### 사용자에게 보이는 공간은 두 개, 전달 레인은 세 개다

사용자에게 보이는 공간:

1. `함께 대화`
2. `나만 (상담)`

실제 작성·전송 레인:

| 레인 | 공개 범위 | 수신 대상 | 허용 |
|---|---|---|---|
| `shared_ai` | 커플 공유 | 아모라 | 허용 |
| `shared_partner` | 커플 공유 | 상대방 | 허용 |
| `private_ai` | 현재 사용자 개인 | 아모라 | 허용 |
| `private_partner` | 개인 | 상대방 | **존재하지 않음** |

`private_partner`는 의미적으로 모순이다. 상대방에게 보내는 순간 개인 상담이 아니므로
UI, 타입, API 어디에도 만들지 않는다.

### 준비 건은 사용자가 관리하는 채팅 폴더가 아니라 결정 그래프에서 파생한다

상견례, 예식장, 스드메처럼 장기 준비 건을 별도 대화방으로 자동 이동하지 않는다.
하나의 준비 건은 승인된 `decision_nodes`와 도구 projection을 중심으로 묶고, 채팅은
그 결정의 근거와 과정으로 연결한다. 분류 신뢰도가 낮은 AI가 메시지를 잘못된 방으로
옮기는 위험을 만들지 않는다.

## 2. 왜 이 구조인가

### 하나의 무한 채팅이 실패하는 방식

- 오래된 가정과 최신 결정이 동시에 모델 문맥에 들어가 답변이 흔들린다.
- 이미 취소되거나 수정된 승인 카드를 다시 살릴 수 있다.
- 개인 상담과 공유 상담의 원문을 합치기 쉬워진다.
- 상대방에게 직접 보낸 말이 아모라의 판단 근거로 섞일 수 있다.
- 긴 대화에서 최근 40개 같은 임의 절단이 실제 주제 경계 역할을 대신한다.
- 사용자는 화면을 “새로 시작”했는데 모델은 예전 원문을 계속 읽는 불일치를 겪는다.
- 한 번의 잘못된 답변이 이후 모든 답변의 전제가 된다.

### 사용자에게 준비 건 목록을 먼저 보여주는 구조가 실패하는 방식

- 사용자가 질문 전에 정보구조를 배워야 한다.
- “이건 예산인가 가족 갈등인가”처럼 실제로 겹치는 문제를 억지로 하나에 넣게 된다.
- 자동 분류가 틀리면 사용자는 대화가 사라졌다고 느낀다.
- 아모라가 하나의 플래너가 아니라 여러 작은 챗봇 모음처럼 보인다.
- 모바일에서 방 목록과 분류 조작이 대화보다 앞에 나온다.

### 선택한 절충안

```text
사용자 표면
  아모라 한 입구
    ├─ 함께 대화
    │   ├─ 아모라에게
    │   └─ 상대방에게
    └─ 나만 (상담)
        └─ 아모라에게

내부 문맥
  현재 segment 원문
    + 확인된 결정
    + 실제 예산·할 일·일정 상태
    + 유효한 승인 대기안
    + 동의된 범위의 기억
```

사용자는 단순한 구조를 경험하고, 시스템은 오래된 원문·공개 범위·실행 상태를
명시적으로 통제한다.

## 3. 대화와 정본 상태를 분리한다

아모라의 상태는 한 테이블이나 한 메시지 배열로 만들지 않는다.

| 계층 | 역할 | 정본 여부 |
|---|---|---|
| 원문 메시지 | 사용자가 실제로 말한 내용과 AI 답변 | 근거 원문, 결정 정본 아님 |
| conversation segment | 이번 대화에서 모델이 읽을 원문 경계 | 현재 원문 범위 정본 |
| 제안·승인 대기 | 아직 실행되지 않은 변경안 | 버전이 고정된 후보 |
| `decision_nodes` | 사용자가 확인한 결정과 폐기 이력 | 결정 정본 |
| 예산·할 일·일정 | 승인된 결정의 현재 실행 상태 | 각 도구 상태 정본 |
| 실행 영수증 | 실제 DB 결과와 변경 전후 | 완료 주장의 정본 |
| 동의된 기억 | 다음 대화에 재사용 가능한 제한된 맥락 | 사용자 통제 보조 맥락 |

모델이 “저장했어요”라고 말한 문장은 어떤 계층의 성공 증거도 아니다. DB 실행 결과를
다시 읽은 영수증이 있을 때만 완료다.

## 4. 현재 확인된 구현 상태

### 4.1 이미 있던 안전 기반

- 실제 사용자 채팅 API는 클라이언트가 보낸 과거 assistant 메시지를 신뢰하지 않고
  DB의 canonical 메시지를 다시 읽는다.
- 상대방에게 직접 보낸 `target=partner` 메시지는 아모라 provider 문맥에서 제외한다.
- 공유/개인 visibility는 서버와 RLS에서 다시 확인한다.
- 도구 실행은 pending action, 멱등 키, 원자 작업과 결과 검증 경계를 가진다.
- 확정 기억과 커플 중재는 `decision_nodes`, proposal version, 양측 확인 규칙을 가진다.

### 4.2 2026-08-01 로컬 구현 완료, 운영 적용 전

- 메인 채팅과 사이드 패널 입력 초안을 세 전달 레인으로 분리했다.
- 레인을 바꿔도 각 레인의 텍스트와 첨부가 독립적으로 유지된다.
- 늦게 끝난 `FileReader`가 사용자가 이동한 다른 레인에 첨부를 넣지 않는다.
- 상대방 레인에는 아모라 추천 문구를 노출하거나 전송하지 않는다.
- 추천 버튼 전송은 사용자가 쓰던 텍스트·첨부 초안을 소비하지 않는다.
- 전송 대상·visibility·첨부 payload를 현재 레인에서만 만든다.
- 역할을 확인할 수 없을 때 개인 상담 visibility를 임의로 만들지 않고 닫힌 상태로
  끝낸다.
- 사용자 메시지 DB 저장 실패 시 텍스트와 첨부를 원래 레인으로 복구한다.
- 저장 성공 여부를 확인할 수 없으면 동일 `client_request_id`로만 다시 시도한다.
- 이미지 첨부는 내용과 재시도 키에서 결정되는 canonical UUID object key를 사용하며
  `upsert: false`로 저장한다. 재시도 때 정확한 409 duplicate만 기존 객체로 인정한다.
- PDF·DOCX는 AI provider 요청에만 포함하고 `chat-image`나 메시지 `imagePaths`에는
  영구 저장하지 않는다. 상대방 직접 전송은 이미지 첨부만 허용한다.
- 운영 Storage 정책은 사용자 DELETE를 허용하지 않으므로 DB 저장 확정 실패 후 이미지
  객체를 클라이언트가 임의 삭제하지 않는다. 같은 재시도 키가 같은 객체를 재사용하고,
  계정 삭제 inventory가 canonical 경로를 회수한다. 장기 미연결 객체 정리는 별도
  service-role janitor와 보존 기간 계약을 둬야 한다.
- AI provider만 실패하고 사용자 메시지가 저장됐으면 초안을 되살려 중복 전송하게 하지
  않고 기존 provider-only 재시도 흐름을 유지한다.
- 아직 segment가 없는 상태에서 문맥까지 초기화한다고 오해시키지 않도록 `새 채팅`을
  `대화 화면 정리`로 바꾸고, 원문과 아모라의 기존 맥락이 유지됨을 UI에 명시한다.

### 4.3 아직 남은 구조적 불일치

현재 `새 채팅`의 화면 정리는 profile의 `shared_chat_cleared_at` 또는
`private_chat_cleared_at` 이후 메시지만 클라이언트에 보여주는 방식이다. 그러나 채팅
API의 **기본 비활성 경로**는 별도로 DB의 최근 canonical 메시지 최대 40개를 읽는다.
따라서 화면에서 이전 메시지가 사라져도 운영 플래그 전환 전에는 모델 원문 문맥이
실제로 새로 시작됐다고 보장할 수 없다.

2026-08-02 로컬 후속 migration은 기존 lane별 메시지·요약 backfill, 서버 소유
`segment_id` dual-write, AI 답변의 source-message segment 결속, 요약 범위 결속과
`NOT NULL` 전환까지 구현했다. 채팅 API에도 현재 active segment만 읽는 경로와
불일치 시 503으로 닫히는 검증이 추가됐다. 다만 hosted DB에는 적용하지 않았고
`AMORA_CONVERSATION_SEGMENT_READ_ENABLED=false`가 배포·로컬 QA 계약의 기본값이다.
사용자가 실제로 새 segment를 시작하고 이전 대화를 다시 보는 UI도 아직 열지 않았다.
최근 N개 제한은 계속 비용 상한일 뿐 대화 의미 경계로 주장하지 않는다.

이 불일치는 아래 세그먼트 구현 전까지 출시 리스크로 취급한다. `새 채팅`이라는 이름만
믿고 과거 원문이 모델에서 제외된다고 주장하지 않는다.

## 5. conversation segment 제품 계약

### 5.1 기본 수

- 커플마다 활성 shared segment 1개
- 사용자마다 활성 private segment 1개
- 과거 segment는 보존하되 비활성 상태
- 동시에 여러 주제방을 자동 생성하지 않음

### 5.2 새 대화의 의미

`새 대화 시작`은 다음을 한다.

1. 현재 레인의 활성 segment를 닫는다.
2. 새 활성 segment를 원자적으로 만든다.
3. 새 segment의 원문 모델 문맥은 빈 상태에서 시작한다.
4. 확인된 결정, 실제 도구 상태, 유효한 동의 기억은 필요한 범위에서 계속 사용할 수
   있다.
5. 이전 메시지는 삭제하지 않고 기록에서 다시 볼 수 있다.
6. 삭제는 별도의 명시적 기능과 삭제 영수증을 사용한다.

즉 `새 대화`, `내 화면에서 숨기기`, `원문 삭제`, `기억 삭제`는 서로 다른 동작이다.

### 5.3 공유 segment를 누가 바꿀 수 있는가

공유 segment 전환은 데이터 삭제나 공동 결정 변경이 아니므로 어느 한 파트너도 시작할
수 있다. 다만 상대방에게 조용히 적용하지 않는다.

- 공유 화면에 “OO님이 새 대화를 시작했어요” 시스템 경계를 남긴다.
- 이전 대화 보기 링크를 제공한다.
- 승인 대기안이 있으면 먼저 “이 제안은 새 대화에서도 유지할까요, 닫을까요?”를
  확인한다.
- 이미 한 사람이 승인한 공동 제안은 새 대화 전환만으로 자동 실행하지 않는다.
- 제안 내용·참여자·버전이 달라지면 기존 승인을 무효화한다.

개인 segment 전환은 현재 사용자에게만 영향을 주며 파트너에게 알리지 않는다.

### 5.4 자동 segment 전환

MVP에서는 AI가 주제를 추측해 자동으로 새 segment를 만들지 않는다. 길이 상한에
도달하면 다음 중 하나만 한다.

- 현재 대화를 계속하기 위해 더 오래된 원문을 안전하게 압축하되 사용자에게 경계를
  표시한다.
- 사용자가 새 대화를 시작하도록 제안한다.

자동 압축은 숨은 장기 기억을 만드는 경로가 아니다. segment를 넘겨야 할 사실은
`decision_nodes`나 사용자가 승인한 도구 상태여야 한다.

## 6. 제안 DB 계약

아래 계약은 `20260801100000_amora_conversation_segments.sql`과 PGlite 계약 테스트로
로컬 구현됐다. 단, **hosted DB에는 적용하지 않았고 런타임 기능도 켜지 않았다.**

### 6.1 `conversation_segments`

필수 의미:

| 필드 | 의미 |
|---|---|
| `id` | segment UUID |
| `couple_id` | 소속 커플 |
| `visibility` | `shared`, `bride_private`, `groom_private` |
| `owner_user_id` | private 소유자, shared는 null |
| `status` | `active`, `closed` |
| `started_by` | 시작한 사용자 |
| `start_reason` | `initial`, `user_started`, `migration`, `safe_compaction` |
| `started_at`, `closed_at` | 원문 문맥 경계 |
| `previous_segment_id` | 직전 segment 추적 |
| `created_at` | 감사 시각 |

제약:

- 커플당 활성 shared segment는 최대 1개다.
- 사용자·private visibility당 활성 segment는 최대 1개다.
- private segment의 owner와 visibility role이 일치해야 한다.
- authenticated 클라이언트가 임의 `couple_id`, owner, visibility를 쓰지 못한다.

### 6.2 기존 테이블의 additive 연결

- `chat_messages.segment_id` nullable FK 추가
- `chat_summaries.segment_id` nullable FK 추가
- `ai_interactions_log`에 segment correlation을 컬럼 또는 검증된 metadata로 추가
- 승인 대기안과 실행 영수증이 근거 segment와 source message를 역추적할 수 있게 연결
- `decision_nodes`는 segment에 종속시키지 않는다. segment를 넘어 유지되는 결정
  정본이기 때문이다. 다만 source message와 source segment는 감사 근거로 남긴다.

### 6.3 원자 RPC

로컬 `start_amora_conversation_segment` RPC는 다음을 한 트랜잭션에서 처리한다.

1. `auth.uid()`와 현재 커플 멤버십 재검증
2. 요청 visibility와 private owner 검증
3. advisory/row lock으로 같은 범위 전환 직렬화
4. 클라이언트가 본 현재 segment id와 DB active segment id 비교
5. 이전 active segment 종료
6. 새 active segment 생성
7. 새 segment id, 상태, 현재 활성 segment id와 정확한 시각 반환

재시도는 같은 operation key로 멱등이어야 한다. 결과가 불명확하면 새 segment를 하나 더
만들지 않고 operation receipt를 조회한다. 최초 응답 유실 뒤 파트너가 다음 segment를
시작한 경우에도 최초 영수증의 `segment_status=closed`와 별도의
`current_active_segment_id`를 반환해 과거 영수증을 현재 활성 상태로 오해하지 않는다.

공유 전환 시스템 경계 메시지 생성, 승인 대기안 유지·종료 선택, provider read 전환은
아직 런타임 후속 작업이다.

## 7. 모델 문맥 컴파일 계약

모델에 보내는 문맥은 다음 순서로 만든다.

1. 현재 요청의 인증 사용자·커플·visibility·segment를 서버에서 확인
2. 현재 segment의 아모라 대상 원문만 시간순으로 읽기
3. `target=partner` 메시지 제외
4. 현재 visibility에서 볼 수 있는 활성·확정 `decision_nodes` 읽기
5. 실제 예산·할 일·일정의 현재값 읽기
6. 현재 segment와 version에 유효한 승인 대기안만 읽기
7. 사용자가 동의한 범위의 기억만 읽기
8. 길이 예산을 넘으면 원문을 자르되 정본 상태를 제거하지 않기

절대 포함하지 않는 것:

- 파트너의 private 원문과 기억
- 상대방에게 직접 보낸 메시지
- 종료된 이전 segment의 원문
- 거절·취소·supersede된 후보를 현재 결정처럼 표현한 내용
- 사용자 동의 전 자동 추정 기억
- 모델이나 첨부파일이 지시한 권한 상승

### 새 segment에서도 이어지는 것

- 사용자가 확정한 예식일·예산·선호·제약
- 실제 저장된 할 일과 일정
- 아직 유효한 계약·지급·마감 근거
- 명시적으로 유지하기로 한 승인 대기안
- 동의된 범위의 활성 기억

### 새 segment에서 이어지지 않는 것

- 일회성 감정 표현
- 확인되지 않은 가족의 속마음
- 과거 모델의 추측
- 철회되거나 수정된 안
- private 원문을 공유 답변에 사용한 흔적
- 단순히 오래 대화했다는 이유로 생성된 숨은 프로필

## 8. 아모라 답변 계약

한 답변은 먼저 한 가지 역할을 선택한다.

1. 감정을 짧게 받아주기
2. 모호한 조건 하나 확인하기
3. 선택 기준과 차이 정리하기
4. 정확한 변경안을 보여주고 승인받기

가능하면 한 답변에 질문 하나, 다음 행동 하나만 둔다. 사용자가 “전부 알려줘”라고 한
경우에도 우선순위와 접을 수 있는 상세로 나누지, 긴 혼합 답변 한 덩어리로 만들지 않는다.

사실 상태는 문장과 UI에서 구분한다.

| 상태 | 허용 표현 |
|---|---|
| 확인된 사용자 사실 | “말씀하신 조건은…” |
| DB 확인 사실 | “현재 저장된 일정은…” |
| 출처가 있는 외부 사실 | 출처·기준일·적용 범위와 함께 |
| 달라질 수 있는 관행 | “선택하는 경우가 있지만 가족마다 달라요” |
| 아모라 제안 | “이렇게 정리해볼 수 있어요” |
| 미확인 | “아직 확인이 필요해요” |

금지:

- 모르는 가격·평균·예약 가능성을 만들기
- 선택 관습을 의무로 말하기
- 사용자의 감정·성격·파트너 의도를 진단하기
- 한 사람의 말을 공동 합의로 표현하기
- 도구 영수증 없이 저장·발송·완료를 선언하기
- 법률·의료·금융·세무의 최종 판단을 대신하기
- 실제 사람·결혼 경험자·상시 전문가인 척하기

## 9. 갈등과 커플 경계

갈등 중재는 일반 공유 채팅의 숨은 자동 모드가 아니다.

레거시 `/api/chat/check-couple-conflict` 자동 감지 경로는 production에서 코드로 강제
비활성화한다. 지원 경로는 사용자가 직접 요약을 작성해 요청하는 메인 채팅의
`requester_summary_only` 중재뿐이다.

1. 개인 상담에서 나온 불만은 자동 공유하지 않는다.
2. 아모라는 “상대에게 공유해도 되는 요약”을 사용자가 직접 확인·수정하게 한다.
3. 중재 카드는 감정 인정, 중립 번역, 확인된 사실, 작은 합의안 순서로 만든다.
4. 양쪽이 실제로 본 동일 proposal version에 각각 동의해야 공동 결정이 된다.
5. 한 사람의 승인만 있으면 그 사람의 의사만 기록한다.
6. 카드 문구·근거·참여자·공개 범위가 바뀌면 이전 승인은 무효다.
7. 폭력·위협·통제·즉시 위험 신호가 있으면 일반 중재를 중단하고 개인 안전을 우선한다.
8. private 내용을 상대 설득, 공유 알림, 공동 추천 근거로 재사용하지 않는다.

이 규칙은 segment 전환으로 우회할 수 없다. 중재 제안은 source message, source segment,
proposal version, 커플 구성 fingerprint를 모두 검증한다.

## 10. 다음 핵심 수직 흐름

기반 작업 다음에 가장 먼저 완성할 제품 흐름은 **공유 일정 제안 하나의 완결**이다.

예시 입력:

> 상견례 9월 7일로 잡았어.

완료 흐름:

1. 아모라는 사용자가 말한 날짜와 아직 모르는 장소·참석 인원·음식 제한을 분리한다.
2. 일정 1개와 준비 할 일의 정확한 변경 전후를 보여준다.
3. 선물·자리 배치·비용 부담은 미확인 선택으로 두고 몰래 추가하지 않는다.
4. 사용자가 실제로 본 proposal version을 승인한다.
5. 서버 RPC가 일정, 할 일, 실행 영수증, confirmed decision을 원자적으로 반영한다.
6. 서버가 저장 결과를 다시 읽는다.
7. UI는 성공한 항목, 미확인 항목, 실패한 항목을 나눠 보여준다.
8. 재접속한 사용자와 파트너가 같은 결과를 본다.
9. 새 conversation segment에서는 과거 원문 없이도 확정된 상견례 날짜를 안다.
10. 날짜 변경 시 기존 결정을 덮어쓰지 않고 supersede 이력과 영향 diff를 남긴다.

이 한 흐름이 안정적으로 끝나기 전 업체 예약·결제·외부 발송을 넓히지 않는다.

## 11. 단계별 구현 순서

### A. 전달 레인과 전송 복구 — 로컬 구현·대상 회귀 완료, 운영 미배포

- 세 레인 draft·attachment 격리
- 추천 버튼 대상 격리
- 동기/비동기 첨부 경계
- DB 실패 시 원래 레인 복구
- persistence unknown 멱등 재시도
- provider-only 재시도 분리
- 메인 채팅·사이드 패널 동일 계약
- 웹·모바일에서 현재 사용자·커플·역할·양쪽 슬롯을 확인한 exact partner UUID만
  직접 전송 대상으로 허용하고, 재시도도 최초 수신자 UUID에 결속
- 로컬 DB migration에 partner 수신자 trigger, sealed-roster backfill, sender·exact-recipient
  SELECT/INSERT RLS 계약 추가
- 화면 정리는 삭제가 아님을 명시하고 서버 원문·기존 모델 맥락 유지 사실을 표시
- 서명된 데모 세션은 원격 Auth 응답을 기다리지 않고 로컬 샘플 상태로 초기화
- 요청자 요약 기반 중재 v2만 확인 카드로 승격하고 출처 없는 기존·부분 카드는 승인 차단
- 변경 도구가 실행된 턴은 모델의 완료 문구를 전부 버리고 서버가 만든 성공·실패
  `displayMessage` 영수증만 표시·저장
- 일반 스트리밍 답변은 완결된 안전 문장만 미리 보여주고, 저장 완료 주장과
  `[suggestions]`·`[pending_action]`·`[mediation]` 내부 표식은 서버 최종 파싱 전 차단
- 모바일 계정·커플·역할 전환 즉시 이전 세션 generation을 무효화하고 늦게 온
  조회·Realtime·AI 결과를 새 사용자 화면에서 폐기

위 항목은 코드와 로컬 회귀의 상태다. hosted migration, 실제 PostgreSQL 독립 세션의
roster 잠금 경합, 운영 카나리, conversation segment 런타임 전환이 끝났다는 뜻은 아니다.

### B. segment additive schema — 로컬 기반 완료, 운영·런타임 미적용

- [x] migration과 DB 계약 테스트 작성
- [x] `conversation_segments`와 nullable FK 추가
- [x] exact expected segment, operation key 멱등 영수증, shared/private RLS 계약
- [x] 응답 유실 뒤 후속 전환이 일어난 replay에서 과거 영수증과 현재 active id 분리
- [ ] hosted migration 적용 전 백업·복원·사후 점검 계약 검증
- [x] 현재 shared/private 메시지·요약을 lane별 legacy segment로 backfill
- [x] 혼합 버전 웹·모바일 쓰기도 DB trigger가 현재 lane segment로 dual-write
- [x] AI 답변은 원래 사용자 메시지의 immutable source segment에 기록
- [x] 요약은 시작·끝 메시지가 같은 segment일 때만 기록
- [ ] 기존 최근-N 읽기와 segment 읽기의 shadow 결과 비교
- [x] provider read 플래그 `AMORA_CONVERSATION_SEGMENT_READ_ENABLED`를 기본 `false`로 추가
- [x] 플래그가 켜진 로컬 경로는 active segment·메시지·요약 범위 불일치 시 fail-closed

### C. 진짜 새 대화 — B 이후

- 서버에서 active segment를 해석
- 현재 segment 원문만 provider에 전달
- 공유 전환 시스템 경계와 이전 대화 보기
- stale pending action 차단
- 웹·모바일에서 동일한 의미와 카피 적용
- 한쪽 기기 offline/reconnect 회귀 검증

### D. 확정한 내용과 영수증 — C와 병행 가능

- 채팅에서 `확정한 내용`을 원문과 분리해 보여준다.
- 현재 결정, 미확인, superseded 이력을 구분한다.
- 예산·할 일·일정 projection에서 source decision과 receipt로 돌아갈 수 있게 한다.
- 사용자가 수정·철회·공개범위 변경을 할 수 있게 한다.

### E. 공유 일정 수직 흐름 — D 기반

- 제안 diff
- version 고정 승인
- 원자 실행
- read-after-write 영수증
- 파트너 동기화
- segment를 넘는 canonical recall
- supersede·복구

## 12. 안전한 출시 방식

1. 스키마는 nullable additive migration으로 시작한다.
2. 기존 읽기 경로는 유지하고 새 segment id만 dual-write한다.
3. backfill은 삭제·덮어쓰기 없이 legacy segment를 추가한다.
4. shadow read로 “기존 최근-N”과 “현재 segment”의 차이를 로그만 남긴다.
5. 개인정보 원문과 민감 내용을 로그에 복사하지 않는다.
6. 내부·데모·소수 베타 순서로
   `AMORA_CONVERSATION_SEGMENT_READ_ENABLED`를 연다.
7. 잘못된 segment, 누락 메시지, private/shared 혼합이 한 건이라도 있으면 read flag를
   즉시 끈다.
8. 롤백은 새 읽기만 끄며, 이미 쓴 segment id는 감사 정보로 보존한다.
9. 운영 migration·백업·복원·카나리 증거 없이는 완료라고 표시하지 않는다.

## 13. 필수 회귀 매트릭스

| 사례 | 기대 결과 |
|---|---|
| shared AI 초안 후 partner로 전환 | partner 입력은 비어 있고 AI 초안 유지 |
| partner 초안 후 private로 전환 | private 입력은 비어 있고 partner 초안 유지 |
| 파일 읽기 중 레인 전환 | 파일은 선택 당시 레인에만 추가 |
| partner 레인 | 아모라 추천 버튼 없음 |
| 추천 버튼 전송 | 사용자의 작성 중 초안·첨부 유지 |
| 역할 없음 + private 요청 | 전송·visibility 생성 모두 차단 |
| 이미지 업로드 실패 | DB/provider 호출 없이 원래 레인 초안·첨부와 재시도 키 유지 |
| DB insert 확정 실패 | 원래 레인 초안·첨부와 재시도 키 복구; canonical 객체는 같은 키로 재사용 |
| DB 결과 미확인 | 같은 request id와 object key로만 재시도 |
| PDF·DOCX AI 전송 | provider snapshot에만 포함, Storage와 `imagePaths`에는 미기록 |
| PDF·DOCX partner 전송 | 전송 전 차단, 초안·첨부 유지 |
| provider 실패 | 사용자 메시지는 한 번만 남고 provider만 재시도 |
| shared 새 segment | 이전 shared 원문은 provider에서 제외 |
| private 새 segment | 이전 private 원문 제외, partner에게 영향 없음 |
| 새 segment + 확정 결정 | 원문은 제외되지만 확정 결정은 기억 |
| partner 직접 메시지 | shared 화면에는 보이지만 provider 문맥에서는 제외 |
| 이전 segment 승인 카드 | 자동 실행되지 않고 재검증 또는 종료 |
| 양측 동시 새 segment | 활성 segment 하나, 중복 경계 없음 |
| 재접속·다른 기기 | 같은 active segment와 영수증 표시 |
| private 상담 | 상대 계정·알림·중재 입력에 노출되지 않음 |
| 연결되지 않았거나 수신자가 바뀐 partner 대상 | UI와 DB가 전송을 거부하고 옛 수신자 초안을 자동 재전송하지 않으며, 미전송·안전상 초안 폐기를 명시적으로 알림 |
| 계정·커플·역할 전환 중 늦은 조회·Realtime·AI 응답 | 이전 identity 결과를 모두 폐기하고 새 identity 화면에 한 글자도 남기지 않음 |
| 일반 채팅에 `[mediation]` 표식 혼입 | 카드·승인 대상으로 승격하지 않고 내부 표식을 화면에 노출하지 않음 |
| 요청자 요약 중재 | 상대의 감정·욕구로 귀속하지 않고 `requester_summary_only` 출처와 네 필드 완결성을 검증 |
| 중재 요청 안의 폭력·협박·강압 통제 | `W2` 안전 경계로 전환하고 중재 모델·중재 카드·장기 기억을 모두 사용하지 않음 |
| `W2` 민감 질문 | 현재 사용자 발화와 이번 요청의 명시적 첨부만 provider에 전달하고 저장된 커플 문맥은 조회·전달하지 않음 |
| `W3` 잡담·감정 표현(직전 맥락을 명시적으로 가리키지 않음) 또는 `W4` 범위 밖 질문 | 현재 사용자 발화만 provider에 전달하고 저장 문맥·첨부·도구·장기 기억을 사용하지 않음 |
| `W3`가 “그게·아까·앞에서 말한”처럼 직전 맥락을 명시적으로 가리킴 | 같은 사용자·같은 visibility의 바로 직전 사용자 발화와 그 발화 ID에 정확히 연결된 AI 답변 1쌍만 제한 길이로 전달; 중간 메시지·partner 대상·연결 불일치·이전 발화 `W2`~`W5`면 현재 발화만 사용 |
| `W4`로 판정되어 첨부가 제외된 요청 | 파일을 읽은 척하지 않고, 웨딩 관련성을 한 줄로 설명한 뒤 파일을 다시 첨부하는 방법을 안내 |
| provider가 저장된 커플 문맥을 사용한 뒤 커밋 직전 역할·커플·동의·개인화가 바뀜 | provider 초안을 화면에 한 글자도 내보내지 않고, 비용 영수증 정산·요청 실패·메시지 미저장을 하나의 DB 트랜잭션으로 확정 |
| `W0`·`W1` 답변 저장 뒤 즉시 기억 큐 응답 유실 또는 실패 | 같은 트랜잭션에서 만든 ID-only 복구 항목 또는 동일한 활성 memory job이 정확히 증명된 경우에만 완료 이벤트를 보내고 서버 작업자가 멱등 복구 |
| 기억 큐의 정확한 복구 증거가 없거나 확인 RPC가 실패 | 완료 이벤트를 보내지 않고 같은 요청 재시도로 저장 답변과 큐 상태를 먼저 정합화 |
| 기억 큐 실패 뒤 앱 종료·새로고침 | 서버 작업자가 content 없는 ID-only outbox의 정확한 `W0`·`W1` 적격 답변만 제한적으로 처리하고 동의·reset 경계를 재검증한 뒤 멱등 복구 |
| `W2`~`W5`·legacy·잘못된 metadata 답변의 누락 기억 | 자동 복구하거나 장기 기억으로 승격하지 않음 |

## 14. 측정

무관용 지표:

- 잘못된 레인 전송 0건
- private/shared 누출 0건
- 동일 사용자 메시지 중복 저장 0건
- persistence unknown에서 자동 중복 실행 0건
- 종료 segment의 stale 승인 실행 0건
- 영수증 없는 완료 주장 0건

제품 지표:

- 첫 세션 제안 승인 후 도구 반영 성공률
- 승인 후 재접속 read-back 성공률
- 이미 확정한 사실을 다시 묻는 비율
- 사용자가 답변을 정정한 비율과 정정 이유
- 새 대화 후 “왜 예전 얘기를 꺼내요” 신고율
- 대화가 예산·할 일·일정 갱신으로 끝난 비율
- 오류 뒤 사용자가 실제로 복구한 비율

대화 수와 평균 메시지 수는 성공 지표가 아니다.

## 15. 이번 범위의 비목표

- 자동 준비 건 분류 UI
- 여러 동시 대화방과 폴더
- AI가 알아서 대화방을 이동하는 기능
- 모든 과거 원문의 무기한 provider 전달
- 한쪽 private 내용을 활용한 공동 중재
- 예약·결제·외부 메시지 자동 실행
- 모델 정확도 100%, 불만 0건 같은 검증 불가능한 약속

## 16. Definition of Done

대화 기반은 다음이 모두 확인돼야 완료다.

- 웹 메인 채팅, 웹 사이드 패널, 모바일이 같은 세 레인 계약을 사용한다.
- 모든 메시지가 서버가 발급하거나 검증한 active segment에 속한다.
- 새 segment에서 이전 원문이 provider 경계를 넘지 않는다.
- 확인된 결정과 실제 도구 상태는 segment를 넘어 정확히 이어진다.
- partner 직접 메시지와 private 원문은 허용되지 않은 provider 문맥에 들어가지 않는다.
- 전송·승인·도구 실행이 각각 멱등이며 결과 미확인 상태가 구분된다.
- 모든 AI 호출은 `ai_interactions_log`, 모든 확정 커플 결정은 `decision_nodes`에
  추적된다.
- 단위·계약·컴포넌트·DB 통합·재접속·모바일 실기기 테스트가 통과한다.
- migration, 백업, 복원, 카나리, 기능 플래그 롤백 증거가 남아 있다.
- 실제 커플 테스트에서 함께/나만/상대방의 의미를 설명 없이 구분한다.

이 조건 전에는 “완벽한 기억”, “아무것도 놓치지 않음”, “모든 갈등 해결”을 제품
주장으로 사용하지 않는다.
