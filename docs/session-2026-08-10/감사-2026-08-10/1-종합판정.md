· **완전 독립 (제휴와 무관, 천장 90%+)**: ③ 비용 통제, ⑤ 관계 조율, ⑦ 정서 지지. 세 축 모두 필요한 재료가 이미 저장소 안에 있다 — PaymentLedger·hiddenCosts·guestGuarantee(③), conflict-detector·mediation 4필드 카드·비공개 탭·payer 필드(⑤), moments 문안·supportOrder(⑦). 막는 것은 플래그·배선·스키마 연결이지 외부 계약이 아니다.

· **사실상 독립 (천장 85%)**: ① 시점 관리. 체크리스트·알림 15종·모멘트 12종·크론이 전부 자체 데이터다. yedan/ham/pyebaek 신호 부재와 venue 마감 불일치(D-270 vs D-60)는 상수 수정이고, 배달은 env 플래그다.

· **부분 종속 (천장 70%)**: ② 의사결정. 결정 4종 중 '어느 업체'만 제휴에 종속되고 '총액 규모·포함 범위·항목 배분·보증인원·계약 여부·무엇을 생략할까'는 전부 독립이다. /price 공시(catalog.ts:1에 hall 포함, publicListData.ts:143로 조회 가능)를 채팅에 연결하면 사용자가 가져온 견적을 같은 조건 공시 분포와 대조해 위치를 표시할 수 있는데 이는 판정이 아니다. 업체 이름을 못 대도 '이 조건에서 800만원은 공시 분포의 어디쯤이고, 확인 안 된 항목이 이것들이다'까지 가면 결정은 난다.

· **부분 종속 (천장 65%)**: ④ 업체 조율. 검색·빈날짜·예약은 영구 봉인으로 두더라도, 보내는 문장(이미 있음)과 **받는 답 기록**(현재 부재)의 왕복만 닫으면 '세 곳 비교표'가 제품 안에서 완성된다. 대신 처리는 못 해도 대신 기억은 할 수 있다.

· **독립인데 가장 비싼 것 (천장 80%, 비용 L)**: ⑥ 정보 비대칭. 시세는 /price로 이미 자급하고, 진짜 공백은 예절·관습이다. 이것은 제휴가 아니라 **응답자 공급**의 문제이며 저장소에 대체 경로가 이미 반쯤 깔려 있다 — decisionThreadApi의 DECISION_APPLICABILITY 4값(applies/conditions_differ/need_more_info/taken_as_next_action)과 cohort digest의 family_etiquette 토픽(키워드에 상견례·혼주·예절·복장 실재). '같은 지역·같은 가족 구성 커플이 실제로 어떻게 했는지의 분포'는 판정이 아니다. 다만 이 축만 유일하게 데이터를 새로 모아야 하고(자동 배선으로 안 됨), 그래서 천장을 100%가 아니라 75% 근처로 눌러 앉힌다.

남는 25~30%의 정체: (a)업체를 실제로 골라 예약해 주는 것 — 영구 포기 시 회수 불가, (b)업체와 직접 통화해 문제를 대신 해결하는 것 — 원리상 불가, (c)예절·관습 데이터의 신뢰 가능한 자체 축적 — 시간이 드는 문제. 반대로 말하면 **업체 제휴는 이 제품의 병목이 아니다.** 지금 막고 있는 것은 스코프 분류기·기능 플래그·도구 게이트·스키마 연결 네 가지이고 전부 자체 코드다.

## 7-6. 순서 추천

의존관계상 **스코프 → 도구 게이트 → 데이터 채널 → 왕복 저장 → 배달 → 데이터 축적 → 제휴** 순이다. 앞을 건너뛰면 뒤가 무의미해지는 구간이 명확히 있다.

**0단계 (선행 필수, XS) — 거짓 약속 제거.** prompts.ts 중재 전략 A·B와 marketPrices.ts의 '검색 도구를 사용하고' 문장 3곳 삭제. 이건 다른 어떤 작업과도 무관하게 지금 해야 한다. 봉인된 도구를 전제로 모델이 답을 만드는 실경로이고, 제품 스스로 '가장 나쁜 실패'라 규정한 행동을 프롬프트가 유발하고 있다.

**1단계 — 스코프 분류기 (XS+S).** 어휘 확장 + 저장 문맥을 W0 신호로 인정. **반드시 첫 번째다.** 아래 모든 개선이 채팅에 닿으려면 발화가 W0로 들어와야 하는데, 현재는 도구를 아무리 잘 만들어도 W4에서 배열이 비워지고 문맥까지 삭제된다. 견적 도구를 고쳐도 '이 견적 800만원인데 괜찮아'가 도달하지 못하면 아무 일도 일어나지 않는다. 이 단계만으로 30발화 중 C 판정 다수가 즉시 움직인다.

**2단계 — 도구 게이트 (XS).** BUDGET_INTENT에 보증인원·하객·식대 추가, quote-check·budgetFinder에 hall 추가. 스코프가 열린 뒤에야 '어떤 도구를 붙일까'가 의미를 갖는다. 순서가 뒤바뀌면 검증이 불가능하다(게이트를 고쳐도 스코프에서 죽으니 효과 측정이 안 된다).

**3단계 — 데이터 채널 (M).** get_market_price를 /price 공시에 연결. 1·2단계가 끝나야 이 데이터가 실제 대화에 흘러들어가고, 이것이 열려야 ②와 ⑥이 동시에 올라간다. 판정 상승폭이 가장 큰 단일 작업이며, 여기까지가 '결론에 도달시키기'의 최소 구성이다. 주의: 이 단계 전에 quoteCheck의 median:0을 그대로 두고 UI만 손대면 0을 근거로 한 비교가 노출될 수 있으니, 데이터 연결과 소비처 수정을 같은 변경으로 묶어야 한다.

**4단계 — 왕복 저장 (XS~M).** not_applicable enum 추가, decision/cohort 범주 확장, 업체 답변 기록 필드, 계약 금액→예산 제안 연결, contractShield에 restaurant 추가. 3단계로 '결론이 나기' 시작한 뒤에야 '그 결론을 저장할 곳'이 필요해진다. 반대로 하면 저장할 결론이 없어 빈 그릇만 늘어난다.

**5단계 — 배달 (S + 운영 판단).** today-one에 모멘트 본문 싣기 → 그 다음 care 플래그 3종 개방. **순서가 중요하다.** 지금 플래그부터 켜면 today-one이 proactive를 자동으로 끄면서 내용 없는 '일정 열기' 카드만 나가 첫인상을 태운다. 본문을 실은 뒤에 켜야 한다. 또 배달은 1~4단계가 끝나 '먼저 말할 내용의 질'이 확보된 뒤여야 의미가 있다 — 빈 제품이 먼저 말을 걸면 이탈만 앞당긴다. 운영 env 실값이 리포지토리에 없어 현재 상태는 [미확인]이므로 켜기 전 실환경 확인 필요.

**6단계 — 예절·관습 데이터 축적 (L).** decisionThread applicability와 cohort family_etiquette 토픽을 예단·혼수까지 확장해 분포를 모으기 시작. 유일하게 시간이 드는 작업이라 마지막이지만, 응답자 공급이 쌓이는 데 걸리는 시간 때문에 **착수는 4단계와 병행**하는 것이 맞다. 결과가 나오는 시점이 늦을 뿐 시작이 늦을 이유는 없다.

**7단계 — 업체 제휴.** 위 전부와 독립이며, 하지 않아도 70~75%에 도달한다. 지금 이것을 병목으로 두면 자체 코드로 해결 가능한 40%p를 방치하게 된다.
