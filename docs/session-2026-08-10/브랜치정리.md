```ts
  return { success: result.success, status: result.success ? "rendered_in_client" : "unavailable" };
}
```

호출은 2곳(`route.ts:3495`, `:2878`)이고 **모든 도구 결과가 통과**한다.
그러나 **페이로드를 실제로 바꾸는 대상은 4개 도구 이름뿐**이고, 나머지는 `return result.toolOutput` 기본 경로다.
반환형이 `Record<string, unknown>`이라 **`toolOutput` 자리 하나만 만든다** — `success`를 별도로 실을 구조가 없다.

→ **"모델은 success를 못 본다"는 main에서도 유효하다.** 예외는 `search_nearby_places` 하나인데 그건 BETA_DISABLED다.

(3-2 라우트 72개 / 3-3 플래그 / 3-4 AI 경로 상세는 2차 감사 문서 `감사-2026-08-10/` 참조)

### 마이그레이션 `20260710110000_wedding_code_atomic_pairing.sql` (+428) — 질문의 핵심

**main에 없다.** main의 wedding_code 마이그레이션은 딱 둘이다.
```

```

**그런데 이건 "잃으면 안 되는 것"이 아니라 "넣으면 안 되는 것"이다.**

1. **대상 테이블이 이미 봉인됐다.** `20260714104000`이 `wedding_code_responses`에서 PUBLIC/anon/authenticated/**service_role** 권한을 회수한다. 주석에 운영 receipt SHA-256 `9F9C36B6…B26D88`, 13행 보존 기록. *"service_role bypasses RLS, so RLS alone is not a collection fence"*
2. **타임스탬프가 역전된다.** `20260710110000` < `20260714104000`. 신규 환경에서는 제약을 만들었다가 4일 뒤 권한을 몰수당하는 무의미한 왕복이고, 운영 ledger에는 **과거 시점 마이그레이션을 사후 삽입**하는 꼴이다.
3. 같은 파일 주석이 *"do not use this comment as approval for a full db push or ledger mark/repair"*로 ledger 손대는 것을 명시적으로 금지한다.
