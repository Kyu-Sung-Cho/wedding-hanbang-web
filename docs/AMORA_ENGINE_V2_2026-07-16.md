## 제품 약속

아모라는 결혼 준비를 대신 결정하는 챗봇이 아니다. 사용자가 말한 조건과 선택을
정확히 기억하고, 근거를 구분해 설명하며, 승인받은 일만 실행하고, 필요한 순간에
부담 없이 먼저 챙기며, 두 사람의 차이를 합의 가능한 문장으로 바꾸는 결혼 준비
동반자다.

친언니 같은 느낌은 과도한 친밀감이나 심리 추측이 아니라 다음 행동으로 만든다.

- 먼저 감정을 짧게 인정하고 바로 상황을 정리한다.
- 한 번에 질문 하나와 다음 행동 하나만 제안한다.
- 사용자가 이미 말한 내용을 다시 묻지 않는다.
- 모르는 사실, 가격, 계약 해석을 아는 척하지 않는다.
- 일정·예산 변경은 실행 결과를 확인한 뒤 완료라고 말한다.
- 갈등에서 한쪽 편을 들거나 한 사람의 클릭을 공동 합의로 표현하지 않는다.

## 다섯 축

### 1. 장기기억

- 기본값은 꺼짐이다.
- 개인 상담 기억은 해당 사용자 한 명의 명시적 동의로 켜진다.
- 공유 대화 기억은 연결된 두 사람 모두 동의해야 켜진다. 한 명이 동의를
  철회하면 즉시 꺼지고 대기 작업도 취소된다.
- 10개 이상의 새 메시지가 모였을 때 최대 40개를 한 번의 Luna 구조화 호출로
  정리한다. 매 대화마다 여러 모델을 호출하지 않는다.
- 사용자 발화에 직접 나타난 확정 선택·선호·제약·관계 맥락·준비 사실만,
  신뢰도 0.80 이상일 때 저장한다.
- 성격·심리·성별·숨은 동기, 불필요한 민감정보, 일시적 감정은 기억하지 않는다.
- 같은 주제는 안정적인 `memory_key`로 식별한다. 값이 바뀌면 이전 기억을
  삭제한 척 덮어쓰지 않고 폐기 이력과 새 값을 연결한다.
- 설정 화면에서 기억을 보고, 고치고, 한 항목 또는 해당 범위 전체를 지울 수
  있다. 전체 삭제는 기억·요약·프로필·동의·대기 작업을 한 DB 트랜잭션에서
  처리하며, 삭제 시점 이전 채팅에서 기억을 다시 만들지 않는다.
- 사용자가 직접 고친 기억은 자동 컴파일러가 덮어쓰지 않는다. 개별 삭제는
  `memory_key`를 숨김 tombstone으로 남겨 같은 과거 대화에서 다시 생기지 않게
  하고, 전체 삭제 때 tombstone까지 제거한다.
- 동의를 처음 켜거나 껐다 다시 켠 시각을 새 기준점으로 사용한다. 동의 전 또는
  동의가 꺼져 있던 기간의 대화는 나중에 소급해 기억하지 않는다.
- 명시적 동의 체계가 생기기 전에 자동 추론된 요약·프로필·미확인 기억은 최초
  활성화 트랜잭션에서 정리한다. 설정 화면에서 사용자가 직접 고친 기억만 명시적
  확인으로 보고 보존한다.
- 큐 등록, 기억 저장, 요약 저장, 동의 철회와 전체 삭제는 같은 범위의 DB 잠금을
  사용한다. API의 사전 조회만 믿지 않고 DB 함수가 동의와 메시지 소유권을 다시
  확인한다. 큐·기억 노드·요약 RPC도 근거 메시지가 최신 `memory_reset_at` 이후인지
  검사해, 서비스 코드가 회귀해도 동의 전 대화의 소급 저장을 거부한다.
- 겹쳐 실행된 크론의 작업 선점은 짧은 전역 트랜잭션 잠금으로 직렬화한다. 같은
  커플·범위에서 두 컴파일러가 동시에 실행되지 않으며, 재선점된 작업은 현재
  `attempt_count`를 임대 토큰처럼 일치시킨 워커만 완료할 수 있다.
- 주민등록번호·휴대전화·이메일·계좌·카드·비밀번호·정확한 주소·건강/성 관련
  민감정보는 프롬프트 금지와 별개로 서버 결정 규칙에서도 제거한다.
- 채팅 원문과 사용자가 일정·예산 기능에서 직접 저장한 정보는 기억 전체 삭제의
  대상이 아니다. 이 차이를 화면에 명시한다.

### 2. 근거와 신뢰

- 가격·통계·업체 정보는 출처, 기준 시점, 확인 수준을 분리한다.
- 확인 수준은 공식/검증 데이터, 참고 시세, 추정 또는 추가 확인 필요로 표현한다.
- 업체가 직접 확인하지 않은 가격을 확정 견적처럼 쓰지 않는다.
- 계약 문서는 위험 문구, 확인 질문, 쉬운 번역을 제공하되 법률 판단이나 승소
  가능성을 말하지 않는다.
- 모델 응답은 데이터베이스 권한이 아니다. 사용자·커플·공유/개인 범위는 서버와
  RLS가 다시 검증한다.

### 3. 결정과 실행

- 일정, 예산, 비교, 체크리스트 등 기존 도구 호출은 사용자 의도를 확인한 뒤
  실행한다.
- 실행 작업은 요청 키와 작업 키로 중복 실행을 막고, DB의 실제 결과를 받은
  뒤에만 성공이라고 말한다.
- 예약·취소·결제처럼 위험도가 높은 작업은 베타 안전 도구 목록에서 계속 막거나
  추가 확인을 요구한다.
- 모델 전환과 메모리 기능은 일정·예산 적용 경로를 대체하지 않는다. 실행은 기존
  도구 계층, 기억은 상담 맥락 계층으로 분리한다.
- 저장 도구가 없는 체험 상담에서는 모델 문구만 믿지 않는다. 날짜·예산·예약의
  확정형 발화를 서버가 감지해 실제 기능에는 저장되지 않았다는 고지를 보장한다.

### 4. 선제적 케어와 위험 감지

- 일정 기반 D-3 준비, D-1 짧은 대본, D+1 안부 흐름을 유지한다.
- 이메일 등 외부 발송은 명시적 수신 동의 시각이 있는 사용자에게만 보낸다.
  과거 기본값 `true`는 동의 증거로 인정하지 않는다.
- 케어 메시지는 한 번에 한 가지 도움만 제안하며 죄책감·불안·긴급성을 인위적으로
  만들지 않는다.
- 연결된 커플의 공유 케어는 두 사람 모두의 명시적 동의를 DB 함수가 발송 직전에
  다시 확인한다. 크론이 앞서 읽은 동의 상태가 오래됐더라도 발송하지 않는다.
- 외부 이메일 직전에도 현재 멤버 전원의 동의를 다시 읽는다. DB 메시지 생성 후
  동의가 달라졌으면 해당 실행의 이메일은 보내지 않는다.
- `memoryKeys`는 단순 메타데이터가 아니라 동의된 기억 컴파일러의 후보 문맥으로
  이어진다.
- 실제 사람이 대기하는 운영 조직이 없으므로 “24시간 내 전문가 검토” 같은 SLA를
  제품 약속으로 사용하지 않는다.

### 5. 관계와 중재

- 공감 → 서로의 표현을 중립적으로 번역 → 확인된 데이터 → 작은 합의안 순서로
  제시한다.
- 심리 진단이나 성별 고정관념을 사용하지 않는다.
- 한 사람이 누른 동의는 그 사람의 의사만 저장한다. 연결된 두 사람 모두 같은
  중재안에 동의한 뒤에만 공동 `decision_node`를 만든다.
- DB가 각 중재 카드에 proposal version과 당시 커플 구성 fingerprint를 발급한다.
  클라이언트는 사용자가 실제로 본 두 값을 확인 요청에 함께 보내며, DB의 최신
  값과 정확히 일치하지 않으면 저장하지 않는다.
- 선택안 문구뿐 아니라 카드의 공감·통역·확인 정보 중 하나라도 바뀌면 새
  proposal version으로 취급하고 이전의 대기 확인을 전부 무효화한다.
- 파트너가 연결되지 않은 계정에서는 중재안을 공동 결정으로 확인할 수 없다.
  파트너 연결 후 두 사람이 각각 최신 중재안을 확인해야 완료된다.
- 중재안은 AI 메시지에 붙는 확인 카드로 보여 주며, 사용자 메시지 분기에는
  렌더링하지 않는다. 수락 API는 현재 사용자 한 명의 의사만 기록한다.

## 런타임 흐름

```text
사용자 메시지
  → 인증·커플·공유/개인 범위 확인
  → 기존 요약/명시적 결정/동의된 기억만 상담 문맥에 포함
  → GPT-5.6 Luna 또는 Terra 응답
  → 승인된 도구만 실행하고 DB 결과 확인
  → AI 메시지 영구 저장
  → DB가 동의·범위·대상 메시지를 다시 확인한 뒤 원문 없는 내구성 작업을 큐에 기록

10분 크론
  → 만료 작업 회수 및 커플/범위별 직렬 처리
  → 메시지 ID+시각 커서로 정확히 10~40개 선택
  → Luna 1회 구조화 컴파일
  → 근거 메시지 UUID와 신뢰도 검증
  → 의미 키 기준 멱등 저장·이전 값 폐기
  → 요약 커서 저장 후 작업 완료
```

OpenAI 요청은 Responses API와 `store:false`를 사용한다. 아모라의 주 상담은 Luna,
복잡하거나 고위험인 경우에만 Terra를 사용한다. Anthropic 런타임은 사용하지 않는다.

## 비용·속도 원칙

- 장기기억은 매 턴 3~4회 호출 대신 10개 메시지 단위 Luna 1회로 묶는다.
- 큐에는 원문을 복사하지 않고 커플·범위·마지막 메시지 식별자만 저장한다.
- 최대 메시지 수, 문자 수, 기억 수, 출력 토큰을 모두 제한한다.
- 메모리 작업 실패는 상담 응답을 잃게 하지 않는다. 재시도는 최대 5회, 임대 만료
  회수와 지수형 지연을 사용한다. 완료 처리에는 획득 당시 시도 번호를 요구해
  만료된 이전 워커가 새 워커의 작업을 완료 처리하지 못하게 하고, 마지막 시도에서
  죽은 워커는 `LEASE_EXHAUSTED`로 종결한다.
- 메모리가 꺼져 있거나 설정 조회가 실패하면 처리하지 않는 fail-closed 방식이다.

“6개월 기억” 같은 고정 기간 마케팅 문구는 기술·보존 정책과 일치하지 않아
폐기한다. 기억은 사용자가 켠 범위와 삭제 선택에 따라 유지된다.

## 기능 플래그와 운영 조건

- `AMORA_OPENAI_ENABLED`: 주 상담 OpenAI 런타임. 기존 운영 게이트를 따른다.
- `AMORA_AUXILIARY_MEMORY_ENABLED`: 장기기억 큐와 크론. 변경 전 정확한 14-table
  baseline 백업과 변경 후 27-table 백업·즉시 검증, DB 마이그레이션,
  `CRON_SECRET`, 배포 후 비활성 카나리가 끝날 때까지 `false`다.
- 기억 플래그를 켜도 사용자별 동의 기본값은 `false`다.
- 웹과 네이티브 모바일 모두 기억 보기·수정·개별 삭제·전체 삭제·동의 제어를
  제공한다. 전역 플래그가 꺼진 동안 새 동의만 막고 기존 데이터 열람·삭제와
  동의 철회는 계속 가능해야 한다.
- 케어 외부 발송은 `care_notifications_enabled=true`와
  `care_notifications_consented_at`이 모두 있어야 한다.

## 냉정한 현재 한계

- 기억의 정확도는 구조와 검증으로 높일 수 있지만 “완벽한 사람 이해”를 보장할 수
  없다. 그래서 사용자 수정·삭제가 핵심 기능이다.
- 공식 업체 제휴·실시간 재고·확정 견적·커미션 공개 체계는 아직 별도 사업/데이터
  프로젝트다.
- 사람 전문가 검토 큐, 법률 자문, 의료·심리 상담은 제공하지 않는다.
- WeddingCode 질문의 과학적 타당화와 재출시는 이 변경의 범위가 아니다. 현재
  수집 API 차단과 비공개 경계를 유지한다.
- HBAM2는 암호화된 논리 스냅샷과 무결성 검증 수단이다. 공급자 물리 복구와 독립
  논리 복원 훈련을 대체하지 않는다.
