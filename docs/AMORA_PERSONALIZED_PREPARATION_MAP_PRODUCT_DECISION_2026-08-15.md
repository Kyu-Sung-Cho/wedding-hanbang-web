## 1. 최종 판단

`개인화된 AI 채팅`, `개인화 체크리스트`, `대화 저장`, `상세 가이드북`을 각각 잘 만드는 것만으로는 최선이 아니다.
이 조합은 유용하지만 사용자는 여전히 다음 질문에 답하기 어렵다.

- 우리는 지금 어디까지 했는가?
- 무엇을 이미 결정했고 무엇은 아직 모르는가?
- 예전에 아모라에게 무엇을 물었고 어떤 답이 실제 우리 상황에 해당하는가?
- 지금 한 가지만 한다면 무엇을 해야 하며 왜 그것이 먼저인가?
- 상황이 바뀌면 무엇을 다시 확인해야 하는가?

아모라의 최선 방향은 다음과 같다.

> **아모라는 두 사람의 결혼 준비 상태, 확인된 사실, 아직 남은 결정, 관련 대화와 근거, 다음 행동을 주제별로 이어 주는 개인화된 결혼 준비 지도다.**

소비자에게는 `나의 결혼 준비 지도`로 표현한다. 내부적으로는 기존 Wedding Operations Graph와 Decision Packet의 읽기 쉬운 projection이다.

## 2. 대안 비교

| 대안 | 해결하는 문제 | 해결하지 못하는 문제 | 판단 |
|---|---|---|---|
| 채팅 검색·북마크 강화 | 과거 답변을 다시 찾기 쉬워짐 | 남은 준비, 현재 상태, 다음 행동을 설명하지 못함 | 보조 기능 |
| 개인화된 살아 있는 가이드북 | 주제별 정보와 관련 대화를 한곳에서 봄 | 확정 결정과 실제 실행 결과가 분리되면 다시 정적 콘텐츠가 됨 | 필요한 구성요소 |
| 개인화 결혼 준비 지도 | 상태·결정·근거·대화·행동·결과가 한 주제로 이어짐 | 구현과 검증이 더 어렵고 정본 경계가 필요함 | **선택** |

공식 제품 설명상 The Knot과 Zola는 이미 일정 기반 개인화 체크리스트, 메모, 할 일 편집을 제공한다.
WedCheese도 AI, 체크리스트, 예산, 업체, 노트, 저장형 바인더를 한 제품으로 묶는다.
따라서 `AI + 체크리스트 + 저장`은 차별점이 아니라 기본 기대치다.

- The Knot: https://www.theknot.com/wedding-checklist
- Zola: https://www.zola.com/faq/115002135931-how-do-i-set-up-my-wedding-checklist-
- WedCheese: https://www.wedcheese.com/
- 확인일: 2026-08-15

아모라의 차이는 한국 결혼 준비의 애매한 결정 깊이, 명시적으로 확인된 개인화, 개인·커플 범위 분리,
한 번의 대화가 실제 다음 준비로 이어지는 연속성에서 만들어야 한다.

## 3. 고객에게 보이는 하나의 구조

새 탭을 추가하지 않는다. 모바일의 기존 4탭과 기존 실행 도구를 유지한다.

| 표면 | 고객의 질문 | 단일 역할 |
|---|---|---|
| 홈 | 지금 무엇을 해야 하지? | 지금 할 한 가지와 이유 |
| 준비 지도 | 전체적으로 어디까지 했지? | 모든 준비 주제의 상태와 남은 것 |
| 주제 화면 | 이 주제에서 무엇을 알고 결정해야 하지? | 상황·결정·가이드·대화·행동의 정본 보기 |
| 아모라 채팅 | 내 상황에서 어떻게 해야 하지? | 생각하고 묻고 정리하는 대화 |
| 일정·예산·체크 항목 | 실제로 어떻게 실행하지? | 승인된 결정의 실행과 결과 기록 |

`준비 지도`는 현재 체크리스트를 폐기하거나 별도 제품으로 복제하지 않는다.
기존 체크리스트는 실행 항목의 한 projection으로 유지하되, 전체 준비 주제의 경계를 체크리스트 카테고리와 동일시하지 않는다.
하객 운영, 계약·지급, 본식 당일, 결혼 후 정리처럼 여러 카테고리를 가로지르는 준비도 같은 지도에서 다룬다.

## 4. 주제 화면의 소비자 계약

모든 주제 화면은 아래 순서를 지킨다. 정보량을 한 번에 펼치지 않고, 요약을 먼저 보여 주고 세부는 사용자가 연다.

### 4.1 지금 상태

- `아직 시작 전`, `알아보는 중`, `결정 필요`, `진행 중`, `완료`, `해당 없음` 중 검증 가능한 상태만 표시한다.
- 완료율 하나로 사실, 결정, 실행을 섞지 않는다.
- 일정, 예산, 행동, 체크 항목의 실제 저장 기록에서 계산한다.
- 데이터가 없으면 `아직 모름`이라고 표시한다. 추정해서 채우지 않는다.

### 4.2 우리 상황

- 사용자가 직접 입력한 사실
- 저장된 일정·예산·체크 상태
- 사용자가 명시적으로 확정한 결정
- 현재 유효한 개인 기준과 커플 기준

각 항목에는 `내가 말함`, `저장된 기록`, `둘이 확인`, `출처 확인`, `아모라 제안`, `아직 모름` 중 근거를 표시한다.
AI가 추론한 성격, 경제력, 가족 관계, 역할 기대를 사실처럼 넣지 않는다.

### 4.3 아직 정할 것

- 이 주제에서 실제로 남은 질문만 보여 준다.
- 이미 답한 질문을 반복하지 않는다.
- 선택하지 않아도 되는 관습은 `선택 사항`이라고 표시한다.
- 가족·지역·종교·업체에 따라 달라지는 것은 하나의 정답으로 말하지 않는다.
- 질문은 정보 수집이 아니라 다음 결정을 위해 필요한 최소 개수만 묻는다.

### 4.4 아모라 가이드

- 질문과 답, 예외 상황, 실행 체크, 확인할 문장으로 나눈다.
- 공개된 원문·공식 출처·검수된 독립 작성 내용을 구분한다.
- 출처, 확인일, 적용 범위, 달라질 수 있는 조건을 함께 표시한다.
- 시중 유료 가이드의 문장, 목차 순서, 표, 예시, 수치 배열을 복제하지 않는다.
- 외부 가이드에서는 `애매한 질문을 누락하지 않는 구조`만 연구하고, 분류와 문장은 독립적으로 만든다.

### 4.5 내가 물어본 것

- 이 주제와 연결된 기존 대화를 다시 찾을 수 있게 한다.
- 원문은 기존 채팅에 남기고 주제 화면에는 참조만 둔다. 같은 내용을 별도 정본으로 복제하지 않는다.
- 비공개 대화는 기본적으로 나만 볼 수 있다.
- 공유 대화와 공동 결정은 원래부터 공유 범위였던 기록만 표시한다.
- AI 답변은 사용자가 `이 주제에 보관`을 명시적으로 선택하기 전에는 주제 기록으로 확정하지 않는다.
- 보관해도 AI 답변 자체가 `사실`이나 `둘의 결정`으로 승격되지는 않는다.

### 4.6 지금 할 한 가지

- 현재 상태와 남은 결정에서 가장 작은 다음 행동 하나만 제시한다.
- `왜 지금인지`, `끝났다고 볼 기준`, `어디에 반영되는지`를 함께 보여 준다.
- 사용자가 완료·막힘·변경·잘 모르겠음을 남기면 다음 제안에 반영한다.
- 사용자가 요청하지 않은 전송, 공유, 예약, 결제, 업체 문의를 만들지 않는다.

## 5. 개인화 계약

개인화는 많이 추측하는 것이 아니라, **확인된 차이를 정확히 반영하는 것**이다.

### 5.1 사용해도 되는 입력

1. 예식일, 지역, 예산, 일정, 예약, 체크 상태처럼 사용자가 직접 저장한 사실
2. 답변 길이·설명 방식처럼 사용자가 직접 고른 개인 설정
3. 사용자가 직접 저장한 개인 기준
4. 두 사람이 명시적으로 확인한 커플 기준과 공동 결정
5. 행동 결과: 완료, 막힘, 변경, 아직 모름
6. 현재 보고 있는 준비 주제와 유효한 최신 기록

### 5.2 사용하면 안 되는 입력

- 대화만 보고 추정한 성격 유형
- 추정 소득·계층·소비 성향
- 확인되지 않은 가족 관계와 관습
- 상대방의 비공개 대화나 개인 기준
- 오래되었거나 폐기된 결정
- AI가 생성했지만 사용자가 확인하지 않은 사실

### 5.3 한 답변의 개인화 설명

중요한 추천에는 다음 중 실제로 사용한 항목만 짧게 설명한다.

- `결혼식까지 남은 기간을 반영했어요`
- `저장한 예산 범위를 반영했어요`
- `내가 고른 답변 방식을 반영했어요`
- `둘이 확인한 기준을 반영했어요`
- `이전 행동에서 막혔다고 한 점을 반영했어요`

사용하지 않은 정보는 사용했다고 말하지 않는다. 내부 키나 민감한 원문은 노출하지 않는다.

## 6. 범위: 결혼 준비 전체를 다루는 하나의 공통 지도

상견례 전용 제품을 만들지 않는다. 상견례는 사용자가 든 예시이자 공통 엔진을 검증하는 테스트 케이스일 뿐이다.
제품 범위는 결혼 준비의 시작부터 결혼식과 결혼 직후 정리까지 전체다.
기존 체크리스트의 19개 카테고리와 132개 준비 항목은 현재 구현된 출발점이지 완전성의 증거가 아니다.
현재 예산 분류의 `reserve`는 예비비·사용처 미정 금액을 담는 분류이지 독립 체크리스트 주제가 아니다.
전체 여정 커버리지 감사를 통과하기 전에는 `결혼 준비의 모든 것을 담았다`고 주장하지 않는다.

### 6.1 현재 구현된 체크리스트 범위

| 준비 축 | 포함 분야 |
|---|---|
| 시작과 큰 결정 | 부모님 첫 만남, 결혼식장 |
| 촬영·스타일·본식 준비 | 웨딩 사진 촬영, 드레스·예식 정장, 헤어·메이크업, 결혼식 날 사진·영상, 결혼식 신발, 꽃 장식 |
| 반지·의상·가족 관련 | 결혼반지·기념 선물, 한복, 두 가족에게 드릴 선물, 전통 혼례 선물, 폐백 |
| 하객과 예식 운영 | 종이·모바일 초대장, 답례 선물, 결혼식 진행·축하 노래 |
| 결혼 뒤 생활 | 신혼여행, 가전·가구·생활용품, 신혼집 |
| 예산 보조 분류 | 예비비·사용처 미정 (`reserve`; 체크리스트 카테고리 아님) |

현재 19개 체크리스트 카테고리는 처음부터 준비 지도에서 잃지 않아야 한다. 다만 모든 분야를 똑같이 긴 가이드로 펼치지 않고,
현재 커플에게 해당하는 상태·남은 결정·다음 행동을 우선한다. 검수되지 않은 상세 콘텐츠를 빈칸을 채우기 위해 노출하지 않는다.

### 6.2 전체 여정 커버리지 감사

현재 카테고리를 아래 전체 여정 축과 대조한다. 빠진 준비는 기존 항목에 억지로 넣지 않고,
사용자에게 독립적인 상태·결정·행동이 필요한지 검토한 뒤 카테고리 또는 하위 주제로 추가한다.

| 여정 축 | 반드시 감사할 범위 |
|---|---|
| 시작 설계 | 예식일, 전체 예산, 원하는 예식 방식, 우선순위, 역할, 현재 완료 상태 |
| 두 사람과 가족 | 부모님 첫 만남, 가족별 기대, 관습 선택, 비용 분담, 갈등과 확인 범위 |
| 장소와 하객 | 예식장, 하객 명단, 참석 확인, 좌석·식사·주차·교통·숙박·접근성 |
| 촬영과 스타일 | 스튜디오, 드레스·정장, 헤어·메이크업, 반지, 한복, 신발, 사진·영상 |
| 본식 구성 | 초대장, 진행자, 축하 공연, 식순, 서약·문구, 꽃·장식, 답례, 당일 역할 |
| 업체와 돈 | 비교 기준, 견적, 포함·불포함, 계약, 변경·취소, 지급 일정, 잔금, 환불·분쟁 근거 |
| 생활 준비 | 신혼집, 입주, 가전·가구·생활용품, 공동 생활 기준과 예산 |
| 여행과 행정 | 신혼여행, 여권·비자·보험·입국 조건, 필요한 결혼 관련 행정 확인 |
| 직전 운영 | 최종 확인, 연락망, 물품, 이동, 시간표, 돌발 상황, 미지급·미수령 확인 |
| 결혼 뒤 정리 | 업체 결과물 수령, 비용 정산, 대여품 반납, 감사 연락, 남은 행정과 기록 보관 |

각 행은 다시 `상태`, `핵심 결정`, `선행 조건`, `일정`, `예산`, `근거`, `예외`, `완료 증거`,
`관련 대화`, `다음 행동` 열로 감사한다. 빈 칸은 콘텐츠로 덮지 않고 제품 공백으로 기록한다.

### 6.3 모든 분야가 공유하는 주제 계약

상견례, 예식장, 스드메, 신혼집은 서로 다른 화면과 저장 방식을 만들지 않는다. 하나의 주제 모델을 사용한다.

```ts
type PreparationTopicView = {
  topicKey: PreparationTopicKey;
  applicability: "unknown" | "applicable" | "not_applicable";
  status: "not_started" | "exploring" | "decision_needed" | "in_progress" | "completed";
  progress: { completed: number; total: number };
  facts: EvidenceBoundFact[];
  unknowns: PreparationQuestion[];
  nextAction: GroundedNextAction | null;
  guideModules: VerifiedGuideModule[];
  relatedMessageRefs: TopicMessageReference[];
  linkedScheduleIds: string[];
  linkedBudgetCategoryKeys: string[];
  linkedActionIds: string[];
  conflicts: PreparationRecordConflict[];
};
```

- `PreparationTopicKey`는 기존 19개 체크리스트 키에 갇히지 않는다. 전체 여정 감사에서 독립 상태·결정·완료 기준이 필요한 주제를 추가할 수 있는 별도 도메인 키다.
- `topicKey`만 달라지고 상태·근거·개인화·개인정보 규칙은 같다.
- 주제별 차이는 질문 체계, 필요한 근거, 일정·예산 연결 규칙으로만 표현한다.
- 공통 엔진이 감사 후 확정된 전체 주제를 계산하고, 주제별 adapter는 도메인 차이만 제공한다.
- 화면 컴포넌트, 대화 보관, 상태 표시, 오류 복구를 주제마다 복제하지 않는다.

### 6.4 분야별 깊이의 공통 질문 축

각 분야는 아래 질문 축에서 해당하는 것만 사용한다.

1. 우리에게 이 준비가 필요한가?
2. 무엇을 먼저 결정해야 하는가?
3. 누가 참여하고 누가 확인해야 하는가?
4. 날짜·마감·선행 조건은 무엇인가?
5. 예산·견적·계약·결제에서 무엇을 구분해야 하는가?
6. 후보를 어떤 기준으로 비교해야 하는가?
7. 실제 실행 전에 무엇을 다시 확인해야 하는가?
8. 변경·취소·지연·불참·분쟁 같은 예외는 무엇인가?
9. 완료되었다고 볼 수 있는 증거는 무엇인가?
10. 이후 다른 준비에 어떤 영향을 주는가?

예를 들어 같은 축이 분야에 따라 다르게 적용된다.

- 상견례: 참석자, 이동, 식사 제한, 비용, 대화 주제, 만남 뒤 합의
- 결혼식장: 날짜, 예상 하객, 포함·불포함 항목, 보증 인원, 변경·취소 조건
- 드레스: 스타일, 편안함, 피팅 일정, 포함 소품, 수선, 최종 수령
- 신혼여행: 여권·비자, 항공·숙소, 공식 입국 조건, 취소 조건, 보험
- 신혼집: 입주 시점, 예산, 계약 조건, 자금 출처, 공간과 생활 동선

### 6.5 상견례는 대표 검증 사례

상견례는 가족별 차이, 비용, 참석자, 식사, 대화, 변경 상황이 모두 존재하므로 공통 엔진의 깊이를 검증하기 좋다.
따라서 첫 개발 테스트 데이터로 사용하되, `meeting`을 하드코딩하거나 상견례 전용 화면을 만들지 않는다.

아래는 외부 가이드의 문장이나 목차를 옮긴 것이 아니라 상견례 adapter가 제공할 독립 질문 범위다.

1. 만남의 목적과 이번에 꼭 정할 것
2. 참석자와 가족 구조, 호칭에서 확인할 것
3. 날짜, 장소, 이동 거리, 접근성
4. 음식 제한, 건강, 좌석과 진행 편의
5. 비용, 결제, 선물, 부담 방식
6. 당일 다룰 주제와 이번에는 미룰 주제
7. 민감한 질문과 대화가 불편할 때의 중단 기준
8. 복장, 준비물, 연락 담당
9. 지각, 불참, 일정 변경, 취소 같은 예외
10. 만남 뒤 합의·미합의·다음 행동 정리

### 6.6 한 주제 화면의 예시

```text
상견례
결정 필요 · 9월 7일 · 23일 남음

지금 할 한 가지
참석 인원과 음식 제한을 양가에 확인하기

✓ 날짜: 9월 7일                         저장된 일정

✓ 우리 기준: 이동이 편한 장소 우선       둘이 확인
```

### 6.7 전체 분야의 정본 데이터와 projection

새로운 거대 상태 저장소를 만들지 않는다.

| 보여 줄 정보 | 정본 |
|---|---|
| 체크 진행 | 기존 wedding progress/checklist IDs |
| 일정과 날짜 | 기존 schedule event와 moment identity |
| 예산 | 기존 예산 카테고리와 사용자 정의 카테고리; 하나의 주제가 여러 예산 항목을 참조할 수 있음 |
| 실행 행동 | 기존 `amora_actions` |
| 확정 결정 | 기존 `decision_nodes`와 유효 revision |
| 개인·커플 기준 | 기존 personalization/criterion 저장소 |
| 대화 | 기존 `chat_messages`; 주제 연결은 message ID 참조만 저장 |
| 가이드 | 출처·확인일·적용 범위를 가진 별도 읽기 콘텐츠 |

모든 주제 화면은 이 정본들의 읽기 projection이다. 서로 충돌하면 숨기지 않고 `확인 필요`로 표시한다.

## 7. 명시적 금지선

- 다섯 번째 하단 탭을 만들지 않는다.
- 체크리스트와 별개인 두 번째 준비 시스템을 만들지 않는다.
- `파트너에게 보일 초안` 같은 새 공유 흐름을 제품 핵심으로 추가하지 않는다.
- 대화 전체를 자동 요약해 사실·결정으로 저장하지 않는다.
- AI 답변을 체크 완료나 공동 결정으로 자동 반영하지 않는다.
- 성격 검사나 점수로 개인화를 설명하지 않는다.
- 모든 분야를 지도에 포함하되 검수되지 않은 가이드 문장을 양을 채우기 위해 만들지 않는다.
- 업체 추천·예약·결제·중개로 범위를 넓히지 않는다.
- 유료 PDF의 표현, 구성 순서, 표, 사례, 금액을 재사용하지 않는다.

## 8. 구현 순서

### 8.1 0단계: 계약과 정보 구조

- 이 문서와 현재 authoritative product contract의 충돌 여부 확인
- 전체 여정 커버리지 매트릭스로 현재 19개 체크리스트 카테고리·132개 항목의 누락과 과도한 묶음을 감사
- 누락 후보를 사용자 문제, 상태, 결정, 실행, 완료 증거가 독립적인지 검토해 카테고리·하위 주제로 확정
- 감사 후 확정된 전체 주제가 공유하는 상태·근거·개인/공유 범위 필드 확정
- `PreparationTopicView` 공통 계약과 전체 topic adapter 목록 확정
- 현재 체크리스트에서 주제 화면으로 들어가는 경로 확정
- 새 쓰기 없이 read-only projection부터 구현

### 8.2 1단계: 전체 준비 지도와 공통 read-only 주제 화면

- 감사 후 확정된 전체 분야와 준비 항목을 준비 지도에 표시
- 모든 분야에서 같은 공통 화면으로 현재 상태, 우리 상황, 남은 질문, 지금 할 한 가지 표시
- 기존 일정·예산·체크·행동·결정을 topicKey 기준으로 읽기
- 불러오기 실패와 충돌을 `아직 모름`과 구분
- 작은 화면, 글자 확대, VoiceOver/TalkBack, 느린 네트워크 검증
- 상견례, 결혼식장, 드레스, 하객 운영, 계약 지급, 본식 당일, 신혼여행, 신혼집, 결혼 후 정리 대표 fixture로 공통 엔진을 먼저 검증한 뒤 전체 adapter 계약 테스트

### 8.3 2단계: 모든 분야의 검수된 독립 가이드

- 감사 후 확정된 전체 주제에 공통 질문 축을 적용하고 필요한 세부 질문을 독립 작성
- 사실, 공식 출처, 일반적이지만 가변적인 관행, 아모라 제안을 분리
- 출처·확인일·적용 범위·예외 표시
- 법률·계약·가격은 최신 공식/직접 근거 없으면 단정 금지
- 대표 주제부터 검수 파이프라인을 통과시키되 최종 상품 범위는 전체 결혼 여정으로 유지

### 8.4 3단계: 대화 다시 찾기

- 기존 메시지를 복제하지 않는 topic link
- `이 답변을 이 준비에 보관`이라는 공통 명시적 동작
- 비공개 원문은 owner-private 유지
- 원본 삭제·계정 전환·커플 변경 시 fail-closed

### 8.5 4단계: 결정과 실행 연결

- 남은 질문에서 아모라 대화로 이동할 때 topic context만 전달
- 대화 후 사용자가 확인한 사실·결정만 기존 정본에 저장
- 다음 행동 하나와 완료 기준 생성
- 결과가 다음 홈과 주제 화면에 반영되는지 검증

### 8.6 5단계: 실제 고객 검증과 전체 깊이 보강

준비 지도 구조는 처음부터 감사에서 확정한 전체 여정을 포함한다. 대표 주제 검증에서 발견한 문제를 공통 엔진에 반영하고,
동일한 기준으로 모든 분야의 질문·근거·예외·완료 기준을 채운다. 상견례 화면만 성공한 상태를 제품 완성으로 간주하지 않는다.

## 9. 상품성 검증 조건

출시 전 숫자를 성공처럼 주장하지 않는다. 다음 행동 테스트를 실제 예비부부에게 수행한다.

1. 처음 온 사용자가 별도 설명 없이 현재 상태와 다음 행동을 말할 수 있는가?
2. 과거에 물었던 특정 준비의 답을 해당 주제에서 다시 찾을 수 있는가?
3. `사실`, `아직 모름`, `아모라 제안`, `둘이 확정`을 구분하는가?
4. 자신에게 해당하지 않는 관습을 건너뛸 수 있는가?
5. 개인 대화가 상대에게 보이지 않는다는 범위를 이해하는가?
6. 일정이나 결정이 바뀐 뒤 오래된 추천이 사라지거나 확인 필요로 바뀌는가?
7. 한 행동을 완료·막힘·변경으로 기록한 뒤 다음 안내가 실제로 달라지는가?
8. 검색이나 외부 메모 없이 `무엇이 남았는지` 답할 수 있는가?

대표 주제에서 한 항목이라도 정상 경로로 실패하면 같은 결함을 가진 공통 엔진을 전체 분야에 배포하지 않는다.
전체 분야가 지도에 보이는 것과 각 분야의 상세 가이드가 검수 완료된 것은 별도 상태로 측정한다.

## 10. 기술·안전 완료 기준

- 공개 행동 테스트를 먼저 작성한다. 소스 정규식만으로 완료를 주장하지 않는다.
- owner, couple, privacy scope, source revision, current identity를 서버와 클라이언트에서 다시 검증한다.
- 개인 기록과 커플 기록을 한 응답이나 캐시에 섞지 않는다.
- 오래된 데이터, 일부 로딩 실패, 재시작, 계정 전환, 연결 해제, 중복 탭을 테스트한다.
- AI 응답 오류가 정본 데이터의 자동 변경으로 이어지지 않는다.
- 관련 mobile/web/shared typecheck, lint, focused/전체 테스트를 통과한다.
- hosted migration, backup/restore, 실기기, 실제 2계정·2기기 증거가 없으면 배포 완료라고 말하지 않는다.

## 11. 이번 결정이 의미하는 것

현재 아모라의 개인화 기반은 버리는 대상이 아니다. 홈의 한 가지 행동, 결과 피드백, 일정 모멘트,
체크리스트, 예산, 결정 기록, 개인 기준, 커플 기준, 비공개 채팅을 이미 갖고 있다.

부족한 것은 기능 수가 아니라 고객이 결혼 준비 전체와 각 준비 주제를 **하나의 이어지는 이야기로 볼 수 있는 표면**이다.
따라서 다음 제품 작업은 상견례 전용 기능이 아니라 전체 결혼 여정이 공유하는 준비 지도 엔진과 공통 주제 화면을 만든다.
상견례는 이 엔진을 가장 깊게 검증하는 첫 fixture이고, 그 결과는 결혼식장·스드메·예물·초대장·본식·신혼여행·신혼집을 포함한
모든 분야에 동일하게 적용한다.
