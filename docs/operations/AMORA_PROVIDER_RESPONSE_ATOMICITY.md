# Amora provider response commit boundary

> **Status: implemented and locally tested; production migrations and current
> candidate deployment NOT RUN.** This is a candidate contract, not evidence
> that production already uses migrations 1060/1100. See
> `CURRENT_WORKSPACE_HANDOFF_2026-07-17.md` for the live release status.

## Release invariant

For every durable terminal Amora response, these three writes are one database
transaction:

1. settle the exact provider receipt using its `amora_claim_token`;
2. insert or reuse the assistant `chat_messages` row using
   `(couple_id, metadata.client_request_id)`;
3. complete the matching `amora_chat_request_claims` generation using its
   current `attempt_count`.

Migration `20260716106000_amora_atomic_chat_response.sql` implements this in
the service-role-only `finalize_amora_chat_response(...)` RPC. It covers:

- main chat responses that finish in a tool round;
- main chat responses that finish after the maximum tool rounds;
- automatic conflict mediation generated by Terra.

A failed message insert, stale claim generation, ownership mismatch, or
visibility mismatch rolls receipt settlement back. Application code must not
fall back to `finalize_amora_provider_call_receipt(...)` after this RPC fails.
Likewise, a successful provider tool round is not allowed to execute its tools
until receipt settlement and its replay checkpoint are both confirmed. A
successful call accepts only `settled` or conservatively `unknown` as receipt
states; `released` is contradictory and fails closed. The request-claim
`attempt_count` is parsed as a required positive integer and is never inferred.

## Non-terminal tool-round recovery

Migration `20260716110000_amora_crash_recovery_atomicity.sql` closes the local
crash window after a paid non-terminal OpenAI response:

1. `finalize_amora_tool_round_receipt(...)` settles the receipt and appends the
   exact replay checkpoint in one transaction;
2. `get_amora_tool_round_journal(...)` loads only the active request-claim
   generation;
3. `claim_amora_tool_execution(..., pending_action_id,
   provider_call_index)` authorizes an automatic mutation only when its tool
   name, input digest, operation key, and call index match that journal;
4. `apply_amora_atomic_tool_execution(...)` commits a supported journey
   mutation and its durable tool result in one transaction.

The initial atomic domain dispatcher covers total-budget changes and schedule
event add/update/delete. Other mutation kinds fail closed as durable no-ops;
they never fall back to the historical domain-write-then-ledger split. Exact
server-confirmed actions use the same atomic claim/commit path and can safely
reacquire an uncommitted operation when the same chat request is reclaimed.

The journal is bounded to two rounds, one tool call per round, eight provider
output items, and 96 KiB per checkpoint. It expires after 24 hours and is
cleared when the chat request completes. It excludes input conversation and
streamed draft text, requires encrypted reasoning, forbids plaintext reasoning
summaries and unbound function calls, and stores only the output items required
for an exact Responses continuation.

## Retry and rolling-deploy behavior

- Retrying the atomic RPC with the same receipt claim token and chat-claim
  generation returns the already committed message without inserting another
  row.
- A conflict mediation that loses the ten-minute cooldown race settles its paid
  receipt and generation-fences the chat claim as `COOLDOWN_RACE_LOST`. The same
  RPC retry returns the same harmless outcome.
- A later HTTP retry looks up the exact `client_request_id` before any quota or
  provider work. `reconcile_amora_chat_response(...)` repairs a legacy
  message-first split, then the server replays the stored response.
- The migration does not replace or revoke the legacy receipt finalizer, so an
  older instance can finish in-flight work during a rolling deploy.

## Irreducible external boundary

There is no database transaction that can include the external provider call.
For a terminal response, if the process stops after OpenAI has produced the
response but before the first `finalize_amora_chat_response(...)` commit reaches
Postgres, the database still has no terminal response body to replay. For a
non-terminal tool response, the same pre-commit crash remains irreducible, but
once `finalize_amora_tool_round_receipt(...)` commits, the request resumes from
the journal without regenerating that paid call. Before either commit, the
receipt remains conservatively `reserved` (or later requires operator
classification as an unknown paid attempt), and an automatic provider retry is
forbidden because the Responses create operation has no relied-upon
idempotency guarantee.

This state is not reported as success. It requires manual reconciliation:

1. confirm there is no exact assistant message for the receipt request key;
2. inspect the receipt status and timestamps without changing them;
3. correlate provider-side request evidence when available;
4. keep the maximum reservation when billing cannot be disproved;
5. never regenerate automatically merely to repair accounting state.

A receipt already `settled` or `unknown` with no exact assistant message is a
legacy/inconsistent split and is also blocked from automatic regeneration.

## Privacy and authorization

- Both 1060 RPCs revoke execution from `PUBLIC`, `anon`, and `authenticated`;
  only `service_role` can execute them.
- The RPC validates receipt token, couple, user, visibility, request-key
  mapping, and claim generation before committing.
- Main-chat receipt and message request keys must match exactly. Conflict Terra
  permits only the bounded mapping `conflict:<sha256>` to
  `mediation:<same-sha256>` and shared visibility.
- Conversation text and message metadata are written to `chat_messages` only.
  They are not copied into `ai_interactions_log`; provider receipt metadata
  remains content-free correlation and usage data.
- The transient tool journal is readable only through its service-role RPC and
  only for the exact active couple/request/attempt generation. Reasoning must
  remain encrypted and plaintext summaries are rejected at both application
  and database boundaries.

## Release evidence

Before deploying application code that calls the new RPCs, migrations 1060 and
1100 must be applied in order and their service-role-only grants verified. The
PGlite migration suites cover atomic success and rollback, stale generations,
same-token retry, journal privacy/settlement coupling, reclaimed tool claims,
budget and schedule commits, conflict Terra, cooldown races, legacy
reconciliation, and role denial. Route and store tests cover clearing a partial
SSE draft, failing closed on an unconfirmed commit, replaying provider and tool
results, confirmed-action recovery, and reusing the original client request on
retry.
