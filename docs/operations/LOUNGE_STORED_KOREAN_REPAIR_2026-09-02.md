# 깨진 한글 — 무엇이 증명됐고, 무엇을 고쳤고, 무엇이 데이터에 남았나 (2026-09-02)

> **상태: 코드 수정은 PR #294 에 있음. 저장된 값의 일괄 복구는 하지 않았고, 하지
> 말아야 할 이유가 있음(아래 「남은 위험」).**
>
> 운영 DB 에 이 문서만 보고 쓰기를 하지 않는다. `AGENTS.md` 의 운영 DB 규칙대로
> 승인된 릴리스 매니페스트·컨트롤러 경로로만 적용한다.

## 1. 근본 원인

### 증명된 것 — 저장소 안에서

**저장소에 깨진 한글이 커밋돼 있었다.** 두 곳이고, 한 곳은 사용자에게 나가는
문구였다. 둘 다 commit `cedd7a1b`(2026-08-04)에 들어왔다.

| 파일 | 무엇 |
|---|---|
| `apps/web/src/app/api/admin/reports/[id]/route.ts:148` | 신고 검토 충돌 시 **관리자에게 409 로 나가는 오류 문구** |
| `apps/web/src/app/api/chat/messages/route.test.ts:548` | 테스트 픽스처 |

깨진 문자열의 코드포인트를 세면 성질이 드러난다.

```
"?좉퀬 ?곹깭媛 ?대? 蹂寃쎈릺?덇굅??媛숈? ?ㅺ? ?ㅻⅨ ?붿껌???ъ슜?섏뿀?듬땲??"
   19자  ASCII '?' (U+003F)
   17자  한글 음절
    6자  ASCII
    4자  한자 (CJK)
    4자  기타
    2자  한글 낱자모 (U+3131~U+318E)
```

대조군(멀쩡한 같은 길이의 한글):

```
"첨부를 정확히 확인해줘"
  hex: ecb2a8 ebb680 eba5bc 20 eca095 ed9995 ed9e88 20 ed9995 ec9db8 ed95b4 eca498
  전부 한글 음절 또는 ASCII. 물음표 0자, 한자 0자.
```

**두 가지가 이 조합을 특정한다.**

1. **한자와 한글 낱자모가 섞여 있다.** UTF-8 을 Latin-1 로 잘못 읽으면 결과는 전부
   U+00FF 이하다 — 한자가 나올 수 없다. 한자·낱자모가 나온다는 것은 UTF-8 바이트를
   **두 바이트 한국어 코드페이지(CP949/UHC)** 로 읽었다는 뜻이다.
2. **물음표가 U+FFFD 가 아니라 ASCII 0x3F 다.** 대체 문자를 넣은 것이 아니라
   **원문 바이트를 버리고** 물음표를 찍었다. WHATWG 디코더는 U+FFFD 를 넣는다;
   `?` 를 넣는 것은 Windows 변환기(`MultiByteToWideChar`)의 동작이다.

이 팀은 Windows 에서 개발하고, `scripts/` 의 PowerShell 여러 곳이 자식 프로세스
stdout 을 **`StandardOutputEncoding` 을 지정하지 않고** 읽는다(예:
`scripts/amora-db-current-baseline-common.ps1:83-90`). 그 경우 부모는 콘솔 코드
페이지로 디코딩한다. 한글이 그런 경로를 한 번 지나면 위와 정확히 같은 모양이 된다.

### 증명된 것 — 운영 데이터에서

저장소가 이미 기록해 두고 있었다(`apps/web/src/lib/ai/amoraToolPolicy.ts:383-385`,
commit `b4f1a4ea`, 2026-08-24 운영 실측):

> 체크리스트 항목 173개 중 90개, 19커플 중 15커플의 저장 라벨이 물음표로 깨져
> 있었다(`'??? ??? ??'`). … **다만 무엇이 그 라벨을 깨뜨렸는지는 아직 모른다.**

이쪽 모양은 한자도 낱자모도 없이 **물음표뿐**이다. 한 글자를 한 바이트로 떨어뜨리는
변환(유니코드 → 단일 바이트 코드페이지)이다. 역시 원문 바이트가 남아 있지 않다.

### 증명되지 않은 것 — 쓰기 경로

**어느 코드가 그 값을 DB 에 넣었는지는 찾지 못했다.** 두 번의 독립적인 전수 조사가
같은 결론에 닿았고, 2026-08-24 조사도 같은 자리에서 멈췄다. 조사 범위와 결과:

| 조사 | 결과 |
|---|---|
| 마이그레이션·SQL 593개 blob 전수(`to_ascii`·`convert_from`·`bytea` 왕복·`SQL_ASCII`·`SET client_encoding`) | **0건** |
| 물음표로 치환하는 마스킹·레닥션 루틴(현재 트리 + 전체 히스토리) | **0건.** 모든 레닥션은 낱말(`[url]`·`[redacted]`)로 치환하고, PII 필터는 **거부하거나 버린다** |
| Git pickaxe(`-S`) — `client_encoding`·`to_ascii`·`SQL_ASCII`·`toString('ascii')`·`pg_restore`·`Out-File`·`chcp`·`-Encoding ascii` | **0 커밋** |
| `scripts/**` 에서 `chat_messages`·`wedding_journeys.progress`·`amora_actions` 에 사용자 한글을 쓴 스크립트 | **0건**(합성 계정에 영문만 넣는 두 개뿐) |
| 스트리밍 디코드 절단·요청 본문 디코드 | 전부 `{stream:true}` + flush, 또는 `fatal:true` 로 **거부**(치환 아님) |
| 되돌릴 수 있는 종류(UTF-8 을 Latin-1 로 읽은 mojibake) 서명 전수 스캔 | **0건**(`docs/AMORA_2_0_GAP_SURVEY.json:389`, 2026-08-05) |

**결론:** 애플리케이션 요청 경로가 아니라 **운영·개발 도구 경로**에서 들어온 것으로
본다. 이것은 추론이며 저장된 바이트를 보기 전까지 `UNVERIFIED` 다.

## 2. 왜 이 고침인가

### 되돌릴 수 있는 종류와 없는 종류를 갈라서 다룬다

| 종류 | 되돌릴 수 있나 | 이 PR |
|---|---|---|
| **Latin-1/CP1252 오독** — 글자가 하나도 안 사라졌고 읽는 방법만 틀림 | **된다.** 표 없이 바이트 왕복으로 정확히 | 화면(읽는 자리)에서 되돌리고, 일괄 복구 스크립트가 **저장값도** 고친다 |
| **CP949 오독** — 한자·낱자모가 섞임 | **여기서는 못 한다** | 되돌린 척하지 않는다. 아래 실측 참조 |
| **잃어버림** — `?`(U+003F)·U+FFFD | **불가능.** 원문 바이트가 없음 | 제목 자리에서 물러나고, 스크립트는 **건드리지 않는다** |

### CP949 를 못 되돌리는 이유 (실측)

되돌리려면 UHC 역매핑 표가 필요한데 **런타임에서 만들 수 없다.**

```
Node TextDecoder("euc-kr") 2바이트 매핑: 8,412개
  그중 UHC 확장 영역(트레일 0x41~0xA0): 0개
한글 음절 왕복 가능: 2,350 / 11,172  (21.0%)
실제 깨진 문자열에서 역매핑 실패한 글자: 12개
```

React Native 에는 그 디코더가 아예 없다. 표를 벤더링하면 되지만, `?` 자리는 그래도
못 살아나므로 **부분 복구**가 최선이다. 저장된 값이 실제로 이 종류로 판명되면 그때
표를 들여오는 것을 별도로 판단한다.

### 대신 한 것

| 무엇 | 왜 |
|---|---|
| `packages/shared/src/utils/textEncodingRepair.ts` | Latin-1/CP1252 오독을 **바이트 왕복으로 검증된 경우에만** 되돌린다. 화면과 스크립트가 **같은 판정**(`diagnoseStoredText`)을 쓴다 |
| 읽는 자리 배선 — 일정·아모라 기록·**채팅 기록(웹·앱)**·저장한 이야기 | QA 가 지목한 두 화면이 일정과 채팅이다. 각 플랫폼에 길목이 하나씩이라 한 곳이면 세 경로(적재·폴링·실시간)가 같이 고쳐진다 |
| 되돌리기를 **검증보다 앞**에 둠 | 깨진 글자에는 C1 제어문자가 들어가서, 뒤에 두면 취소 사유·완료 기준·담당자 이름이 깨진 일정이 **통째로 탈락해 화면에서 사라진다** |
| 깨져 있던 소스 문자열 2곳을 다시 적음 | 하나는 지금 사용자에게 나가는 문구 |
| `scripts/tests/no-mangled-korean-in-source.test.mjs` | 같은 경로로 또 들어오는 것을 막는다 |
| **`scripts/repair-stored-korean.mjs`** | 저장된 값을 고치는 자리. 아래 3절 |
| 잔해는 **제목 자리**에서만 물러남 | 대화 말풍선은 다시 적을 수 없는 기록이라 안내문으로 덮지 않는다 |

### 왜 화면 되돌리기만으로 부족한가

화면 되돌리기는 읽을 때마다 고쳐 **보여줄** 뿐 저장된 값을 바꾸지 않는다. 그래서
화면을 거치지 않는 자리는 계속 깨진 값을 본다 — 2026-08-24 실측이 정확히 그것이다.
**화면은 멀쩡한데 아모라만** 항목 이름을 못 알아봤다. 저장값을 고치는 경로가 따로
있어야 한다.

## 3. 안전한 일괄 복구 경로

`node scripts/repair-stored-korean.mjs`

| 규칙 | 어떻게 |
|---|---|
| **기본은 읽기 전용** | `--apply` 없이는 한 줄도 안 쓴다 |
| **되돌릴 수 있는 행만 쓴다** | `diagnoseStoredText(...).kind === "repairable"` 이고 `repaired` 가 있을 때만. 잃어버린 행은 **건드리지 않는다** — 지우거나 지어낸 문장으로 덮는 것은 사용자의 기록을 없애는 일이다 |
| **목적지를 먼저 확인** | `verifySupabaseServiceDestinationFromEnv`. 쓰기면 `operator-write`, 운영이면 `SUPABASE_PRODUCTION_WRITE_CONFIRM=OPERATOR_WRITE:<ref>` 가 더 필요하다 |
| **사용자 원문 미출력** | 개수와 종류만. `--sample` 을 줘야 길이·앞바이트·해시 같은 **내용 비포함 지문**을 보여준다 |
| **쓰고 다시 읽어 확인** | 쓴 값이 의도와 다르면 그 자리에서 멈춘다 |
| **상한** | 페이지 200행, JSONB 깊이 8, 노드 2,000 |

```bash
node scripts/repair-stored-korean.mjs                          # 세기만
node scripts/repair-stored-korean.mjs --sample --couple=<id>    # 지목된 커플부터
node scripts/repair-stored-korean.mjs --apply --table=chat_messages
```

운영 대상 실행 전에는 백업·복구 검증·rollback artifact 를 먼저 갖춘다.
`supabase db push` 나 임의 SQL write 로 진행하지 않는다.

## 3. 어떻게 확인하나 — 읽기 전용 진단

읽기 전용이며 사용자 원문을 밖으로 내보내지 않는다. 결과를 문서·Git·채팅에
붙여넣지 않는다(개인정보 경계).

> **반드시 UTF-8 클라이언트에서 실행한다.** Windows 콘솔에서 실행하면 콘솔이
> 스스로 한글을 `?` 로 바꾼다 — 찾으려는 증상을 도구가 만들어 낸다. 이것이 지금
> 원인을 못 찾은 이유 중 하나일 수 있다.

```sql
-- 어느 커플이 얼마나 깨졌나. 원문은 세지 않고 개수만 본다.
SELECT
  count(*) FILTER (WHERE content LIKE '%??%')                   AS question_marks,
  count(*) FILTER (WHERE content LIKE '%' || U&'\FFFD' || '%')  AS replacement_chars,
  count(*)                                                       AS total
FROM public.chat_messages
WHERE couple_id = '<couple>';
```

```sql
-- 한 행의 바이트. 종류를 가른다.
SELECT encode(convert_to(content, 'UTF8'), 'hex') AS utf8_hex,
       length(content)       AS char_len,
       octet_length(content) AS byte_len
FROM public.chat_messages
WHERE couple_id = '<couple>' AND content LIKE '%??%'
LIMIT 3;
```

| hex 모양 | 뜻 | 조치 |
|---|---|---|
| `3f` 반복 | ASCII 물음표가 **저장돼 있다** | 되돌릴 수 없다. 이 PR 의 처리(제목 물러남 + 사용자 재입력)가 최선 |
| `efbfbd` | U+FFFD 가 저장돼 있다 | 되돌릴 수 없다. 위와 같다 |
| 한자·낱자모의 정상 UTF-8 | CP949 로 잘못 읽힌 것이 저장됐다 | **물음표가 없는 행만** CP949 역매핑으로 되돌릴 수 있다. 그때 복원기를 짠다 |
| 정상 한글 UTF-8 인데 화면만 깨짐 | 저장은 멀쩡하다 | 표시·글꼴 문제. 이 문서 밖 |

`wedding_journeys.progress` 와 `amora_actions` 도 같은 방식으로 본다.

## 4. 남은 위험

**옛 행에 마이그레이션이 필요한가 — 지금 답은 「아니오, 아직」이다.**

- 관찰된 종류는 **되돌릴 수 없다.** 일괄 쓰기로 할 수 있는 일은 값을 지우거나 우리가
  지어낸 문장으로 덮는 것뿐이고, 둘 다 사용자의 기록을 없앤다. **하지 않는다.**
- 3절 질의가 되돌릴 수 있는 종류를 가리키면 그때 결정이 바뀐다. 그 경우에도 백업·
  복구 검증·rollback artifact·승인된 릴리스 컨트롤러 경로를 먼저 갖춘다.
  `supabase db push` 나 임의 SQL write 로 진행하지 않는다.

**나머지 위험**

| 위험 | 상태 |
|---|---|
| 쓰기 경로를 못 찾았으므로 **지금도 새 행이 깨질 수 있다** | 저장소 안에서는 배제했다. 운영·개발 도구 경로는 배제하지 못했다. 3절 질의의 `created_at` 분포를 보면 최근 유입 여부가 갈린다 |
| PowerShell 9곳이 자식 stdout 을 콘솔 코드페이지로 읽는다 | 이 PR 범위 밖. 쓰기 경로는 아니지만 **운영자가 읽는 한글을 못 믿게** 만들고, 그 경로로 뜬 백업을 나중에 복원하면 깨짐이 진짜로 기록된다. 별도 건으로 다뤄야 한다 |
| 대화 말풍선의 깨진 글은 그대로 남는다 | 의도한 것이다. 사용자가 다시 적을 수 없는 기록이라 안내문으로 덮지 않는다 |
| 「한 계정만」이라는 QA 관찰과 「15/19 커플」이라는 2026-08-24 실측이 어긋난다 | 3절 질의로만 갈린다. 범위가 넓으면 이 PR 의 화면 처리가 더 많은 사용자에게 닿는다는 뜻이지, 처리 방식이 달라지지는 않는다 |
