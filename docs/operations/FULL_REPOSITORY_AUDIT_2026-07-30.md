MVP의 실행 경로와 신뢰 위험이 큰 코드에 집중했다. 자동 테스트도 실제 소비자 효용,
법률 적합성, 운영 DB 상태를 증명하지 않는다.

## 2. 현재 제품 판정

현재 제품 계약은 다음 한 문장이다.

**웨딩한방은 아모라에게 결혼 준비를 말하면, 예산·체크리스트·일정이 함께 정리되는
서비스입니다.**

주 내비게이션은 `아모라 | 할 일·일정 | 예산 | 커뮤니티`다. 업체 추천·예약·축의금·
공시가격 독립 제품화·WeddingCode·견적 체크 독립 제품화·모바일 출시는 장기 코드가
남아 있더라도 현재 웹 MVP의 전면 범위가 아니다.

감사 결론은 **처음 상태보다 훨씬 일관되고 안전해졌지만 완벽하지도, 출시 승인 상태도
아니다**다. 특히 아모라가 제안한 변경을 사용자가 확인하고 실제 예산·할 일·일정에
반영하며 실패 시 복구하는 핵심 흐름은 운영 환경과 실제 사용자로 아직 검증되지 않았다.

## 3. 이번 감사에서 수정한 핵심 문제

### 제품·소비자 신뢰

- 공개 화면과 메타데이터를 아모라 중심 MVP 계약에 맞추고, 예약·업체·축의금·모바일을
  현재 제공 중인 핵심 기능처럼 소개하던 표현을 제거했다.
- 존재하지 않는 고객지원 URL을 실제 `mailto:` 경로로 바꿨다.
- 오류 상태와 데이터가 없는 상태를 분리하고, “곧 제공”, “알려드리겠다”, “추천이
  좋아진다”처럼 구현·운영 근거가 없는 약속을 제거했다.
- 기본 예산 2,000만원, 실제 거래 분포처럼 보이는 가공 수치, 사용자 성향 위험점수 등
  근거 없는 계산과 주장을 제거했다.
- 현재 MVP에서 제공하지 않는 업체·예약·주변 장소 도구가 모델에 노출되지 않도록
  provider 도구 경계를 좁혔다.

### 아모라와 프롬프트

- 설정 UI의 `원하는 결과 우선`, 하객 수, 준비 우선순위가 프롬프트에서 다른 뜻이나
  내부 키로 바뀌던 문제를 고쳤다.
- 해당 값을 “성향 프로필”이 아닌 `사용자가 설정한 준비 참고값`으로 전달한다.
- 프롬프트 길이 제한이 걸려도 위 참고값이 사라지지 않도록 composer와 회귀 테스트를
  맞췄다.
- 모델 응답과 도구 실행을 분리하고, 사용자의 명시적 승인 없이 예산·일정·할 일을
  변경하지 않는 계약을 유지했다.

### 개인정보·보안

- `/api/auth/me`의 `select("*")`를 제거해 새 DB 컬럼이 자동으로 인증 응답에 노출되지
  않게 했다. 전화번호·push token·초대 코드는 일반 인증 bootstrap 응답에서 제외했다.
- WeddingCode는 분석·세션 수집에서 제외하고 결과를 서버에 저장하지 않으며, 공유
  데이터는 URL query가 아닌 fragment에 둔다.
- 견적 체크는 명시적 동의가 없는 한 저장하지 않고 공개 링크 생성을 중단했다.
- 공개 AI 페르소나와 자동 게시 흔적을 중단·격리하는 migration을 추가했다.
- 채팅 평가 localStorage를 schema 검증, ID 길이 제한, prototype key 차단, 최근
  500개 상한으로 보호했다.
- 출시되지 않은 돌봄 알림을 새 사용자가 켤 수 없게 하고, 과거 동의 사용자에게만
  철회 경로를 남겼다.
- 계정 삭제 안내를 실제 구현 범위인 커뮤니티 새 파일 업로드 차단으로 한정하고,
  별도 보관 경계가 아직 확인되지 않은 법정 보관을 이미 구현한 것처럼 쓰지 않게 했다.

### WeddingCode·견적 체크

- WeddingCode를 검증된 심리검사·궁합·성공 예측으로 표현하지 않고, 유형·동물·4글자
  코드·점수·상대 평가를 제거했다.
- 16개 질문과 선택지를 중학생도 사전 지식 없이 읽을 수 있는 구체적인 결혼 준비
  상황으로 다시 썼다.
- 결과는 맞고 틀림이 아니라 카테고리별 차이, 주의할 갈등, 먼저 할 대화와 행동을
  제공하도록 제한했다.
- 견적 체크는 `포함`, `이용하지 않음`, `확인 필요`의 세 상태로 정리하고, 가격
  적정성이나 업체 품질을 임의 판정하지 않는다.
- 정적 HTML만 맞고 버튼 상태 전이가 깨지는 회귀를 놓치지 않도록 WeddingCode의
  `시작 → 답 선택 → 다음 문항`과 견적 체크의 세 상태 전환 테스트를 추가했다.

### 모바일·커뮤니티·문서

- 모바일의 죽은 cohort 탭과 오해를 부르는 자동 배정·미래 제공 문구를 제거했다.
- 예약 기록이 향후 추천을 개선한다는 검증되지 않은 주장을 삭제했다.
- 커뮤니티의 빈 상태와 실패 상태를 분리하고 허위 미래 약속을 제거했다.
- 일정 요약이 예산 전용 `reserve` 카테고리를 할 일로 잘못 세던 계산을 고쳐,
  canonical checklist 19개만 집계하게 했다.
- 모바일 랜딩 첫 화면의 여백을 조정해 핵심 설명과 예시를 유지하면서 다음 섹션의
  시작이 첫 viewport 안에 보이게 했다.
- `CLAUDE.md`를 현재 규칙만 남긴 짧은 기준서로 교체했다.
- `docs/README.md`에 문서 권한과 완료 증거 규칙을 만들고, 오래된 감사·데모·백로그·
  세션 문서에 `HISTORICAL` 또는 `SUPERSEDED` 경고를 추가했다.
- 후속 migration의 실제 canonical SHA-256과 release manifest의 pin이 어긋난
  상태를 찾아 현재 파일 해시로 다시 고정했다. manifest의 출시 판정은 계속
  `deployment_blocked`다.

## 4. 자동으로 고정한 회귀 계약

- 현재 한 줄 제품 정의와 주 내비게이션
- 비전면 기능이 랜딩·메타데이터·아모라 도구 목록에 다시 나타나지 않는 경계
- WeddingCode의 비진단·비유형화·비저장 계약과 문항 exact version
- 견적 체크의 세 상태, 비저장 기본값, 공개 route 종료
- `/api/auth/me`의 명시적 컬럼 선택과 private no-store 응답
- 아모라 설정값이 사용자 문구 그대로 프롬프트에 전달되는 계약
- 출시되지 않은 돌봄 알림의 신규 opt-in 금지
- 과거 문서가 현재 기준서로 위장하지 못하는 문서 권한 계약

1. PID 8680의 개발 서버 작업이 끝난 뒤 현재 source state를 고정하고 production
   build를 실행한다.
2. 로그인된 테스트 계정으로 아모라의 `제안 → 확인 → 승인 → 반영 → 실패 복구`,

3. `git diff`를 목적별로 검토해 다른 작업자의 변경과 이번 감사 패치를 구분한다.
4. 의도한 파일만 commit하고 GitHub checks를 통과시킨다.
5. hosted clone에서 승인된 release manifest와 migration을 검증한다.
6. 백업·복구 준비 후 controller 경로로 DB를 적용하고 read-only 사후 검사를 한다.
7. 같은 commit을 production에 배포하고 운영 URL smoke를 남긴다.
8. 그 뒤에만 `deployment_blocked` 해제 여부를 별도 승인한다.

않는다.
