# 탈퇴 문의의 본인 확인과 단건 처리 기록

자동 접수·cron을 켜지 않고 고객지원 담당자가 한 건씩 처리하는 경로를 추가했다. 사용자 본인이 운영 담당이며 기존 문의 주소는 `contact@hanbang.ai`다. 시험 메일 발송 보류는 그대로다.

## 고객 화면

설정의 탈퇴 지원 영역에서 **탈퇴 문의용 확인 코드 만들기**를 누르면 현재 로그인한 계정의 본인 확인 코드를 발급한다. 발급은 접수나 삭제 승인이 아니다. 코드는 24시간 뒤 만료되고, 계정 전환·만료 시 표시와 복사를 중단한다. 고객은 실제 탈퇴 요청과 함께 코드를 문의 수신함으로 보낸다. 비밀번호나 로그인 토큰을 요구하지 않는다. 로그인하지 못하는 고객의 대체 본인 확인은 자동 판정하지 않고 담당자가 확인한다.

서버는 `auth.getUser()`와 요청 출처, 실제 본문 길이, 허용 필드, 익명 계정 거절, 계정별 발급 한도를 확인한다. 코드는 목적·프로젝트·본인·발급/만료 시각을 서명한다. 서명 원문은 로그에 남기지 않고 장애 원인도 고정 오류 코드로만 보고한다.

## 운영 명령과 사건 기록

`node scripts/account-deletion-support.mjs --help`로 정확한 인수를 볼 수 있다. 작업은 깨끗한 검토 commit에서만 실행한다. 인증값은 기존 목적지 검증에 필요한 환경변수로 전달하며 인수·Git·일반 로그에 저장하지 않는다.

1. **prepare:** 실제 받은 문의를 읽고 탈퇴 요청임을 확인한 담당자가 새 case UUID, 코드, 문의 원문, 담당자 식별자, 명시 확인값을 전달한다. 요청 내용은 private stdin JSON이다. 단순 `verified:true`나 이메일 주소로 삭제 대상을 지정할 수 없다. 원문의 SHA와 서명된 본인 ID·코드 참조·담당자·검토 시각을 같은 사건에 보존한다. 코드 발급만 했거나 문의 원문이 없으면 거절한다.
2. **enqueue:** 검토 사건의 hash를 명시 확인하고 `requestAccountDeletion(..., {processImmediately:false})`를 한 번 호출한다. 파괴 동작을 실행하지 않는다. 호출 전에 `enqueue-unverified`를 저장하고 반환 후 같은 본인의 활성 job 하나를 조회·검증해 job ID를 먼저 저장한다. 응답이 유실되면 **inspect**가 같은 본인의 job을 조회한다. 없는 job을 추측하거나 다른 계정을 사용하지 않는다.
3. **process:** 보호된 사건에 이미 결합된 job만 기존 worker에 전달한다. enqueue와 process는 실행 직전에 운영 health의 commit과 읽기 전용 `/api/ops/account-deletion-state`가 반환한 전체 commit·현재 시각·두 플래그를 재검사한다. 이 조회에는 메모리의 `CRON_SECRET`을 사용하며 DB·삭제 worker·메일에 접근하지 않는다. 응답은 캐시 금지여야 하고, 실제 서버 관측이 30초 이상 지났거나 미래 시각이거나 두 플래그 중 하나라도 false가 아니면 실행하지 않는다. 수동 관측 파일로 이를 대체할 수 없고, 작업을 실행할 수 있는 기존 cron GET/HEAD는 호출하지 않는다. 원격 호출 전에 `process-unverified`를 보존한다. 한 번 처리 후 종료하며 반복 실행은 하지 않는다.
4. **inspect:** 같은 job의 상태를 읽고 현재 claim·보류를 확인한다. 응답 유실 또는 Auth 삭제 후 finalizer 실패가 있어도 기존 job을 보존한다. claim 중이거나 `manual_review`이면 강제 실행·일반 Auth 삭제로 우회하지 않는다. 불명확한 처리 결과를 inspect 없이 재실행하지 않는다.

사건은 현재 Windows 사용자의 `%LOCALAPPDATA%/WeddingHanbang/DeletionSupport/<case UUID>`에 DPAPI로 암호화한다. 디렉터리/파일 ACL과 reparse 경로를 검사하고, 사건별 배타 lock·변경 불가 순차 기록·이전 암호문 SHA 연결을 사용한다. 암호화 왕복, 전체 쓰기와 fsync, 저장 후 바이트 대조가 끝나야 다음 원격 단계가 진행된다. 도중 종료된 파일이나 lock은 자동 정리하지 않는다. 담당자는 프로세스가 종료됐는지와 해당 사건 기록을 먼저 확인해야 한다. 이 암호화 기록은 다른 PC/Windows 사용자에게 복사하는 것만으로 열리지 않는다.

## 완료의 정확한 의미

worker의 문자열 응답만으로 완료라 하지 않는다. 같은 job의 `completed` 및 Storage/Auth/완료 시각, 익명화된 job 소유자, Auth·profile 부재를 읽어 확인한다. 그래도 최종 사건 상태는 **scope_review_required**이며 `generalCustomerDataRemovalVerified`는 false다.

이는 기존 worker의 처리 범위 밖인 개인·공유 대화, AI 로그·파생 기억, 남은 파트너의 자료, 백업/복원 시 삭제 재반영까지 확인했다는 뜻이 아니다. 그 자료의 실제 처리/보존 범위를 담당자가 확인하기 전에는 고객에게 전체 자료 삭제 완료를 안내하지 않는다. 로그인 불가 고객의 대체 본인 확인, 자료별 최종 처리, 고객의 완료 회신은 이 코드가 자동 수행하지 않는다. 보존 기간이나 응답 시간을 임의로 새로 약속하지 않았다.

## 실제 검증과 남은 운영 검사

- 본인 코드/API/UI: 위조·목적/프로젝트 변경·만료·출처·본문 크기·익명 거절·발급 제한·계정 전환·클립보드 실패 회귀. 오류 보고 자체 실패 때도 비공개 503 응답을 보존한다.
- 사건 engine: 문의 없는 입력, 파괴 전 영속 기록 실패, 접수 응답 유실, job/본인 불일치, 중복 접수, 처리 응답 유실, claim/수동 보류, Auth 이후 finalizer 실패, 원장·부재 미확인과 실행 직전 관측 만료를 검사했다.
- 읽기 전용 운영 경로는 별도 인증과 캐시 금지를 적용하며 배포 commit을 모르면 null을 반환한다. 운영 명령은 null·다른 commit·문자열 false·누락/추가 필드·활성 플래그·만료된 응답을 거절한다. Vercel 대시보드 인증을 완료한 것으로 간주하거나 자동 탈퇴를 켜는 우회가 아니다.
- 실제 Windows DPAPI 저장소: 원문 비노출, 재열기, 중복 프로세스 거절, 암호문 손상 거절, 순차 저장을 실행했다. PowerShell 7에서 5.1을 호출할 때 상속되는 모듈 경로 때문에 ACL 검사가 실패한 문제도 수정했다.

이 문서 시점에는 고객 삭제·새 시험 계정의 제품 삭제·메일 발송을 실행하지 않았다. 실제 운영 시험은 새로 만든 빈 단독 시험 계정의 exact 대상에서 진행하고, 그 성공을 자료가 있는 모든 고객의 삭제 완료로 확대하지 않는다. 현재 일반 고객 처리의 자료별 마감은 **W12 미완료**로 유지한다.
