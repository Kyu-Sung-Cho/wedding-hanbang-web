## 이번 검증

핵심 9개 파일 **576개 회귀 검사 통과**, 실패·건너뜀 0. 실제 route의 제안→승인→실행 배선, 예산 CAS·배분 보존, 개인 저장 권한, store 재조회와 replay, 검색 후속과 큰 변경 프롬프트를 포함한다. 모델은 합성이며 SQL은 로컬 PGlite다. 유료 모델/운영 DB 실행으로 집계하지 않는다. 원문은 `core-regressions/vitest-raw.log`다.

랜딩 본문 변경 `ab7e53c`에 대해 저장소의 `pnpm verify`가 정한 웹 타입·lint, 웹 911개 파일의 10,515개 검사와 저장소 433개 검사를 통과했다. 뒤이어 추가한 글꼴 캐시 갱신은 파일과 URL 해시가 다르면 실패하는 회귀 검사를 먼저 확인했고, 수정 후 관련 19개 검사·lint·토큰 검사와 production build를 통과했다. 최종 로컬 화면은 320·390·1440px에서 가로 넘침·JavaScript 오류 없이 열렸으며 두 CTA 목적지와 비로그인 루트 307 이동을 확인했다. 장식용 `aria-hidden` 따옴표에 대한 대비 검사 경고 2개는 남아 있어 접근성 자동 검사 전체 통과로 표시하지 않는다.

운영 평가 스크립트도 실행했으나 `/api/demo/start`에서 404로 종료했다. **모델 호출은 0회**다. 공개 체험은 닫혀 있고, 현재 프로세스의 평가 토큰은 운영에서 인증되지 않았다. Vercel에는 production·preview 평가 비밀값이 각각 등록돼 있음을 확인했지만 값 불일치 등 정확한 원인은 확정하지 않았다. 비밀값·공개 체험 설정을 변경하지 않았다. 이 평가기는 정상 작동해도 demo 전용이므로 실제 고객형 예산 저장 E2E를 대신하지 않는다.

이후 소유권이 확인된 합성 계정·준비 공간과 정확한 삭제 범위를 갖춰 실제 인증 예산 시험을 진행했다. 사용자 데이터나 현재 로그인된 고객의 예산을 실험용으로 변경하지 않았다.

### 실제 인증 시험 첫 실행의 판정 정정

06:54 UTC 운영 `75b4606`에서 실제 모델이 합성 입력의 총 3,500만 원·정확한 8항목 확인 카드와 변경 미리보기를 만들었고, 확인 전에는 예산과 revision이 그대로였다. 그러나 시험 하네스가 현재 화면에서 쓰지 않는 예전 `POST` 승인 단계를 호출해 503으로 종료했다.

현재 예산 카드 정책은 `single`이며 화면은 `PUT` 실행권 확보 후 확인 메시지로 실행한다. 운영 DB 정책·함수·권한과 화면 코드를 대조해 확인했다. 해당 정책에서 불필요한 `POST`를 호출하면 RPC가 거절하고 API가 503으로 변환한다. **이 실행은 정상 UI의 저장 결함을 입증하지 않는다.** 처음 이를 서비스 결함으로 보고한 설명을 정정했고 제품 로직이나 승인 경계를 변경하지 않았다. 첫 실행에서 유효한 증거는 실제 모델의 정확한 제안과 확인 전 미변경까지다.

시험 계정의 세션 해제·Auth 삭제 이후 일반 REST로 읽을 수 없는 내부 테이블 때문에 정리 확인이 중단됐다. 이어 운영 Management API의 명시적 읽기 전용 조회로 Auth·프로필 부재와 본인 커플 범위 14개 테이블의 잔여 행 0을 확인했다. Auth→커플의 정상 CASCADE이며 원장 직접 삭제·비용 장부 복원은 하지 않았다. 첫 실행 결과를 덮어쓰지 않고 `owned-live-budget-eval/result.json`과 `cleanup-readonly-result.json`을 함께 보존했다.

### 현재 UI 계약에 맞춘 실제 운영 저장 시험

07:13–07:14 UTC, 운영 `75b4606`에서 새 소유 합성 계정으로 v2 시험 1회를 실행해 exit 0으로 통과했다. 서로 다른 두 검토자가 현재 화면과 `single → PUT claim → confirmedActionId 실행` 계약을 대조한 뒤 실행했다. 고객 자료와 로그인 세션은 사용하지 않았다.

- 실제 모델이 예식장 1,200만·스튜디오 300만·드레스 200만·메이크업 100만·예물 400만·신혼여행 700만·본식스냅 200만·예비비 400만 원의 확인 카드와 미리보기를 생성했다.
- 확인 전 총액·배분·revision은 변경되지 않았다. 실행권 확인 후 확정 메시지로 실행하고 성공 영수증의 8항목과 총 3,500만 원을 검사했다.
- DB 재조회에서 모든 배분과 총액이 일치했고 revision은 0→1이었다. 요청 밖 준비 정보는 보존됐으며 앱이 사용하는 `/api/auth/me` 조회와도 일치했다. `/api/chat` 요청은 정확히 2회, 불필요한 이전 POST 승인 호출은 0회였다.
- 세션 해제·Auth 삭제 후 Auth·프로필 부재, 일반 REST 11개 범위와 Management 읽기 전용 내부 3개 범위의 잔여 행 0을 확인했다. 비용 장부를 되돌리거나 로그를 임의로 삭제하지 않았다.

이는 **표준 분류로 명확히 주어진 합성 8항목의 실제 저장 시험**이다. 팀원 T12의 ‘사진’, ‘드레스·정장’, ‘초대장·꽃·하객선물’처럼 여러 분류가 묶인 원문을 그대로 재생한 시험은 아니다. 그 자연어 분류 품질, 브라우저 예산 탭의 실제 표시, 모든 기존 대화의 품질까지 이 결과로 통과 처리하지 않는다. 원문 증거는 `owned-live-budget-eval/v2/result.json` 및 `cleanup-internal-readonly-result.json`이다.

## 랜딩 변경의 이유와 경계

‘지금 할 일부터 함께 정리’, ‘궁금한 것부터 정할 것까지’, ‘흩어진 준비를 한곳에’ 세 방향을 비교했다. 처음 준비하는 사용자가 무엇을 도움받는지 가장 직접 이해할 수 있도록 첫 번째를 선택했다. 사용자 실험으로 전환율 개선이 입증됐다는 주장은 하지 않는다.

- 첫 화면에서 AI 아모라, 준비 순서·예산 질문과 사용자가 확인한 뒤 기록되는 목적지를 설명한다.
- 대화 예시 바로 다음에 확인→예산·할 일·일정 반영 예시를 보여준다. 의견 차이·무료 도구·커뮤니티는 그 뒤에 설명한다.
- 개인 상담의 처리·저장·배우자 비노출 설명을 개인 상담 카드 안에 배치한다. 공동 대화까지 비공개라는 오해를 줄인다.
- 가입 필요, 현재 결제 미요청, 향후 비용 미정, AI 답변·샘플·출처 고지는 유지한다. 실제 상담 무제한·영구 무료·자동 장기 기억·절감 성과는 약속하지 않는다.
- 팀원 HTML의 종이 표면·색·서체·모바일 배치를 유지한다. 새 문구가 다른 글꼴로 섞이지 않도록 랜딩 전용 WOFF2 6개에 필요한 한글을 추가했다.
- 실제 운영 글꼴 응답의 1년 immutable 캐시를 확인했다. 각 글꼴 주소에 파일 SHA256을 붙여 재방문자도 새 글꼴을 받도록 하고, 파일과 주소가 함께 갱신되는 회귀 검사를 추가했다.
- 루트 진입 규칙은 유지한다. 비로그인 `/`는 `/landing`으로, 로그인 사용자는 기존 준비 공간으로 이동한다.

이번 랜딩의 새 커밋·배포·화면 검증 결과는 별도 최종 영수증으로 남긴다. 위의 05:56 배포 기록은 새 랜딩 문구의 배포 증거가 아니다.
