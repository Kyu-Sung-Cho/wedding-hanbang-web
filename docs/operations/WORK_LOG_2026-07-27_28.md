- `DISCLOSURE_ROUND_SNAPSHOT_LABELS = ["2026Q3"]` — 화면 라운드가 **어느 내부 스냅샷을

`SAME_BUSINESS_DIFFERENT_NAME` 대응표를 뒀다.

목록(`vendorIdentityKey`)과 상세 형제 조회(`loadVendorIdentityRows`)가 같은
`canonicalVendorName`을 쓴다. 형제 조회 ILIKE 패턴도 **대표 이름으로** 만든다 —
방문한 이름이 긴 쪽이면 그것으로 만든 패턴이 짧은 형제를 못 잡아, "가을"에서는 병합되고
"가을스튜디오"에서는 안 되는 반쪽 상태가 된다.

### 미결 37쌍을 웹 검색으로 못 닫는 이유

1차 리서치가 **이미 시도했다가 증거 게이트에서 걸러낸 것**이다. 미결 쌍 102곳에 대한
건너뜀 기록 135건, 사유는 `low_confidence` 82 · `nothing_verified` 33 ·
`proof_gate_reject` 9. 거절 사유 문장이 대부분 이렇다:

> 정규화 후 2자 초단명 상호. 같은 배치의 'X스튜디오'와 동일 업체일 가능성은 있으나
> 별도 행으로 공시돼 있어 단정 불가 — 오배정 위험으로 보류

즉 **"다른 업체다"가 아니라 "짧은 이름이라 확정할 근거가 없다"**이다. 일반 웹 검색으로
재시도해도 웨딩 플랫폼 제휴 목록에 이름만 스치는 수준이라 "동명 업체가 없다"를 확정할
수 없다. 남은 경로는 업체 직접 확인이나 다음 공시 라운드다.

### 라이브 실증

| | 시작 | 1차 후 | 2차 후 |
|---|---|---|---|
| 카드 | 868 | 852 | 842 |
| studio | 313 | 303 | 297 |
| dress | 215 | 209 | 205 |
| 후보 | 79쌍 | 63쌍 | 53쌍 |

양방향 확인: `구호 스튜디오`(변형 슬러그)로 열어도 대행사 5곳 전부,
`더청담`(대표 슬러그)에서도 4곳 전부. 분리 유지한 것들은 그대로 남아 있다.

## 5. 첫 화면 업체 수 502 → 412 (`da283897`)

**유통 글 게시 직전에 잡았다.**

### 무엇이 틀렸나

첫 화면과 유통 글이 "업체 502곳"이라 했지만 화면에서 세는 카드는 **412개**다.
`502`는 `count(distinct vendor_id) from v_public_vendor_policies`, 즉 DB 행 수다.

차이 90의 분해:

- `502 → 428` : 같은 이름+카테고리 중복 행(74) — 이미 한 카드로 묶이고 있었다
- `428 → 423` : 공백·구두점 정규화
- `423 → 412` : 오늘 병합 26쌍

즉 **78은 2026-07-26 위약금 기능 출시부터 있던 과장**이고 12가 오늘 것이다.
`831건`(원문 수)은 병합해도 안 변하므로 그대로 맞다.

### 왜 안 잡혔나

§1-④ 참고. 정합성 테스트가 세 표면의 **일치**만 봤다.

### 수리

- `PUBLISHED_VENDOR_COUNT` 502 → 412, 왜 행 수를 쓰면 안 되는지 상수 주석에 기록
- `audit:production`에 `=== 1-c. 공시 규모 표기 (화면 기준) ===` 신설 —
  첫 화면 상수를 **소스에서 읽고**, `vendorIdentity.ts`의 병합·분리 목록을 적용해
  카드 수를 계산해 대조. 어긋나면 어디를 고칠지까지 말한다.
- 정합성 테스트 전제 교체 — "같은 숫자"가 아니라 ①vendor 행 수 ≥ 화면 업체 수
  ②감사에 화면 기준 대조 구간 존재 ③감사가 첫 화면 상수를 실제로 읽음
- 유통 글 2곳 + 커버리지 비율(502/868 → 412/842) 정정

### 실측

```
=== 1-c. 공시 규모 표기 (화면 기준) ===
  vendor 행 502 → 화면 카드 412 (병합 대응표 26 · 분리 3)
  PASS  첫 화면의 업체 수가 화면에서 셀 수 있는 값과 일치 — 주장 412곳 · 실제 카드 412곳
```

502로 되돌리면:

```
  FAIL  ... — 주장 502곳 · 실제 카드 412곳 — CommunityLandingClient의
        PUBLISHED_VENDOR_COUNT를 고칠 것
```

정적 테스트로는 못 잡는다(값 검증에 DB가 필요하다). 그게 맞는 분담이다.

## 6. 검증 방법에서 배운 것

### 배포 확인

**`/wedding`의 `Age` 헤더를 쓰면 안 된다.** force-dynamic이라 늘 0에 가까워서,
배포되지 않았는데 "새 배포"로 오판한다(이 세션에서 실제로 그랬고, 라이브는 여전히
502를 보여주고 있었다).

**정적 경로(`/price/studio`)의 ETag 변화**로 본다. 빌드마다 반드시 바뀌고
동적/정적 구분에 안 휘둘린다. 배포 전후로 화면 문구가 안 바뀌는 변경(상수 추가·CI·
스크립트)에서는 ETag가 유일하게 믿을 수 있는 신호다.

### 게이트 범위

`pnpm qa:local`(=`verify-local.mjs`)은 **웹·모바일·shared의 typecheck·lint·vitest·build만**
돈다. 루트 계약 스위트(`scripts/tests/*.test.mjs`)는 `pnpm test`에만 있다.
qa:local 그린만 보고 "전부 통과"로 읽으면 새로 추가된 계약 검사가 조용히 안 돌아간다.

### 인라인 스크립트

Python으로 파일을 다시 쓰면 Windows에서 **줄바꿈이 전부 CRLF로 바뀐다.** 이 세션에서
그것 때문에 YAML 파서가 통째로 헛돌아 변이 테스트를 오판했다. `newline='\n'`을 명시하거나
Node로 쓸 것. 가드 쪽도 줄바꿈을 정규화하게 고쳤다.

`| tail` 파이프는 종료코드를 가려 실패를 통과로 오독시킨다(이전 세션 교훈, 여전히 유효).
