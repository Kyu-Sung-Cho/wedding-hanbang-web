| 인기순을 페이지 분할 후 다시 정렬 | 기존 점수와 같은 순서의 DB 생성 컬럼·인덱스로 전체 정렬 후 페이지 분할 | 페이지 밖의 실제 상위 글 진입, 동점 순서, 댓글 변경 반영, null 날짜, RLS 유지. |

행동 목록은 표시량을 제한한다. 전체 개수와 `truncated`를 반환하며, 수정 과정에서
전체 기록을 무제한으로 읽는 방식은 채택하지 않았다.

## 초기화와 진행 중 답변의 경계 보강

`reset_own_amora_chat_view`는 인증된 본인 화면의 커서만 변경한다. 기존 프로필 잠금
순서를 따르고, 기존 답변 저장 함수와 같은 커플 epoch를 잠근 뒤 DB 시각으로 커서를
만든다. 답변 저장이 먼저면 그 답변까지 숨기고, 초기화가 먼저면 이전 epoch의 저장을
거절하며 기존 비용 정산·영수증을 유지한다. 커서와 epoch는 한 SQL snapshot으로 읽는다.

웹은 계정 수명과 화면 경계를 분리해 진행 중 응답을 무효화하면서 Realtime 구독을
유지한다. 늦은 SSE, 연속 초기화의 응답 역전, 초기화 이후 도착한 새 메시지 보존,
빈 화면 polling에서 숨긴 과거 50건에 막히는 경로를 함께 처리한다. 다른 탭의 저장
커서와 현재 탭에 적용된 커서를 구분해, 다중 탭에서도 경계 전진 시 이전 응답을 중단한다.

개인 초기화도 기존 **커플 단위 epoch**를 올리므로 파트너나 다른 상담 범위의 진행 중
답변이 취소될 수 있다. 해당 범위의 메시지·커서·저장된 예산·일정·메모리 동의는
삭제하거나 변경하지 않는다. 공동 정리 요청의 기존 요청 시점 의미도 유지한다.

  다른 탭 커서 뒤 지연 SSE 재노출은 수정 전 실패를 재현한 후 통과했다.

## 배포 전 필요한 일과 남은 위험

1. **실제 AI 대화 재시험:** 첨부의 두 라운드를 분리된 테스트 공간에서 다시 실행해
   초기화 직후 응답, 긴 예산 회상, 공동/개인 귀속, 세 일정 요청, 여러 예산 배분,
   조건 변경 후 요약을 확인해야 한다. 프롬프트 규칙의 존재는 출력 품질의 보장이 아니다.
2. **hosted 초기화 동시성 검증:** reset과 epoch/저장 RPC의 계약은 로컬에 보강했다.
   PGlite에서 실제 SQL을 실행해 두 순서의 결과·롤백·정산을 확인했으나, 두 연결이
   실제로 잠금을 다투는 hosted PostgreSQL 시험은 하지 않았다. 운영 적용 전 그 경계를
   검증해야 한다. 개인 초기화가 다른 범위의 진행 중 답변도 취소할 수 있는 점도 확인한다.
3. **입력량 측정 장애의 영향:** 측정 서비스가 장애이면 상담 요청은 일시 실패한다.
   제공자의 더 큰 context 한도에 맡겨 앱의 64K 예약 상한을 우회하던 동작을 제거한
   의도적 결과다. 실제 count endpoint의 가용성·지연은 배포 전에 확인해야 한다.
4. **DB→웹→모바일 순서:** 인기순 migration
   `20260905153207_community_hot_rank_before_pagination.sql`과 초기화 migration
   `20260905223222_amora_atomic_chat_view_reset.sql`을 hosted 환경에서 검증한 뒤
   API를 배포해야 한다. 미적용 DB에서는 인기 목록 및 새 채팅 snapshot/reset 조회가
   실패할 수 있다. 초기화 migration은 기존 원자적 저장 함수와 활성 epoch trigger를 요구한다.
   모바일 설정의 서버 커플 검사를 먼저 배포하고 새 모바일을 배포해야 한다.
5. **릴리스 서명:** 두 새 migration을 현재 manifest에 등록하고 로컬 기대 서명을 갱신했다.
   `deployment_blocked` 및 기존 운영 증거 상태는 유지했다. Vercel 운영 환경변수
   `VENDOR_DISCLOSURE_PRODUCTION_AUTHORIZATION`은 변경하지 않았다. 최종 서명은
   `scripts/tests/release-manifest-signature-pin.test.mjs`와 실제 manifest로 확인하고,
   운영 승인·백업·복구·hosted 검증을 마친 배포 절차에서만 교체해야 한다.
6. **기기 검증:** SecureStore의 실제 iOS/Android 잠금·백그라운드 갱신 및 새 앱의
   승인 카드 표시를 기기에서 확인해야 한다. 테스트의 동시성 보장은 단일 JS runtime이다.
