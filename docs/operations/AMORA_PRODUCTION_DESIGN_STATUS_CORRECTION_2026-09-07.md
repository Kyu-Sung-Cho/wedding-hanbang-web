## 화면 순서와 시안 반영 범위

현재 진입 흐름은 비로그인 사용자의 `/` → `/landing`, 로그인 사용자의 `/` 및 기본 로그인 완료 목적지 → `/wedding/lounge`다. 이번 작업은 이 기본 진입 순서를 바꾸지 않았다. 사용자에게 아모라 미션·대화 중 어느 화면을 먼저 열지 확인 중이며, 답변 전에 다른 흐름으로 임의 전환하지 않는다.

시안의 미션·보드 표면은 `/wedding/chat/missions`, `/wedding/chat/board`에 연결된다. 소스 내부 경로는 `/chat/missions`, `/chat/board`다. 새 shell은 아모라·체크리스트 경로에 적용되고 라운지·예산·일정까지 전부 같은 shell로 교체한 것은 아니다.

랜딩의 큰 섹션 순서는 팀 HTML과 기존 구현이 이미 유사했다. 내부 배치·타이포그래피·카드 스타일 변경과 진입 순서 변경은 다른 작업이다. 팀 HTML의 사진 영역은 실제 사진이 아닌 자리 안내였다. 제공되지 않은 사진이나 가상의 고객 후기를 실제 자료처럼 넣지 않았다.

기존 보드는 할 일의 완료·진행·숨김 상태를 보여주고 있었다. 시안의 결정 보드와 의미가 달랐다. 상단에 실제 `decision_nodes`의 공동 결정 기록을 연결하고 기존 실행 기능은 아래 공유 할 일 영역에 보존했다.

- 실제 저장 상태로 확정·논의 중·미정을 분류한다. ‘확정’을 두 사람의 승인 완료로 표현하지 않는다. 서버에 존재하지 않는 합의나 예산 반영 결과를 만들지 않는다.
- 30개씩 이전 기록을 읽으며 표시 숫자는 불러온 기록 수다. 기존 할 일 편집·완료·복원 기능은 유지한다.

## 운영 사전 절차의 실제 완성도

원본 복구 환경 정보만 받으면 모든 준비가 끝난다는 이전 설명도 부정확했다. 현재 범위의 원본 수집기와 hosted SQL 리허설 실행기 자체에 빠진 부분이 있어 이번에 보완했다.

`supabase:release:capture-current`는 현재 252개 보존 대상과 Storage 원본을 HBAM2/CurrentUser DPAPI로 암호화하는 실행기다. 일관된 읽기 snapshot, 원본 크기·해시, 두 번째 읽기 비교, 실패한 수집의 사용 거부를 수행한다. 개별 relation 32 MiB와 Storage 원본의 명시적 한도를 넘으면 실패하며 일부만 저장하고 성공으로 보고하지 않는다. **운영 원본 수집이나 격리 복구는 아직 실행하지 않았다.**

`supabase:release:rehearse-current`는 검토된 SQL 8개와 합성 시나리오를 하나의 트랜잭션에서 실행하고 rollback을 확인하는 도구다. 운영 project ref와 PostgreSQL system identifier를 거부한다. **실제 hosted 실행, 여러 연결의 동시성, HTTP feature flag, 전체 릴리스 성공을 증명하지 않는다.** 결과의 `evidenceComplete`는 false다.

다음은 여전히 미완료다.

1. 원본 DB·Storage 전량의 실제 암호화 수집, 안전한 격리 환경 복구 및 원본 비교. 현재 범위 전체를 복구하는 hosted 실행기와 실행 증거도 필요하다.
2. 실제 외부 쓰기 차단, 기존 업로드 URL·TUS 만료/배수 확인, 실패 시 복구 및 차단 유지 검증.
3. Auth 차단 중 복구 비교와 운영자 전용 합성 인증 시험을 단계로 나눈 실행 검증.
4. 실제 hosted SQL·동시성·HTTP 플래그 회귀와 인증 사용자·실제 AI 모델의 전체 흐름 시험.
5. 운영 candidate 배포, 정확한 커밋 확인, 도메인 전환 후 PC·모바일 실사용 확인.

`AGENTS.md`의 운영 변경 규칙은 전역 쓰기 차단·백업·복구·rollback 증거와 사전 게이트를 요구한다. 다만 현재 릴리스 계약의 ‘모든 로그인·refresh 차단, 모든 공개 권한 0, 모든 외부 송신 차단’은 그 요건을 구현하기 위해 선택한 구체적 설계다. 유일한 가능한 방식이라고 설명해서는 안 된다. 동등한 안전성을 실증하는 다른 격리 방식은 계약과 검증기를 함께 검토해야 하며, 체크박스 삭제나 임의 성공 영수증으로 대체할 수 없다.

## 검증 결과의 읽는 방법

이전 의존성 보완 및 배포 사전 절차 문서는 각각 작성 당시 커밋의 기록이다. 그 문서의 테스트 수를 이번 미커밋 변경의 성공 증거로 재사용하지 않는다. 이번 변경은 새 테스트의 실제 의미 변이 검출, diff가 고른 전체 검사, 빌드 및 새 Preview 커밋 확인 결과로 별도 판정한다. 운영 배포가 없으면 검사 성공과 무관하게 **운영 배포 안 됨**으로 보고한다.
