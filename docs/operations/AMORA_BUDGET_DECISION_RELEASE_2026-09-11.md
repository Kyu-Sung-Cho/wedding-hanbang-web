# 아모라 승인 예산의 결정 기록 보완

2026-09-11 KST. 상태: 코드 검증 완료, 운영 적용 증거 준비 중. 이 문서는 출시 완료 증명서가 아니다.

## 확인한 문제와 변경

운영 시험 계정에서 승인한 사용자 예산 항목을 1,500,000원→1,501,000원→1,500,000원으로 변경하고 새로 읽었을 때 금액은 맞았다. 실행 기록과 revision receipt는 각각 2개였지만 신규 예산 decision_nodes는 0개였다. 기존 트리거가 일정 실행만 처리했다.

신규 SQL `20260910160514_amora_shared_budget_decision_receipts.sql`은 실제 승인 실행의 예산 변경 전후 값을 기존 receipt에 보관하고, 같은 트랜잭션에서 공유 결정 기록을 생성한다. 총예산, 기본·사용자 항목, 항목 추가, 배분안을 지원한다. 승인하지 않은 요청, 개인 상담, 수동 수정, 실패, 금액 변화 없는 실행과 지출액만의 수정은 이 기록을 만들지 않는다. 재시도는 중복 결정을 만들지 않으며 기록 생성이 실패하면 예산 변경도 함께 되돌아간다.

과거 완료된 실행을 소급해 채우지 않는다. 원래 일정 전용 decision_node_id/decision_recorded_at 제약은 바꾸지 않는다. 금액 미입력과 0원을 구분하며 기존 nullable progress도 유지한다. 두 사람 모두의 합의나 지불 완료라고 표현하지 않는다.

웹의 상담 맥락은 새 예산 기록 중 현재 예산과 달라진 과거 값을 제외한다. 결정 보드의 이력 자체는 보존한다. SDK 수준 검사에서 과거 1,501,000원 대신 현재 1,500,000원 기록만 실제 provider 입력에 전달되는 것을 확인했다.

## 소스와 배포 검증의 분리

새 후속 계약은 현재 전체 migration 227개의 검토된 원문을 검사하고, 운영에서 직접 읽은 ledger 215개와 head 20260907085111에 신규 SQL 정확히 1개만 적용하도록 제한한다. 새 허용 변경은 함수 2개와 relation 4개의 정확한 hash 전이뿐이다. 기존 모든 행, hot_rank, 권한과 다른 스키마는 보존한다. 새 budget_delta 열만 행 hash에서 정규화하고, 적용 직후 기존 행의 값이 모두 NULL인지 별도로 검사한다.

기존 계약·self pin·과거 SQL은 수정하지 않았다. 구판 계약의 정상/거절 시험은 a4f27ae2313faf9ba0b172ff128665e5cbf16d2b의 검증된 전체 역사 입력을 이용한다. 실제 현재 checkout에 구판 loader를 적용하면 계속 거절된다. fixture는 고정 Git blob/SHA 300개를 읽으며 원문 누락 시 현재 파일로 대체하거나 네트워크로 받지 않는다. 해당 CI 두 작업만 전체 Git 이력을 가져온다.

관리형 Storage 인덱스 3개와 Realtime 날짜 partition 변화는 별도 읽기 원문과 이전 구조 재구성 hash로 검증했다. 이 차이를 일반적인 미검토 스키마 허용으로 확대하지 않는다.

## 운영 적용 전에 남는 단위

1. 격리된 PostgreSQL 17 대상의 현재 제품 baseline과 정확한 새 SQL로 hosted rollback을 실행한다.
2. 실제 두 DB 연결로 roster/예산 경합, 같은 승인 재시도, 다른 owner lease를 검사한다.
3. 현재 후보에 묶인 fresh backup과 원본 복구 자료, Storage 원본·Auth 등 필요한 격리/복구 증거를 확보한다.
4. 기존 정식 release 진입점에서 write fence, 정확한 pending SQL 1개 dry-run, check-only, 원자 apply를 수행한다.
5. 같은 후보의 Vercel 배포·읽기 canary·정확 owner finalizer 후 fence를 해제하고, 실제 승인 예산과 결정 보드 동시 저장을 재검사한다.

현재 저장소의 기존 hosted/backup CLI는 과거 계약에 고정되어 있다. 이전 운영에서 사용한 별도 native 두 연결 리허설과 independent snapshot 수집기 원문도 발견했으며, 현재 후보·대상 기준으로 재사용할 수 있는 범위를 추가 검토 중이다. 환경변수가 비어 있다는 이유로 인증 경로가 없다고 판단하지 않는다. 검증기를 약화하거나 임의 SQL wrapper로 운영에 적용하지 않는다. 로컬 PGlite 성공을 hosted 두 연결 또는 운영 복구 성공이라고 표시하지 않는다.

두 시험 계정의 공유·개인 분리, 개인/공유 Memory ON, 실제 제품 탈퇴, 전체 DB/Auth/Storage 복구와 알림 전달은 이 예산 코드 변경과 별도 출시 검증이다. 시험 계정에서 실제 확인한 항목과 미확인 항목을 나누어 출시 판단에 사용한다.
