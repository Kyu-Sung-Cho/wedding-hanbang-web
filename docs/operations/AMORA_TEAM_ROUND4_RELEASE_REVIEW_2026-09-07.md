## 배포 조사에서 직접 확인한 것

- 운영 Supabase 기준은 `20260902120000`이며 과거 릴리스 계약의 7월 기준과 다르다. 로컬 기록만 있고 원격 ledger에는 없는 과거 항목 12개를 전부 재실행하거나 적용됐다고 repair하지 않는다. 10개는 효과 존재를 확인했고, 일부 권한·RPC 차이는 별도 drift로 남겼다. 누락된 mediation share/discard RPC는 현재 앱 runtime caller가 없으므로 이번 실행 실패 원인이라고 단정하지 않았다.
- 기존 staging에는 합성 외 계정·대화와 Storage가 있다. 빈 복구 후보도 signup/provider/public API 격리가 되어 있지 않아 운영 원문을 즉시 복사할 수 있는 상태가 아니다.
- 공식 Supabase CLI 인증으로 비공개 Storage 객체 1개를 메모리에서 받아 기존 HBAM2 암호화·복호화·digest·ACL 검증에 성공했다. 합성 객체인지는 확인되지 않았다. 기존 프로젝트 설정의 토큰을 메모리로만 읽은 공식 Management API READ ONLY 경로도 확인했다. 이것은 전체 DB/Auth/Storage 백업·복구 영수증이 아니다.
- Vercel CLI 인증은 성공했다. 공식 `env run`은 민감 설정값을 내려주지 않았다. 임의로 민감 속성을 해제하거나 서버에서 키를 출력하지 않았다. preview의 연결 대상·필수 설정도 완성된 검증 환경으로 확인되지 않았다.
- 기존 운영 평가기를 서명 경로로 실행했으나 demo session404에서 종료했다. 모델 응답은 평가하지 못했다. 앞선 일반 smoke403은 서명 없는 기존 검사 도구의 경로 문제이며 제품 장애로 세지 않는다.
- 운영 DB·Auth·Storage의 실제 쓰기 중단/서명 업로드 대기, 최신 전체 암호화 백업, 별도 대상 복구, staging 적용, 정확한 finalizer·canary 영수증은 아직 없다. `deployment_blocked`와 증거 누락을 유지한다. 운영 서명 환경변수, main, 운영 DB는 수정하지 않았다.
- 최종 제품 SQL 7개는 정확한 SHA256으로 기존 manifest에 등록했다. 정적 release fence는 통과하지만 기존 manifest는 7월 기준의 전체 후속 SQL 109개와 백업 27개 테이블에 묶여 있고 현재 baseline을 받는 controllerContract가 없다. 독립 담당자가 실제 로컬 선택 함수를 실행해 `SUCCESSOR_RELEASE_DEPLOYMENT_BLOCKED`를 확인했다. 원격 적용 명령은 실행되지 않았다. 차단을 제거하거나 과거 이력을 재실행하는 수정은 이번 제품 수정에 섞지 않았다.

검수한 코드·자산·문서 254개만 커밋 대상으로 선택했고 원본 상담·환경변수·비공개 검증 자료를 포함하지 않았다. 최종 자료 처리·저장소 검사는 새 파일을 Git index에 포함한 상태에서 실행됐다. `git diff --cached --check`는 원문 폰트 라이선스 공백 5줄과 Markdown 의도적 줄바꿈 2줄을 보고했다. 이 7줄을 개별 확인해 원문과 문서 형식을 보존했고 코드 공백 오류는 없었다. 원래 `wedding`의 추적 파일과 기존 백업 stash는 보존했다. 원격 main은 기준 SHA 그대로이며 운영 배포는 이 검증에 포함되지 않는다.
