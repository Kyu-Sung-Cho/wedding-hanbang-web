- **상태: 어둡게 병합 / 사람 확인 0건 / `UNVALIDATED`.** 새 방문자의 기본 진입은 계속 v3.1이다(`apps/web/src/app/wedding-code/entry.ts`의 상수 `WEDDING_CODE_DEFAULT_VERSION`이 v3.1이고, 골든 표 `entry.golden.json` 136줄이 옛 링크의 파싱 결과를 고정한다). v4는 `?v=v4.0-tendency`(답 없음, noindex)와 `#v=v4.0-tendency&a=…` 링크로만 열린다. 기본 진입 교체는 문항 검수(0a)와 인지면접(0b)을 통과한 뒤의 별도 PR이고, 재검사(G3)를 통과하기 전에는 noindex·사이트맵 제외·홍보 없음이다.
- **링크 전용.** 서버 함께 보기, 계정 저장, 아모라 도움 설정 연결은 v3.1에만 있다. v4의 답은 주소의 `#` 뒤와 이 브라우저 저장소(30일)에만 있고 서버에 보내지 않는다. 저장은 브라우저 단위라서 사파리, 크롬, 카카오톡·인스타그램 같은 앱 안 브라우저는 서로 저장소가 다르다(화면 문구도 「이 기기」가 아니라 「이 브라우저」다). 이용 통계는 이미 고지한 이벤트 8개와 속성 8개만 쓴다. 주소의 `#` 뒤가 오류 수집 도구로 나가지 않게 하는 정제기 PR(#473)이 운영에서 확인되기 전에는 v4의 링크 공유를 공개하지 않는다. 이 순서는 문장이 아니라 병합 규칙이다: `#…&a=` 를 읽는 입구 PR(계약 문서 13절의 PR-5)은 #473이 병합되고 운영에서 확인되기 전에는 병합·배포하지 않으며, 소스 가드(`wedding-code-v40-source-guards.test.mjs` 규칙 10)가 병합 여부를 본다. #473의 병합 커밋이 들어 있는 브랜치(`feat/wedding-code-v4-depth-20260929`)에서는 규칙 10이 초록이지만 운영 확인은 사람이 한다.
- **기존 경계는 그대로다.** Candidate 6.3 차단(§4 여섯 게이트)은 v4를 해제하지도 대체하지도 않는다. 공개 `/wedding-code`는 Candidate 6.3 측정 코드와 별개이며, v4의 0a~3 단계는 v4 자신의 공개 문구 게이트다. 궁합 점수·관계 예측 금지와 2026-09-27 결정(스타일 이름 없음)도 그대로다.

## 결과 정직성·질문 흐름 정리: 2026-09-27 (v3.1 전용)

2026-09-26 v3.1 감사의 ‘지금 고칠 것’을 반영한 변경이다. 아래 내용이 같은 주제를 다룬 2026-09-23·09-24 문서의 해당 문장보다 앞선다. 배포 여부는 PR과 검증 영수증으로 따로 확인한다.

- **우선순위는 기본 흐름 끝 화면에서 묻는다.** 기본 흐름 화면은 동의 문장 15개 → 취향 6개 → 피하고 싶은 것 → 더 쓰고 싶은 곳 → 우선순위 순서의 24개, 14페이지다. 선택 질문은 동의 문장 8개, 3페이지다. 우선순위는 선택 흐름에서 빠졌다.
  - 서버 함께 보기 계약과 완료 판정은 그대로다. `isV31CoreComplete`와 `V31_CORE_INDEXES`는 23개(우선순위 제외)이고, 화면 순서는 `V31_CORE_SCREEN_INDEXES`가 따로 맡는다. 문항 ID·보기 값·`v3.1-preferences`·공유 codec은 바꾸지 않았다.
  - 우선순위 화면은 앞에서 고를 보기가 있을 때만 나온다(‘그런 편이에요’ 이상으로 답한 문장, 직접 고른 취향, 피하고 싶은 것). 보기가 0개면 그 화면을 건너뛰고 우선순위를 채우지 않는다. 앞의 답을 고쳐 보기가 0개가 되면 다시 확인하라고 빈 화면으로 보내지 않는다.
  - 아무것도 고르지 않았으면 아래 고정 버튼이 ‘고르지 않고 결과 보기’(이전 전체 흐름은 ‘고르지 않고 다음 질문’)로 바뀌어 `skipped`를 남긴다. 목록 아래 보조 넘어가기 버튼과 비활성 버튼을 겹쳐 두지 않는다. 후보는 접지 않고 바로 보여준다.
  - 한 번도 우선순위를 묻지 않은 결과(예전 기본 흐름을 마친 저장본, 보기 0개로 건너뛴 뒤 취향을 고친 결과)에는 결과 화면에 ‘꼭 지키고 싶은 것 고르기’를 둔다.
  - 이 결정이 대체하는 문장: [34문항 부담·중복 감사](./2026-09-23_question_burden_audit.md)의 ‘우선순위는 결과 후 선택’, [선택형 마무리 계약](./2026-09-23_resume_and_optional_finish.md)의 ‘후보를 접고 넘어가기를 먼저’. 같은 계약의 ‘비활성 다음 버튼을 중복으로 보여주지 않는다’는 고정 버튼 하나로 지킨다. 두 문서의 해당 줄에 대체 표시를 달았다.
- **통계 기준이 같은 판 안에서 바뀐다.** `WEDDING_CODE_V31_VERSION`은 그대로인데 이 배포부터 기본 흐름 `scene_total`이 23→24, 선택 흐름이 9→8이고, 우선순위 건너뜀이 기본 흐름 `skipped_count`에 잡힌다. 끝까지 간 비율은 `scene_index == scene_total`이 아니라 `wedding_code_completed`로 센다. 우선순위 보기가 0개인 사람은 `scene_index` 23에서 끝난다. 새 이벤트나 속성은 만들지 않았다.
  - `result_kind`는 처리방침 고지대로 화면에 보인 결과의 종류다. 함께 보기 초대로 답해도 상대 답을 받기 전에는 `solo`다. 초대로 왔다는 사실은 `has_partner_link`가 맡는다.
- **네 글자 요약**은 [응답 요약 계약의 2026-09-27 개정](./2026-09-23_response_summary_contract.md#2026-09-27-개정)을 따른다(다섯 칸 점, 두 가지 ‘?’, 아슬한 글자, 이름 없음).
  - 같은 날 파운더 결정("스타일 이름은 빼고 아슬한 글자 기준도 바꿔줘")으로 ‘~스타일’ 이름·이름 출처 줄·헤드라인을 없앴다. 코드 옆에는 코드와 주제별 줄(글자, 글자 뜻 한 줄, 두 문장의 실제 답)만 있다. 한 문장에서 나온 글자(K·R·T·D·F·C·L·A)는 뜻 줄을 따로 두지 않고 그 문장의 답 줄에 영문 낱말을 붙이며, 글자가 정해진 자리(이 여덟 글자와 B)에는 ‘한 문장에만/두 문장 모두 ‘그런 편’ 이상’ 근거 한 줄이 붙는다. 시작 화면 소개도 「네 글자로 보는 준비 방식」이다.
  - 아슬한 글자는 한 문장만 ‘그런 편’ 이상인 한쪽 글자(K·R·T·D·F·C·L·A)이고 두 답이 정확히 한 칸 차이(4 대 3, 3 대 4)일 때만이다. B·M·N·‘?’는 아슬하지 않다. 예전 ±1 기준(답 하나를 한 칸 옮겨 글자가 바뀌면 아슬)은 25칸 중 19칸이 아슬이었다. 답이 25칸에 고르게, 주제끼리 따로 흩어진다고 치면 네 주제 중 하나라도 걸릴 확률이 약 99.7%다(계산값이며 실제 사용자 비율은 재지 않았다).
- **두 사람 비교**는 서로 반대로 답한 문장을 먼저 전부 펼치고, 함께 동의한 내용 바로 다음에 둔다. 한 사람만 ‘그런 편’ 이상인 문장은 ‘한 사람만 동의한 문장’, 상대가 해 주길 바라는 도움(H1·H2)에 둘 다 동의하면 ‘둘 다 바라는 도움’으로 따로 묶는다. 한쪽이 ‘어느 쪽도 괜찮아요’나 ‘따로 없어요’로 답하면 열린 답이다([문항·결과 계약](./2026-09-23_v31_clarity_contract.md) 해석 절 개정). 묶음 안은 화면에서 묻는 순서다.
- `/wedding-code`, `/wedding-code/together`, `/wedding-code/taste`는 자기 공유 카드를 쓰고 `og:url`은 적지 않는다(답과 초대 키가 `#` 뒤에 있다).

## 소비자 흐름 재검토: 2026-09-24 (v3.1 전용)

[문항·결과·초대 재검토](./2026-09-24_consumer_audit.md)는 그때의 문항 뜻과 코드 계산을 유지하면서, 하객 수 입력 기준·하객 없는 예식의 안내·보기 없음 상태·위임 허용 표현·우선순위 설명의 반복을 보완한다. 느린 생성·참여 응답이 답 수정 화면을 바꾸지 않도록 하고, 응답이 유실된 요청은 같은 탭에서 다시 확인할 수 있게 한다. 실제 소비자 유용성과 배포 여부는 문서의 설계 판단과 구분해 검증 기록으로 확인한다.

## 질문 페이지·초대 연결 변경: 2026-09-23 (v3.1 전용)

[질문 페이지·양방향 비교 계약](./2026-09-23_paged_couple_flow_contract.md)이 현재 변경의 기준이다. 기본 흐름은 짧은 동의 문장 3개씩과 개별 취향 선택을 조합해 보여준다(2026-09-27부터 끝 화면 우선순위를 더해 14페이지, 선택 8문항은 3페이지. 위 2026-09-27 절). 문항·점수·공유 codec은 바꾸지 않는다. 두 사람 결과는 함께 보기·내 결과·상대 결과를 나눠 읽는다.

별도 동의한 공개 ‘함께 보기’에 한해 서버 보관을 추가한다. 초대한 사람과 참여한 사람이 각자의 답 공유에 동의해야 두 사람 모두 결과를 볼 수 있다. 계정 연결 없이 접근 키로 확인하며 초대 생성 후 7일까지 접근하고 만료 후 하루 안에 지운다. 어느 쪽이든 연결을 끝내면 두 사람의 공유 답을 즉시 지운다. 이 예외는 기존 자동저장의 본인 브라우저 보관·옛 답 포함 링크·연구 저장 금지 계약을 일괄 변경하지 않는다. 아래의 ‘서버에 보내지 않는다’는 기존 개인 자동저장 설명이며 새 함께 보기의 별도 동의 후 전송에는 적용하지 않는다. 배포 여부와 실제 소비자 유용성은 각각 릴리스 증거와 소비자 검증이 필요하다.

## 응답 부담을 줄이는 현재 변경: 2026-09-23 (v3.1 전용)

새로 시작하는 v3.1은 **기본 23개 질문(2026-09-27부터 끝 화면에 우선순위) → 결과 → 원하는 경우 추가 질문**으로 나눈다. 문항별 판단은 [34문항 부담·중복 감사](./2026-09-23_question_burden_audit.md)를 따른다. 기본은 동의 문장 15개, 직접 취향 6개, 피하고 싶은 것과 더 쓰고 싶은 곳 각 1개다. 일반적인 비용 재배분 의향 B2와 조건 충족 시 선택 D2는 새 흐름에서 다시 묻지 않는다. 세부 문장 8개는 결과를 본 뒤 선택적으로 답한다. 우선순위는 2026-09-27부터 기본 흐름 끝 화면에서 묻고, 고르지 않고 넘어가도 결과를 볼 수 있다. 추가 질문은 전부 끝내지 않아도 결과로 돌아올 수 있다. 23이라는 숫자가 최적 길이나 측정 타당도를 입증한다는 뜻은 아니다.

문항 원문·선택지·v3.1 공유값·해석은 그대로 둔다. 기존 34개 사전의 배열을 지우거나 재배열하지 않으며, 아래 34개 설명은 이전 전체 흐름과 저장·공유 호환의 기준이다. 보지 않은 질문을 중간·건너뜀·비해당으로 자동 채우지 않는다. 새 결과는 실제 남긴 답만 세고, 미노출 질문을 미정 목록이나 빈 우선순위 카드로 늘어놓지 않는다. 두 사람 모두 보지 않은 항목은 비교 화면에서 제외한다.

자동 저장 schema 2는 기존 canonical 문항 위치와 `core`/`extra`/`full` 흐름을 구분한다. schema 1은 원래 34개 `full` 흐름으로 이어서 읽고, 실제 답이나 진행을 바꾸기 전에는 재저장하지 않는다. 마지막 저장부터 30일, 본인 답만 저장, 공유 동의·상대 답·메모 제외, 저장 끄기·삭제·탭 간 충돌 보호는 유지한다. 문서의 구현 계약은 테스트·배포 영수증을 대신하지 않는다. 현재 변경의 검증과 배포는 해당 PR·공식 영수증·운영 화면 확인으로 따로 기록한다.

## 현재 작업 트리의 공개 진입 구현: 2026-09-23 (v3.1 전용)

- **서술형은 결과의 「상대에게 보낼 말」 한 곳에만 둔다.** 문항마다 자유 입력을 받으면
  그 글이 공유 링크(`#a=...`)에 실려 이름·집안 사정·금액이 카톡과 브라우저 기록에 남고,
  전달된 링크는 회수할 수 없다. 저장하는 쪽으로 바꾸면 로그인·동의·삭제·AI 로그 원문
  비복제가 한 묶음으로 딸려오므로 그건 아모라 쪽 설계다. 결과의 편집 상자는 링크에도
  저장소에도 들어가지 않고 사용자의 클립보드로만 나간다.
- **선택지는 고른 사람을 탓하지 않는다.** 솔직한 답과 자책하는 답은 다르다. 같은 행동도
  「고르는 게 지쳐서 그냥 정해달라고 했다」로 쓰면 고르는 순간 자기 흠을 인정하는 문장이
  되고, 사람들이 그 답을 피한 만큼 축이 기운다 — **불편함과 편향은 같은 자리에서 생긴다.**
  `솔직히`·`그냥`·`통보`·`하소연`·`지쳐서` 같은 말과 `잘못`·`무책임`류 판정어는 테스트가 막는다.
- 현재 활성 문항은 `constants/weddingCodeV12.ts`, 진입 기준은 `scene/config.ts`다.
  `weddingCodeV07` 문항·검사는 이전 버전 기록이며 현재 문항의 이해도·정확도 근거가 아니다.
  새 판은 지금 나라면 고를 답으로 시제를 맞췄다. 받고 싶은 도움과 상대에게 건넬 말을
  질문과 결과에서 구분하며, 실제 행동이나 고정된 성격으로 자동 변환하지 않는다. C축은 최종 결정에 누가 참여하는지 묻는다.
  `scene/resultProfile.ts`는 선택한 장면들을 연결하고 그 근거를 인용한다. 모든 답은 펼쳐 볼 수 있다.
  v1.1·v1.2 연구 기여는 허용하지 않으며 기존 판의 수집·삭제 경계를 유지한다.
- 응답 설명 버전은 **`wedding-code-response-summary-v2`**다. 소수 답의 실제 문장도 보존하고,
  비교는 두 응답에 공통으로 답한 동일 장면을 기준으로 한다. 미응답은 일치로 세지 않는다.
- **아모라 도움 설정은 직접 확인 후 저장한다.** `profile/amoraBridge.ts`는 자동 설정값 대신
  답한 축에 대응하는 미선택 질문을 만든다. 사용자가 `decisionStart`, `workMode`, `familyOrder`,
  `supportOrder` 중 직접 고른 enum만 기존 개인 설정 API에 저장한다. 로그인된 사용자는 결과에서
  저장할 수 있고, 비로그인은 명시적인 계속 동작 후 `/settings/amora-style`에서 로그인·계정·변경
  내용을 다시 확인한다. 원래 20개 답과 인용문은 보내지 않고 고르지 않은 기존 설정은 보존한다.
  서버 성공 전에는 반영 완료로 표시하지 않으며 상대 설정·공동 합의는 변경하지 않는다.
- **실제 취향은 별도 선택형 화면에서 묻는다.** `/wedding-code/taste`의 새 진입 `wedding-taste-v2`는
  우선 주제 최대 2개, 분위기, 고른 주제의 세부 취향, 피할 것, 의견이 다를 때 처음 살펴볼 후보 범위를 최대 6개 질문으로
  확인한다. 기본 답·자유문·심리 점수는 없다. 미정·상관없음·계획없음·건너뜀을 구분하며,
  모두 건너뛴 결과는 공유·아모라 전달을 제공하지 않는다. v2 하객 수는 하객 없음과 1~49명을 구분한다.
  v1 링크는 기존 질문·유지 선호 표현으로 열고 상대도 같은 판으로 답한다. 서로 다른 판의 답을 합쳐 공유하거나 비교하지 않는다.
- 직접 취향은 공유 동의 후 고정 enum만 별도 버전 fragment에 넣는다. 먼저·나중에 답한 사람은
  응답 순서이며 계정 인증된 상대라는 뜻이 아니다. 두 사람이 모두 값을 고른 항목만 같은/다른
  선택으로 표시하고, 미정·미응답 등이 포함된 항목은 직접 확인할 부분으로 남긴다.
- **내 취향만 나만 상담의 초안으로 연결한다.** 본인이 이 화면에서 직접 입력한 선택을 검토하고
  요청할 때만 전달한다. 받은 링크의 답을 본인 것으로 자동 적용하거나 상대 답을 AI로 보내지 않는다.
  로그인·온보딩·상담 인계의 허용 enum만 현재 탭 `sessionStorage`에 최대 15분 보관하고 URL에는

  URL fragment(`#`)에 넣어 서버 요청과 referrer에서 제외하고, 이 경로의 페이지뷰·세션
  녹화도 끈다. 다만 전체 링크를 받은 사람은 답을 볼 수 있으므로 공유 전에 알린다.
- **2026-09-15 파운더 결정: 흐름 통계는 연다.** 경로 억제는 유지하고, 이름을 박아 둔
  `wedding_code_*` 이벤트만 `sanitizeWeddingCodeFunnelCapture`를 거쳐 보낸다 — 주소는 쿼리와
  `#`를 잘라 경로만, 속성은 버전·장면 순번·개수·자리 이름만 남긴다. 고른 답·코드·링크는
  싣지 않는다. 처리방침 제10조의 사전 고지 약속에 따라 2026-09-23부터 보낸다
  (`WEDDING_CODE_FUNNEL_ANALYTICS_EFFECTIVE_AT`). 이것은 응답 저장이나 연구 수집 재개가 아니다.
- **2026-09-16 파운더 결정: 답 익명 보태기(선택)를 연다.** 과거 `wedding_code_responses`
  (retired, 410)를 되살리지 않고 새 테이블 `wedding_code_research_contributions`와 새 경로
  `/api/wedding-code/research-contribution`을 쓴다. 명세 `56` §8.1·§9.1의 조건을 코드로 지킨다:
  기본값이 꺼진 동의·만 19세 확인, 받는 것(문항 판·답 기호·동의 판·시각)과 받지 않는 것(이름·
  연락처·계정·IP·링크·상대 답) 고지, 60일 TTL(보태기 RPC와 `ai-log-retention` 크론), 원문을
  저장하지 않는 HMAC 삭제 코드, 존재 여부를 드러내지 않는 삭제 응답, 삭제 tombstone 30일.
  - **받기와 지키기는 스위치가 다르다(2026-09-16 적대 검토 반영).** 지키기
    (`isWeddingCodeResearchStorageActive()` = 32자 이상 `WEDDING_CODE_RESEARCH_RECEIPT_SECRET`)가
    전용 보관기간 크론(`/api/cron/wedding-code-research-retention`)·삭제 API·삭제 폼·처리방침
    고지를 켠다. 받기(`isWeddingCodeResearchContributionOpen()`)는 지키기 + 플래그 +
    `WEDDING_CODE_RESEARCH_CONTRIBUTION_EFFECTIVE_AT`(처리방침 제10조 사전 고지, 2026-09-23) 이후에만
    카드·보태기 API를 켠다. 수집을 멈출 때는 플래그만 끄고, 비밀값은 마지막 보태기 후 60일까지
    지우거나 바꾸지 않는다.
  - 삭제 코드는 브라우저가 먼저 만든다(끊겨도 같은 코드로 재전송·삭제, 고유 제약으로 한 번만
    저장). 저장 시각은 날짜 단위로만 남기고, 보냈다는 분석 이벤트는 보내지 않는다 — 이름 없는
    답이 시각 대조로 한 기기에 이어지지 않게. tombstone은 같은 코드의 재저장을 막고 지운 코드의
    남은 행을 크론이 지운다. DB 전체를 백업 시점으로 되돌리면 tombstone도 함께 되돌아가므로
    그 경우의 재삭제는 약속하지 않는다.
  - 운영 순서: DB 레인 inspect → rehearse → apply(사람 승인) → 비밀값 → 플래그 → 재배포.
  - 이것은 문항 타당도 검증이 아니다. 아래 §4 인간 게이트(Candidate 6.3)는 그대로 미통과이며,
    보탠 답으로 유형·점수·궁합을 만들지 않는다.
- 과거 `?a=`·`?b=` 링크는 v0.6 호환을 위해 읽은 뒤 fragment 링크로 바꾼다. 최초 요청이
  이미 서버에 도달한 과거 링크의 노출을 되돌릴 수는 없으므로 신규 공유에는 쓰지 않는다.
- `profile/amoraHandoff.ts`와 `tasteHandoff.ts`의 임시 저장은 본인이 따로 확인한 도움 설정·취향의
  제한된 인계다. 장면 응답 DB 저장이나 Candidate 6.3의 browser storage 금지를 해제하지 않는다.
  취향 입력의 전용 DB 테이블·마이그레이션은 추가하지 않는다. 개인 상담에서 보내기를 누른 뒤에는
  기존 개인 대화의 처리·저장·AI 로그 경계를 따른다.

## 4. 재개 전 필수 인간 게이트

아래는 문서나 자동 테스트로 대신할 수 없으며 현재 모두 **미통과**다.

- 대상자 concept elicitation과 Candidate 6.3 반복 인지면접
- simulation/power 계획에 따른 파일럿과 별도 구조 검증
- 독립 동의한 실제 커플 최소 3쌍의 비난·도구화 검증
- 측정/설문 또는 관계·소비자 연구 전문가 검토
- 개인정보·소비자 안전 담당자의 서면 승인
- 별도 Production 재개 PR과 운영 승인

이 게이트가 끝나기 전에는 “검증됨”, “정확한 웨딩 성향”, “궁합”, “성공 예측”을 말하거나
Candidate 6.3 containment를 해제하지 않는다. 공개 장면 도구 역시 사람 검증 전에는
“유용성이 입증됨”, “최상”, “갈등을 예방함”이라고 말하지 않는다.
