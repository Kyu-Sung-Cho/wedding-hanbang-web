# WeddingCode Candidate 6.3 제품화 로드맵

상태: **COFOUNDER PRODUCT DIRECTION / 실행 순서 제안 / 운영 출시 승인 아님**
작성: 2026-07-18
대상 exact-version: `wedding-code-candidate6-research.3`

## 1. 코파운더 판정

WeddingCode의 10-star 경험은 “정확해 보이는 유형 이름”이 아니라 다음 세 가지를 동시에 주는 것이다.

1. 내 답을 평가받는 불편 없이 결혼 준비의 실제 장면을 쉽게 고른다.
2. 끝나자마자 오늘 연인과 꺼낼 수 있는 한 문장을 얻는다.
3. 답을 노출하지 않고도 “우리도 같이 해보자”고 안전하게 초대할 수 있다.

현재 Candidate 6.3은 이 방향을 시험할 `M0` 후보이지 소비자용 진단검사가 아니다. 한국 예비부부의
exact wording 이해, 구조, 공정성, 실제 도움과 공유 후회를 검증하기 전에는 점수·유형·궁합·개인 결과를
열지 않는다.

## 2. 목표 소비자 여정

### A. 발견

- 한 줄 약속: “결혼 준비, 오늘 어떤 말부터 꺼내면 편할지 찾아봐요.”
- 완료 시간을 미리 추정해 쓰지 않고 실제 사용성 관찰 뒤 안내한다.
- 로그인·연락처·연인 초대를 시작 조건으로 두지 않는다.

### B. 장면 선택

- 실제 사람 검증 뒤 정보량이 높은 8~10개 이하 장면만 남긴다.
- 한 화면에서 핵심 다섯 답을 동시에 비교한다.
- `상황 차이`, `비해당`, `경험 없음`, `넘기기`를 숨은 결측이 아니라 선택 가능한 의미로 보존한다.
- 짧은 chapter 전환, 선택 체크, 150~160ms press feedback으로 리듬을 만들되 정답·연승·보상 점수는
  만들지 않는다.

### C. 즉시 보상

- 응답을 몰래 해석한 결과 대신 사용자가 직접 `대화 카드` 한 장을 고른다.
- 카드는 한 문장 질문과 10분 안에 해볼 수 있는 작은 행동으로 끝낸다.
- “당신은 이런 사람”이 아니라 “오늘 이 대화를 먼저 해볼까요?”라고 말한다.

### D. 안전한 공유

- 공개/친구 공유 기본값은 답·점수·예산·가족·업체가 없는 초대 카드다.
- 초대 링크는 상대가 답해야 내 결과가 열린다는 강제 호혜를 쓰지 않는다.
- 연인 공유는 각자 독립 동의, 공개 범위, 만료, 철회, 삭제를 선택한다.
- 공유율만 보지 않고 오해, 후회, 삭제, 압박, 지원 요청을 함께 본다.

### E. 제품 적용

- 아모라·예산·일정·업체 기능에는 자동 반영하지 않는다.
- 근거가 남은 관찰만 “이렇게 도와드릴까요?”라는 제안 diff로 보여준다.
- 사용자가 변경 내용을 확인한 뒤 적용하고, undo와 감사 로그를 제공한다.
- WeddingCode 자체 문항/결과 생성에는 LLM을 쓰지 않는다. 결정적 버전 문항과 규칙을 사용해 비용과
  재현성 위험을 줄인다.

## 3. 재미를 만드는 원칙

허용:

- “장소 고르기”, “작은 준비 일이 쌓인 날”처럼 내가 겪을 법한 장면
- 한 번 탭하면 분명히 보이는 체크와 부드러운 전환
- 진행률보다 “장면 1”, “마지막 한 장” 같은 이야기 리듬
- 사용자가 직접 고른 대화 카드와 답 없는 초대 카드
- 새로고침하면 사라지는 로컬 연구 경험의 명확한 안내

금지:

- 희귀 유형, 상위 퍼센트, 가짜 참여 수, 정확도 배지
- 결혼 성공·이혼·궁합 예측
- 상대 답을 봐야 내 결과가 열린다는 압박
- confetti나 연속 정답처럼 특정 응답을 보상하는 장치
- 답·예산·가족·업체 정보를 OG, 알림, 로그, analytics에 넣는 것

## 4. 단계별 출구 조건

| 단계 | 할 일 | 다음 단계로 가기 위한 증거 | 아직 금지 |
|---|---|---|---|
| `R0` | 실제 장면 concept elicitation | 빠진 P0/P1 장면과 subgroup 공백 기록 | 문항 정확성 주장 |
| `R1` | 적격성 screener를 거친 `P1/P2/P3` 반복 인지면접 | exact item별 assigned/administered/eligible/non-applicable, 대체, 이해·대안 해석·응답과정 ledger | 점수·유형·공유 |
| `R1-UX` | 실제 320/390 기기, screen reader, 200% zoom | 첫 행동·스크롤·오탭·중도이탈·불편 관찰 | 완료시간 마케팅 |
| `R2` | 사전등록 파일럿 | category 기능, 구조, local dependence, subgroup 공백 | 규준·cutoff·4글자 코드 |
| `R3` | 직접 선택 카드와 답 없는 초대 실험 | 실제 사용, 오해·후회·압박·철회 결과 | 원응답 공개 viral loop |
| `R4` | 독립 동의 커플 검증 | 도움과 위해를 함께 검토한 승인 기록 | 자동 커플 평가 |
| `Launch` | 별도 운영 재개 PR | 개인정보·법적·측정·접근성·운영 승인과 rollback | 게이트 우회 |

고정 숫자 하나로 자동 PASS하지 않는다. 각 라운드는 `통과`, `관찰했지만 모름`, `미평가`를 분리한다.

## 5. 가장 먼저 검증할 제품 가설

1. 8~10개 이하로 줄였을 때도 “내 결혼 준비 이야기 같다”는 느낌이 남는가?
2. 다섯 핵심 답을 동시에 보이면 위치 편향과 문항당 스크롤이 줄어드는가?
3. 대화 카드가 유형 결과보다 실제 7일 내 대화 시작에 더 도움이 되는가?
4. 답 없는 초대 카드가 원응답 공개 오해 없이 공유하고 싶은가?
5. 연인이 참여하지 않아도 혼자 얻은 가치가 충분한가?
6. 아모라 제안 diff와 undo가 자동 반영보다 편안하고 신뢰되는가?

## 6. 현재 구현과 남은 사람 작업

구현됨:

- 21개 `M0` item pool과 item별 source/context/limitation linkage
- Form A/B endpoint orientation과 `ES_FIRST/AS_FIRST` 독립 배정
- SI core 후 contextual block
- 인지면접용 `P1/P2/P3` 8~10문항 패널
- recording/vendor-assisted/partner-collaboration 적격성 screener, 같은 theme 대체, 대체 불가 차단,
  item별 노출 카운팅 계약
- 한 화면 5답 비교, 명시적 다른 답, 모바일 safe-area/단일 scroll
- 로컬 zero-I/O, fake PostHog/Sentry 0건, 운영 artifact 비포함

사람이 해야 함:

- 실제 예비부부 concept elicitation과 인지면접
- `CP3`, `ES1`, `DS3`, `DS4` rewrite/drop/contextual 판정
- 전문가 내용·관계 위해·개인정보·접근성 검토
- 데이터 수집 동의·TTL·삭제·backup re-delete 설계와 승인
- 파일럿·공정성·제품 consequence 검증

현재 운영 WeddingCode의 안내-only, API `410 Gone`, DB write fence는 그대로 유지한다.
