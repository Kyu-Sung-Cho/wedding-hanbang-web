## 1. 한 문장 정의

WeddingCode는 사람을 고정된 성격이나 궁합으로 판정하는 검사가 아니라, **실제 결혼 준비 장면을
짧고 편하게 돌아보고 오늘 연인과 어떤 대화부터 꺼내면 좋을지 찾는 도구**다.

장기적으로는 “내 웨딩코드가 뭐지?”라고 기억하고 공유할 수 있는 문화적 자기소개 토큰을 지향한다.
그러나 재미있는 이름, 4글자 코드, 형용사와 동물 캐릭터는 **표현층**이다. 그것이 정확한 측정의
근거나 채점 원천이 되어서는 안 된다.

## 2. 우리가 처음부터 원한 것

파운더가 반복해서 제시한 요구를 제품 언어로 정리하면 다음과 같다.

1. **쉽고 짧아야 한다.** 별도 설명 없이도 실제 예비부부가 바로 이해해야 한다.
2. **현실적이어야 한다.** 추상적인 성격 질문이 아니라 실제 결혼 준비에서 겪는 장면이어야 한다.
3. **재미있어야 한다.** 끝까지 하고 싶고, 상대에게 보내고 싶고, 결과를 기억하고 싶어야 한다.
4. **믿을 만해야 한다.** 모든 문항과 결과 주장에 “왜 이렇게 물었는가”를 설명할 수 있어야 한다.
5. **낙인찍지 않아야 한다.** 비용, 가족, 감정, 분업, 도움 선호 어느 쪽도 더 성숙하거나 더 좋은
   배우자로 보이면 안 된다.
6. **실제로 도움이 되어야 한다.** 결과를 읽고 끝나는 테스트보다 대화, 일정, 예산, 업체 비교,
   아모라 케어로 안전하게 이어져야 한다.
7. **문화적 자기소개 토큰이 될 수 있어야 한다.** 장기적으로는 선보는 자리에서도 “웨딩코드가
   뭐예요?”라고 물을 만큼 기억되고 공유될 수 있어야 한다.

이번 작업 대화에서 예시로 제시된 “신사적인 코끼리”처럼 **긍정적인 형용사 + 동물**로 기억하게 만드는
방향은 살아 있는 표현 가설이다. 다만 현재 승인된 동물, 유형 수, 코드 체계, 분류식은 없다. 실제 구조와
재검사 안정성이 확인되기 전에 캐릭터부터 확정하면 재미가 근거를 앞서게 된다.

## 3. 제품 철학

WeddingCode는 웨딩한방의 원칙을 다음 순서로 적용한다.

### 3.1 신뢰가 바이럴보다 먼저다

- 답을 공개해야 결과를 볼 수 있게 만들지 않는다.
- 가짜 참여 수, 희귀도, 정확도 배지, 궁합 점수로 공유를 유도하지 않는다.
- 광고주나 업체 이해관계가 문항, 결과, 아모라 적용을 바꾸지 않는다.
- 안전상 반드시 해야 할 행동을 “특정 성향의 선택”으로 점수화하지 않는다.

### 3.2 재미와 정확성은 같은 층이 아니다

- **정확성층:** 장면 근거, 문항 이해, 응답 과정, 구조, 공정성, 사용 결과를 검증한다.
- **도움층:** 사용자가 직접 대화 카드와 다음 행동을 고른다.
- **표현층:** 충분한 근거가 생긴 뒤 코드, 이름, 형용사, 동물, 공유 카드로 기억하기 쉽게 만든다.

검증 전 먼저 만들 수 있는 표현은 분류와 무관한 공통 마스코트나 사용자가 직접 고른 장면 카드까지다.
코드·형용사·동물 **유형**은 표현층 승인 조건을 통과한 뒤에만 만들며 정확한 진단처럼 판매하지 않는다.

### 3.3 사람을 설명하는 대신 다음 대화를 돕는다

현재 가장 중요한 질문은 다음이다.

> **오늘 둘이 어떤 말을 먼저 꺼내면 결혼 준비가 조금 편해질까?**

제품 가치 흐름은 다음과 같다.

```text
실제 결혼 준비 장면
  → 사용자가 편한 답을 직접 선택
  → 사용자가 오늘 필요한 대화 카드 직접 선택
  → 원답 없는 안전한 초대
  → 각자 독립 동의한 커플 대화
  → 미리보기·확인·되돌리기가 있는 제품 적용
```

### 3.4 메모리는 커플의 자산이다

WeddingCode가 아모라의 장기 기억과 연결되는 것은 장기적으로 큰 가치가 있다. 그러나 현재 연구
답변을 몰래 프로필로 만들거나 일정·예산·업체에 자동 반영하지 않는다. 사용자가 무엇이 바뀌는지
미리 보고 승인했을 때만 최소한의 관찰을 적용하며, 철회와 되돌리기를 제공한다.

## 4. WeddingCode가 다루는 범위와 다루지 않는 범위

### 현재 연구하는 범위

- 중요한 선택에서 어떤 이야기부터 꺼내면 편한지
- 한 준비 행동을 같이 할 때 어떤 영향이 있는지
- 합의한 담당자에게 방식과 순서를 맡길 때 어떤 영향이 있는지
- 합의한 시점에 진행 상태를 같이 확인할 때 어떤 영향이 있는지
- 정서적 도움과 실행 도움의 구체적 행동이 어떤 영향을 주는지
- 가족·지인 등 의견을 듣기로 합의한 상황에서 어디서 대화를 시작하면 편한지
- 문항 뒤에 사용자가 직접 고른 대화 카드가 실제 대화에 도움이 되는지

### 현재 다루지 않는 범위

- 사람 전체의 성격 또는 모든 결혼 성향
- 관계 만족도, 사랑의 크기, 책임감, 성숙도
- 궁합, 결혼 성공 가능성, 이혼 또는 갈등 예측
- 특정 업체의 품질·안전 보장
- 예산 수준이나 가족 관여도를 이용한 사람 평가
- 임상·심리 진단, 관계 상담, 법률 자문
- 광고 세그먼트나 업체 추천을 위한 비밀 프로파일링

### 현재 핵심 사용자와 미래 확산 사용자는 분리한다

- **현재 1차 연구 대상:** 실제 결혼을 준비 중이거나 구체적인 준비 장면을 확정한 커플
- **미래 확산 대상:** 결혼 전 연애·맞선 단계에서 자기소개 토큰을 원하는 사람

현재 문항은 실제·확정된 준비 경험을 전제로 한다. 맞선·연애 사용자를 같은 문항에 넣으면 비해당과
가정 응답이 늘어 “정확한 자기소개 토큰” 약속이 깨질 수 있다. 미래 확산 대상은 별도 가정형 장면,
별도 exact-version, 별도 사람 검증이 필요하다.

과거 12개 구성개념은 결혼 준비의 넓은 문제 지도를 만드는 데 도움을 주었지만, 현재 Candidate 6.3의
7개 연구 테마와 같은 개념도 아니고 검증된 잠재축도 아니다.

## 6. 설계가 바뀐 과정

### Candidate 4: 넓고 재미있었지만 너무 빨리 점수화했다

- 12개 구성개념, 4개 공개축 후보, 16개 forced-choice 문항을 설계했다.
- 개인 축 점수, confidence band, 커플 overlap, 공유 카드와 유형 표현까지 구현 흔적이 있다.
- 그러나 안전상 우월한 행동과 개인 선호가 같은 선택지에서 경쟁했다.
- 한 선택지가 여러 구성개념 점수를 동시에 올렸고, 축별 노출과 가중치가 달랐다.
- 합성 50,000응답 구조 감사에서도 일부 축이 중립적으로 분포하지 않았다.
- 사람 검증 없이 정밀한 퍼센트와 유형처럼 보일 위험이 커서 전면 retired 처리했다.

### Candidate 5: 단일축과 안전 분리를 시도했다

- 문항 하나를 한 연구축에만 연결했다.
- 안전 행동을 비점수 도움 모듈로 분리했다.
- Form A/B 위치 보완, 별도 결측, 무점수 연구 경계를 만들었다.
- 그러나 네 방향 문장이 반복적이고, 행동·순서·가정이 여전히 복잡했으며 현재 제품 방향보다
  “축을 만들기 위한 문항”에 가까웠다.
- Candidate 6.3이 이를 대체했다.

### Candidate 6.3: 한 행동, 균형 응답, 직접 선택 보상으로 재설계했다

- 21개 문항 후보를 7개 연구 테마로 분리했다.
- 모든 문항을 `M0`, `scoreEligible:false`로 고정했다.
- 같은 문항 안에서 여러 행동을 묶지 않고 한 행동의 영향을 묻는다.
- 중앙값과 네 종류의 비서열 응답을 보존한다.
- 결과를 추론하지 않고 사용자가 대화 카드를 직접 고른다.
- 로컬 무저장·무전송 환경과 운영 artifact 차단까지 코드로 강제했다.

### 우리가 얻은 핵심 교훈

1. 현실적인 장면이라고 해서 그 문항이 사람의 안정적 성향을 측정하는 것은 아니다.
2. 소비자 안전 행동은 취향 점수가 아니라 모두에게 제공할 안전 카드여야 한다.
3. “좋은 파트너처럼 보이는 답”이 생기면 결과가 아니라 문항이 잘못된 것이다.
4. 재미는 희귀도와 궁합 수치가 아니라 “나도 겪을 법한 장면”, 리듬, 직접 선택, 안전한 공유에서
   만들어야 한다.
5. 코드 테스트가 통과해도 사람 타당도가 생기지 않는다.

| `AS` | 한 가지 실행 지원 행동이 미치는 영향 | `ES`의 반대가 아님 | 금지 |
| `SI` | 같은 한 사람/집단의 의견을 듣는 장면에서 대화를 시작하는 방식 | contextual tool | 총점·유형 영구 제외 후보 |

이 테마들은 연구 편의를 위한 이름이다. 현재 잠재차원, 척도, 유형, 성향 코드가 아니다.

### 7.2 네 개의 이야기 장

1. **선택의 첫 단추:** 최종 비교에서 어느 이야기부터 시작할지
2. **우리의 팀플:** 함께 하기, 맡기기, 확인하기의 구체적 행동
3. **필요한 도움:** 같은 장면에서 정서·실행 도움 행동의 영향
4. **주변 의견 다루기:** 의견을 듣기로 합의했을 때의 시작점

### 7.3 응답 구조

#### `DS`와 `SI`: 유효 중앙이 있는 다섯 범주

- 첫 번째 이야기부터 시작하고 싶어요
- 첫 번째 이야기를 조금 먼저 꺼내고 싶어요
- 두 이야기를 나란히 시작하고 싶어요
- 두 번째 이야기를 조금 먼저 꺼내고 싶어요
- 두 번째 이야기부터 시작하고 싶어요

#### `JI/OA/CP/ES/AS`: 방해부터 도움까지의 다섯 범주

- 오히려 많이 방해돼요
- 조금 방해돼요
- 도움도 방해도 거의 없어요
- 조금 도움이 돼요
- 많이 도움이 돼요

#### 모든 문항의 별도 비서열 응답

- `depends`: 상황마다 많이 달라져요
- `not_applicable`: 지금 내 준비에 해당하지 않아요
- `no_experience`: 비슷한 경험이 없어 가늠하기 어려워요
- `skip`: 이 질문은 넘길게요

이 네 값은 중앙값, 0점 또는 하나의 결측으로 합치지 않는다.

### 7.4 Form과 순서

- Form A/B는 양극 문항의 의미 위치만 보완한다.
- `ES_FIRST`/`AS_FIRST`는 Form과 독립적으로 지원 문항 순서를 바꾼다.
- SI는 모든 core 문항 뒤의 contextual block에만 놓는다.
- Form, support order, SI 위치를 하나의 이름이나 점수 규칙으로 섞지 않는다.

### 7.5 적격성

R1 인지면접 전 다음 세 장면을 각각 `eligible/not_applicable/unsure`로 확인한다.

- `recording`: 사진·영상 등 기록 옵션을 실제로 비교하거나 결정할 장면이 있는가
- `vendor-assisted`: 업체·플래너를 비교·계약·이용할 장면이 있는가
- `partner-collaboration`: 파트너와 결정·역할·도움 방식을 조율할 장면이 있는가

비적격 문항은 같은 테마의 적격·미배정 문항으로만 대체한다. 대체할 수 없으면 전체 투여안을
`incompatible`로 막고 문항을 0개 반환한다. 다른 테마 문항으로 조용히 바꾸거나 부분 패널로 강행하지
않는다.

### 7.6 전체 UI와 실제 연구 투여의 차이

- 로컬 전체 흐름: SI 적용 여부에 따라 19개 또는 21개, **모바일 UI stress preview**
- 실제 R1: 참여자당 core 8개 + 적용 가능한 SI 1~2개, 총 8~10개
- `P1/P2/P3`: 노출을 분산하기 위한 운영 패널이지 동등한 검사 form이 아님

세 패널을 같은 수로 배정해도 모든 exact item의 노출 횟수가 같아지지는 않는다. 일부 문항은 패널 한
곳에, 일부는 두 곳에 들어 있다. 의도적인 과표집이라면 이유와 패널 배정 비율을 사전등록하고, 아니라면
item별 목표 노출량을 기준으로 패널 비율을 조정해야 한다.

### 7.7 현재 연구 배정 원장 계약과 남은 공백

`planCandidate6InterviewAssignment`와 tracking row는 다음을 각각 보존한다.

- opaque RFC 4122 assignment UUID와 exact-version
- Form/orientation, support order, rotation, panel
- 전체 eligibility screener snapshot과 stakeholder applicability
- 요청 원문항, 최종 배정문항, replacement item, 원문항 적격성
- assigned/administered/eligibility-at-assignment/response-disposition의 서로 다른 상태

summarizer는 runtime에서 잘못된 enum·버전·응답 조합, panel 불일치, screener에서 파생한 적격성 불일치,
cross-theme/누락 substitution lineage, assignment metadata 혼합, 중복
`(exactVersion, assignmentId, itemId)` row를 거부한다. 이로써 과거의 중앙 원장 P1은 코드 수준에서
해소됐다.

그러나 template은 **저장하지 않으며 수집 가능한 완성 연구 원장이 아니다.** 동의, 최소 수집,
TTL·삭제·철회·backup re-delete, 실제 연구 도구 연동이 아직 없다. 또한 rotation은 한 배정 안의
결정적 대체 규칙일 뿐 전체 표본의 item별 노출 균형을 보장하지 않으므로 패널 배정 비율과 과표집
이유를 사전등록해야 한다.

## 10. 사용자 여정과 UX

### 현재 로컬 연구 여정

1. **인트로:** 무엇을 하는 화면인지, 저장하지 않음, 정답·점수·유형·궁합이 없음을 안내한다.
2. **주변 의견 적용 여부:** `applicable/not_applicable/unsure`를 직접 고른다.
3. **장면:** 장면 이름, 전제, 질문, 다섯 핵심 답, 네 별도 답을 본다.
4. **이동:** 답을 고른 뒤에만 다음으로 가며 이전 답을 다시 볼 수 있다.
5. **마지막 한 장:** 세 대화 카드 중 사용자가 직접 고른다.
6. **완료:** 대화 질문과 10분 행동만 보여주고 처음부터 다시 볼 수 있다.

### 목표 소비자 여정

1. 발견: 로그인·연락처·연인 초대 없이 시작
2. 장면 선택: 사람 검증 뒤 8~10개 이하로 축약
3. 즉시 보상: 직접 고른 대화 카드
4. 안전한 공유: 답·점수 없는 초대 카드
5. 연인 참여: 각자 독립 동의
6. 제품 적용: 변경 미리보기 → 확인 → 실행 → undo

### 현재 UX의 알려진 제품 공백

- 19/21개 전체 흐름은 연구용 stress preview라 소비자용으로 너무 길 수 있다.
- 대화 카드를 마지막에 별도로 고르기 때문에 “앞에서 왜 답했지?”라는 보상 단절이 생길 수 있다.
- 다음 실험에서는 사용자가 **자기가 답한 장면 중 가장 이야기하고 싶은 장면 하나를 직접 선택**하고,
  그 선택이 대화 카드로 이어지는 투명한 다리를 검증한다. 알고리즘 추론은 하지 않는다.
- 답 없는 초대 카드는 안전하지만 자기표현성이 약한 일반 광고 카드로 느껴질 수 있다.
- 실제 완료시간, 재미, 공유 의향, 공유 후회 데이터는 아직 없다.
- 영향 응답의 시각 문구와 접근성 라벨은 모두 canonical 문구 “도움도 방해도 거의 없어요”로 통일했다.
  실제 사람이 이를 중립 영향으로 이해하는지는 인지면접에서 계속 확인한다.
- `depends/not_applicable/no_experience/skip`은 데이터 의미상 분리돼 있지만 현재 화면에서는 기본으로
  접힌 `<details>` 안에 있다. 핵심 다섯 답으로 사용자를 밀지 않는지 R1에서 발견률을 측정하거나 처음부터
  노출하는 안을 비교해야 한다.

### 편안함을 만드는 UI 원칙

- 한 화면의 주 행동은 하나만 둔다.
- 답을 고르기 전 다음 버튼은 비활성화한다.
- 다섯 핵심 답은 한 화면에서 비교할 수 있게 한다.
- 맞는 답이 없을 때 네 이유를 데이터상 숨은 결측으로 합치지 않는다. 다만 현재 접힌 UI에서 실제로
  발견되는지는 아직 검증하지 않았다.
- 진행 숫자는 보여주되 정답·연승·레벨처럼 만들지 않는다.
- 완료 시간은 실제 관찰 전 추정해 마케팅하지 않는다.
- press feedback은 약 150~160ms의 짧은 리듬만 사용한다.
- confetti, 희귀 배지, 퍼센트, 경쟁 요소로 특정 답을 보상하지 않는다.

### 접근성·모바일 계약

- 320px/390px 기준 단일 scroll과 safe-area
- 최소 48px 터치 영역
- `dvh` 기반 높이와 고정 하단 행동 영역
- 질문 전환 시 제목으로 프로그램 초점 이동
- `focus-visible`, 키보드, progressbar, 하나의 radio group 낭독
- `prefers-reduced-motion`, 200% zoom, screen reader 검증 대상
- 작은 화면에서 아래 답을 발견할 수 있도록 방향 안내

## 11. 코드·형용사·동물 결과의 장기 설계

### 현재 판정

- 현재 승인된 코드, 유형 수, 동물, 형용사, 분류 경계는 **0개**다.
- 현재 7개 테마를 바로 4글자나 16유형으로 압축할 근거가 없다.
- “신사적인 코끼리” 같은 표현은 원하는 기억 방식의 예시이지 과학적 분류가 아니다.

### 제품화가 가능해질 때의 층

1. **관찰층:** “이번에 답한 네 장면 중 세 장면에서 조건 이야기를 먼저 골랐어요.”
2. **맥락층:** “준비 단계와 장면에 따라 달라질 수 있어요.”
3. **도움층:** 사용자에게 맞는 대화 카드와 다음 행동
4. **표현층:** 사용자가 원할 때만 긍정적 코드·형용사·동물로 기억

### 표현층 승인 조건

- 충분한 문항이 사람 검증을 통과
- 구조가 실제 데이터에서 반복됨
- 재검사에서 표현이 지나치게 흔들리지 않음
- subgroup별 오독·불공정 검토
- 모든 이름이 우열·성역할·돈·효도 낙인 테스트 통과
- 사용자가 설명을 읽지 않고도 진단·궁합으로 오해하지 않음
- “이름이 재미있다”와 “내 결혼 성향을 정확히 맞힌다”를 별도로 측정

유형 검증 전 브랜드 재미가 필요하면 모든 사용자에게 공통인 **중립 마스코트**를 먼저 쓸 수 있다.
마스코트는 분류 결과가 아니라고 명시하고, 색각·스크린리더 대체 표현과 캐릭터 IP 권리를 함께
검토한다.

구조가 4축으로 나오지 않으면 4글자를 포기하거나 글자 수와 표현 방식을 바꾼다. 이미 만든 캐릭터를
살리기 위해 데이터 구조를 억지로 맞추지 않는다.

## 12. 공유와 커플 경험

### 첫 공유물

첫 공개/친구 공유는 **원응답이 없는 초대 카드**다.

- 답, 점수, 예산, 가족, 업체, 관계 평가를 넣지 않는다.
- 상대가 답해야 내 결과가 열린다는 강제 호혜를 쓰지 않는다.
- 가짜 분포나 희귀도를 넣지 않는다.
- 공유하지 않아도 개인이 얻는 가치가 충분해야 한다.

### 연인 공유

- 발신자와 수신자가 각각 독립 동의한다.
- 상대가 볼 내용, 공개되지 않는 내용, 만료일을 exact preview로 보여준다.
- 공개 범위, 철회, 만료, 삭제를 직접 고른다.
- 한쪽이 철회·삭제하면 파생 뷰와 링크를 닫는다.
- 돈·가족·업체·안전 행동을 자동 하이라이트하지 않는다.
- 같음/다름 개수, overlap %, 궁합 점수를 만들지 않는다.

### 평가할 결과

공유율만 보지 않는다.

- 오해, 후회, 삭제, 압박, 통제, 비난
- “상대가 참여하지 않으면 미안하다”는 느낌
- 대화를 실제로 시작했는지
- 공유 뒤 지원 요청이나 위해가 있었는지

현재 이 기능들은 제품 방향만 있으며 Candidate 6.3에 구현되지 않았다.

## 15. 사람 검증 계획

### R0: 문항을 보여주기 전 실제 장면 찾기

- 시작 12명, 필요하면 6명 단위 top-up
- 준비 단계, 정식/소규모/무예식·미정, solo/joint/planner, stakeholder low/high/none,
  접근성·신경다양성 등 공백 기록
- 연속 2회 인터뷰에서 새 P0/P1 장면이 없을 때만 “이번 라운드 잠정 포화”로 기록
- 포함하지 못한 집단은 `not assessed`

### R1: 반복 인지면접

- 참여자당 최대 8~10개 item
- final exact wording의 각 core item을 관련 참여자 최소 10명이 봄
- 양극 endpoint orientation별 최소 5명
- 최소 2개 반복 라운드
- 문구 변경 시 exact-version 증가, 이전 관찰을 새 문구에 합치지 않음
- 이해, 전제, 떠올린 경험, 행동 수, 선택 이유, 정답감, 오남용을 probe

### R1-UX: 실제 사용성

- 320px/390px 실제 기기 또는 동등 환경
- screen reader, 키보드, 200% zoom, 저시력, 고대비, reduced motion
- 첫 행동까지 거리, 스크롤, 오탭, 중도 이탈, 불편 관찰
- 마지막 카드가 추론 결과가 아니라 직접 선택임을 이해하는지 확인

### R2: 정량 파일럿

- R0/R1에서 살아남은 문항만 사용
- 표본 크기는 Monte Carlo simulation과 분석계획으로 정함
- 독립 EFA/CFA 표본, ordinal estimator, threshold, local dependence, category functioning 검토
- `JI/OA/CP`, `ES/AS`, DS 구조의 대안 모형을 비교
- SI는 factor, reliability, 총점에서 제외
- total WeddingCode score를 만들지 않음
- 부족한 표본은 `untested`

### R3: 제품 효용과 공유

- 직접 고른 대화 카드를 7일 안에 실제 사용했는지
- 도움, 불편, 비난, 압박, 회피가 있었는지
- 답 없는 초대가 원응답 공개로 오해되지 않는지
- 공유 증가와 함께 후회·삭제·강요도 같이 측정

### R4: 독립 동의 커플 검증

- 두 사람이 각각 독립 동의
- 대화 도움과 위해를 함께 관찰
- 커플 평가, 같음/다름 점수, 자동 결과 금지
- 공개 범위·만료·철회·삭제를 이해하는지 확인

### Launch

- 별도 운영 재개 PR
- 개인정보·법적·측정·접근성·운영 승인
- exact-version 호환, rollback, API/DB fence 재폐쇄 리허설

고정 숫자 하나로 자동 PASS하지 않는다. 각 항목은 `통과`, `관찰했지만 모름`, `미평가`를 분리한다.

## 16. 즉시 중단·개정 조건

다음 중 하나면 출시 속도나 공유율과 관계없이 멈춘다.

- 한 번의 심각한 낙인, 비난, 통제, 답 강요, 궁합·성공 예측 해석

- 응답이 예산·마감·숙련·성역할·관계 권력·장애/신경다양성에 지배됨

숫자는 자동 실패·통과가 아니라 review trigger다. 한 번의 심각한 위해는 작은 표본이라는 이유로

### 유출 방지

- route 파일은 커밋하지 않고 실행 중에만 만들며 종료 시 삭제

- `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet`
- 차단 응답 `private, no-store`

공식 wrapper 대신 raw `next dev` 또는 `next build`를 직접 실행하면 lock과 검사를 우회할 수 있다.
개발·CI·build 문서와 명령은 반드시 패키지 wrapper를 사용한다.

### 운영 DB fence

`20260714104000_disable_wedding_code_collection.sql`은 적용 계약상 다음을 수행한다.

- `PUBLIC`, `anon`, `authenticated`, `service_role`의 table/column 권한 회수
- 과거 insert/pair RPC 모든 overload 제거
- 모든 과거 RLS policy 제거
- `CHECK (false) NOT VALID`로 새 `INSERT`·`UPDATE` 거부
- 적용 당시 확인한 과거 13행은 별도 보존·삭제 결정 전까지 읽거나 변경하지 않음

RLS 하나만으로 service-role 쓰기를 막았다고 간주하지 않는다.

이번 worktree에는 live Supabase link 정보가 없어 현재 운영 행 수, 권한, migration drift를 다시 조회하지
못했다. migration 주석만 근거로 `supabase db push`, baseline normalization 또는 migration repair를
실행하지 않는다.

WeddingCode의 영구 collection fence와 전역 임시 `PRODUCTION_WRITE_FENCE_ENABLED`는 별개다. 새 전역
write-fence probe는 현재 운영에서 `404`였으므로 전역 fence 활성 여부는 이 문서에서 완료로 주장하지

## 25. 최종 판정

WeddingCode는 이제 “문항을 많이 만들어 둔 테스트”가 아니라 다음을 갖춘 연구·제품 시스템이 됐다.

- 파운더 비전과 제품 원칙
- 21개 exact-version 문항 후보
- 문항별 출처·대안 해석·폐기 기준
- 유효 중앙과 네 별도 비서열 응답
- Form·순서·적격성·substitution lineage를 보존·검증하는 tracker — 저장·동의 연구 원장은 아직 미구현
- 편안한 모바일 로컬 프로토타입
- 직접 선택 대화 카드
- 무저장·무전송·운영 artifact 격리
- 단계별 사람 검증과 운영 재개 게이트
- 안전한 공유와 아모라 적용 방향

그러나 아직 갖추지 못한 가장 중요한 한 가지가 있다.

> **실제 한국 예비부부가 이 문항을 의도대로 이해하고, 유용하고 편안하게 느끼며, 반복했을 때도
> 의미 있는 구조가 남는다는 사람 근거**

따라서 현재 평가는 다음과 같다.

- **제품 철학과 안전 경계:** 잘 갖춰짐
- **연구 후보 문항과 코드 품질:** 정적 계약·격리·원장 metadata 검증은 통과했지만 사람 타당도와 승인된 저장 원장은 없음
- **로컬 연구·운영 artifact 격리:** 검증됨. live DB drift와 과거 Git 식별자 후속은 미완료
- **소비자용 검사 신뢰도·타당도:** 아직 없음
- **4글자·형용사+동물·궁합·커플 결과:** 아직 만들면 안 됨
- **다음 우선순위:** 더 많은 코드가 아니라 실제 사람 검증
