# 웨딩코드 v4 문항 깊이 감사와 차기 판 설계 기준

작성: 2026-10-04 · 상태: **편집 감사 / 사람 검증 전 / 현행 문항·채점 미변경**  
대상: `v4.0-tendency`의 68문항 원본 `2026-09-29_v40_items.json`, `weddingCodeV40.ts`, `v40/score.ts`, `v40/quote.ts`, `v40/couple.ts`

## 먼저 내리는 판정

v4는 4주제 × 4측면의 채점 문항 64개와 마지막 자기 선택 4개, 여러 입력 형식을 이미 갖췄다(E). 그러나 문항 수와 형식 다양성만으로 **결혼 준비의 내면을 정확히 알아낸다**고 말할 수 없다. 네 글자는 돈·준비·가족·지원 장면에 준 답을 설계자가 정한 양극과 가중치로 합친 결과다. 실제 사람의 문항 이해, 재검사 안정성, 축 구조와 대화 효과는 아직 확인하지 않았다(E: [`v4 계약`](./2026-09-29_v40_tendency_contract.md) §2·§15, 사람 확인 0건). 따라서 이 감사의 목적은 사용자에게 새로운 성격 이름을 붙이는 것이 아니라, **선택한 행동·그때 지키려던 것·상황이 달라지면 바뀌는 조건**을 더 잘 드러내는 문항과 결과 계약을 만드는 것이다.

감사 시작 시 기준 브랜치의 기본 `/wedding-code`는 v3.1이고 v4는 명시 주소에서만 열렸다(E: 당시 `app/wedding-code/entry.ts`). 이 작업 브랜치에서는 기본 입구를 v4로 바꾸었지만 공개 배포 여부는 별도다. 기존 v3.1의 같은 글자 중복 문제를 v4의 고유한 여덟 글자로 피하더라도 문항 자체의 결함과 사람 검증 부재는 남는다.

## 차기 판의 문항 구조

현재 68문항과 6형식은 **분량·화면 형식의 출발점**으로 쓸 수 있다. 같은 틀을 반복해서 80~100문항으로 늘리는 것은 깊이의 증거가 아니다. 새 판에서는 각 질문을 아래 네 요소 중 하나에만 연결하고, 다른 요소를 답에 몰래 덧붙이지 않는다.

| 질문이 직접 받는 것 | 예시 초점 | 결과에서 허용되는 말 |
|---|---|---|
| 장면의 첫 반응 | 예상과 다른 견적, 상대의 결정, 가족의 제안 직후 가장 먼저 든 생각 | “이 장면에서 이 생각을 골랐어요.” |
| 내가 지키려는 것 | 돈의 여유, 기억에 남을 장면, 내 결정권, 상대의 노동, 가족의 마음 중 무엇이 걸렸나 | 고른 표현 그대로. 선택하지 않은 동기를 추정하지 않음 |
| 실제로 요구할 도움 | 들어주기·함께 확인·일 맡기기·잠시 쉬기 등 | “이 상황에서 먼저 요청하고 싶은 도움” |
| 조건이 바뀌면 달라지는 지점 | 시간이 충분할 때/급할 때, 둘만 볼 때/가족이 볼 때, 내가 맡을 때/상대가 맡을 때 | 같은 사람 안에서도 답이 달라진 조건을 함께 보여줌 |

새 장면 후보는 아래처럼 **결과를 미리 암시하는 성향 낱말 대신**, 결혼 준비에서 양립 가능한 걱정들을 드러낸다. 아직 문항 은행이 아니며 선택지 분포·이해도·채점 대상은 사람 검토 전이다.

1. 상대가 맡은 예약·답장을 계속 챙기고 있었다는 사실을 뒤늦게 알았을 때, 무엇이 먼저 마음에 걸리나: 내가 못 알아본 일 / 미리 말하지 않은 일 / 앞으로의 총량 / 상대가 쉬지 못한 일. 이는 **보이지 않는 노동과 인정**의 대화 소재다. 책임감 유형으로 집계하지 않는다.
2. 둘이 정한 예산선을 넘는 곳이 마음에 들었을 때, 상대에게 꺼내기 가장 어려운 말은 무엇인가: 내가 원한 장면을 포기하기 싫음 / 이후 생활비가 걱정됨 / 상대에게 부담을 넘길까 걱정됨 / 약속을 바꾸자는 말 자체가 어려움. 이는 **돈의 의미와 말하기 어려움**을 직접 묻는다. 지출 능력을 추정하지 않는다.
3. 가족이 비용을 도와주며 식순 한 가지에 의견을 낼 때, 가장 먼저 확인하고 싶은 것은 무엇인가: 지원 조건 / 가족이 그 순서를 바라는 이유 / 둘이 포기하기 어려운 부분 / 상대가 감당할 설명의 부담. 이는 **지원·관계·경계**를 나누어 묻는다. 가족을 사랑하는 정도로 읽지 않는다.
4. 둘이 합의한 담당 일을 상대가 마쳤지만 기대와 다른 결과를 가져왔을 때, 처음 떠오른 생각과 실제로 할 말을 따로 묻는다. “왜 미리 물어보지 않았지”와 “내 기준을 말했어야 했나”를 같은 책임 분담 점수로 합치지 않는다.
5. 준비를 마친 좋은 날에도 남은 일이 보일 때, 먼저 원하는 반응을 묻는다. 지쳤을 때의 도움과 **기쁜 날의 축하·회복**이 같다고 가정하지 않는다.
6. 같은 문제를 시간이 넉넉한 날과 마감이 급한 날에 한 번씩 제시한다. 답이 바뀌면 한쪽을 오류로 처리하지 않고 “언제 방식이 달라지는지”로 읽는다.

차기 문항 청사진에는 각 ID에 `직접 묻는 것`, `응답 주체(나/상대 추정/제삼자)`, `시점(회상/지금 가정/희망)`, `가장 그럴듯한 대안 설명`, `비해당 조건`, `안전·계약 공통 전제`, `폐기 기준`, `정확 버전`을 적는다. 응답 선택지는 현실적인 네 방식이 모두 존중받도록 쓰고, “둘 다”, “상황에 따라”, “보기 밖”, “모름”, “비해당”, “지금 답하지 않음”을 하나의 중간값으로 합치지 않는다.

## 결과·커플 비교 계약 제안

- **첫 화면:** 네 글자의 순서와 고유 뜻을 나와 상대 각각 같은 표로 푼다. 글자를 읽을 근거가 약하거나 상황에 따라 바뀌면 그 상태를 숨기지 않는다. 동물 별명 등 재미 요소는 답에서 추론한 인격 설명처럼 쓰지 않는다.
- **두 번째 층:** 주제별로 내가 실제 선택한 문장, 그때 고른 이유(직접 고른 경우에만), 반대로 답한 장면, 비해당과 모름을 구분한다. `quote.ts`의 대표 인용만으로 “왜 이 글자가 나왔는지 전부 알 수 있다”고 말하지 않는다.
- **두 사람 보기:** 같은 exact-version의 같은 질문에 둘 다 유효하게 답한 경우에만 나란히 놓는다. 글자가 같아도 지키려던 것이 다를 수 있고, 달라도 실제 요구가 같을 수 있다. 차이를 점수·궁합·비난 문장으로 바꾸지 않고 “각자 무엇을 지키려 했나”, “이번 준비에서 어디까지 함께 정할까”를 묻는다.
- **퍼센트:** 사용자가 원하면 `실제로 답한 문항 중 특정 방향 선택`처럼 **분모가 보이는 응답 분포**만 쓴다. 현행 v4는 형식마다 -6~+6의 서로 다른 값을 가중 합산하므로 단순 선택 비율은 글자 계산의 설명이 아니다. 성향 확률·검사 정확도로 표시하지 않는다. 비율이 결과의 산식과 다르면 별도 표제로 분리해야 한다.
- **링크:** 질문만 보내는 초대와 내 답이 담긴 링크, 두 사람 결과 링크를 다른 행동과 문구로 안내한다. 결과 링크는 다시 답하라고 말하지 않는다. 주소의 `#` 뒤에 답이 실리는 경우 받는 사람도 답을 볼 수 있음을 전송 전에 알린다.

## 버전과 검증 경계

현행 `v4.0-tendency`의 원본이나 생성 파일은 이번 감사에서 바꾸지 않았다. 링크는 문항 ID·보기 위치를 인코딩하고, 다시 열 때 현재 은행의 원문으로 결과를 만든다. 위의 회상 보기에서 결과 절을 삭제하거나 새로운 내면 동기 선택지로 교체하면 예전 링크의 답이 **그 사람이 읽지 않은 문장**으로 복원된다. 이 변경은 새 exact-version과 별도의 은행·코덱/입구 호환 계획이 필요하다. 문항 수·형식·방향·가중치가 달라질 때도 같다.

### 새 exact-version의 최소 안전 경로

`v4.1-depth`는 **제안 태그**이며 아직 코드나 운영 링크가 아니다. 다음 판이 현행 68문항의 ID·형식·순서·극·가중치를 유지한다면 70자 응답 코드의 문자 배치와 값 계산기는 재사용할 수 있다. 그러나 코드만 같아도 **URL의 판 태그가 다르면 다른 문항**이다. v4.0 응답을 새 은행에 가져오거나 서로 비교하지 않는다.

1. `2026-09-29_v40_items.json`과 생성된 `weddingCodeV40Bank.ts`를 동결한다. 새 JSON과 생성 파일을 각각 만들고, 별도의 생성·검사 과정이 두 원본의 해시를 검증한다. 현행 생성기 `build-wedding-code-v40-bank.mjs`와 JS 검사기는 v4.0 버전을 문자 그대로 요구하므로 파일 경로만 바꾸어서는 새 은행을 만들 수 없다.
2. `v40/types.ts`의 `BankData`·`Bank.version`, `v40/bank.ts`의 버전 검사를 새 판을 받도록 일반화하거나 새 판 전용 은행 생성자를 둔다. 기존 `WEDDING_CODE_V40_BANK`는 언제나 구은행을 낸다. 구버전의 테스트 표본과 링크 인용을 그대로 고정한다.
3. `v40/codec.ts`의 인코드/디코드 **값 부분**은 은행 인자를 받으므로 재사용 후보지만 링크 조립·해시는 `v4.0-tendency`를 고정한다. 새 판은 명시적인 판 인자로 링크를 만들고 정확한 판만 풀어야 한다. 서로 짐작하기의 `guessLink.ts`도 판을 고정한다. 구버전 링크 생성 함수의 기본 판을 조용히 바꾸지 않는다.
4. 새 판의 질문 화면·클라이언트가 **새 은행**을 인자로 받아야 한다. 현재 `WeddingCodeV40Client.tsx`는 모듈 범위에서 구은행을 잡고 판 태그를 통계·공유·재시작에 반복해서 사용한다. `storage.ts`와 글자 짐작 봉투도 v4.0 버전과 저장 키를 고정한다. 새 판은 다른 보관 키를 쓰고 옛 답을 새 질문의 답으로 자동 복원하지 않는다.
5. `entry.ts`가 명시 `?v=`와 `#v=...&a=`를 정확한 판으로 라우팅하고, 두 사람이 다른 판으로 답한 링크는 비교를 거절한다. 기존 `v4.0-tendency`의 저장·공유·받는 사람·결과 인용이 바이트와 의미 모두 같아야 한다.
6. 새 판에는 별도 골든 링크, 구판 링크 회귀, 교차 판 거절, 생성 원본 해시 대조, 문항 인용, 같은 ID가 다른 문구로 해석되는 일 없음, 저장 키 격리, 모바일 완주를 검사한다. 채점 방향을 그대로 둬도 새 문구에서 그 방향이 사람에게 어떻게 읽히는지는 인지면접 전까지 미검증이다.

코드 의존성은 은행·코덱만의 변경이 아니라 클라이언트·보관·짐작 링크·입구·테스트 전반이다. 이 경계가 한 번에 닫히지 않으면 **연결되지 않은 다음 판 문항 후보만** 남기고 현행 v4.0의 답을 재해석하지 않는 편이 안전하다.

[CDC의 인지면접 안내](https://www.cdc.gov/nchs/ccqder/question-evaluation/cognitive-interviewing.html)는 응답자가 질문을 어떻게 이해하고 답을 고르는지 조사하는 방법을 설명한다(S). [Pew의 설문 작성 안내](https://www.pewresearch.org/writing-survey-questions/)는 선택지 문구·순서와 사회적 바람직성이 응답을 바꿀 수 있음을 설명한다(S). [검사 표준 원문](https://www.testingstandards.net/uploads/7/6/6/4/76643089/standards_2014edition.pdf)은 **의도한 해석과 용도마다** 타당도 근거가 필요하다고 밝힌다(S). 이 자료는 웨딩코드가 검증됐다는 근거가 아니다.
