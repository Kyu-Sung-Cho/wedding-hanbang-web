# 웨딩코드 v1.2 결과 문구 재검수

2026-09-20. 문항 20개를 서로 다른 세 소비자 상황으로 읽고 실제 결과 함수에 응답을 넣었다. 이는 내부 시뮬레이션이며 실제 소비자의 이해도나 몰입도를 검증한 자료가 아니다. 최종 전체 관문과 브라우저 실행 증거는 [소비자 역할 테스트 기록](./2026-09-20_consumer_walkthrough.md)을 따른다.

## 발견한 불일치

- A1의 받는 사진 수, A2의 포함 서비스, A3의 촬영 시간, A5의 식사 인원 확인 방법을 묻는 답이 결과에서는 `적힌 내용이 사실인지`로 묶였다. 서비스 정보를 묻는 것을 거짓 여부를 의심하는 태도로 읽을 수 있다.
- C는 부모님 조건을 이미 확인한 뒤 마지막 선택에 누가 참여하는지 묻는다. 그런데 제목·셈·부재 설명은 `우리 둘 먼저 / 가족·하객까지`를 유지했다. 부모님과 손님을 배려했는지의 차이로 읽힐 여지가 있었다.
- B의 `한 사람이 도맡지 않는` 설명은 함께 고르고 상담을 같이 듣는 실제 선택보다 범위가 넓다.
- 후속 `이번 주에 함께 정할 것`의 C 문구에는 부모님 의견을 듣는 순서나 즉답 압박이 남아 있었다. v1.2에서는 마지막 선택 참여자를 함께 맞추는 제안으로 연결한다. D의 할 일 먼저 제안도 남은 일을 일괄 주말로 미루도록 하지 않고 마감을 확인한 뒤 정하도록 좁힌다.

## 후보와 결정

1. 기존 짧은 이름을 유지하고 하단 설명만 덧붙인다. 제목과 셈을 먼저 읽는 사용자의 오해가 남으므로 채택하지 않는다.
2. v1.2 응답 결과에서만 짧은 이름·셈·제목·부재·반복 확인과 배지를 함께 맞춘다. **채택.** 네 글자와 집계, 구판 응답 결과는 그대로 둔다. 판 정보가 없는 코드 조회는 아래 보완 gate에 따라 공통 주제만 설명한다.

C 이름 후보는 `둘이 정하기 / 부모님과 정하기`와 `둘이 정하기 / 부모님도 참여`를 검토했다. C3은 부모님께 선택을 맡기는 보기까지 있으므로 두 번째를 쓴다. A의 서비스 확인은 `무엇을 어떻게 해주는지`, 경험·기억은 `그날의 경험과 남길 기억`으로 적는다. B의 함께하는 쪽은 `함께 고르거나 상담을 같이 듣는 답`으로 좁힌다.

## 구현·검증 범위

v1.2 결과 프로필에서 전용 표시 문구를 제공하고 배지·셈 생성기는 그 문구를 받는다. 구판 기본값, 네 글자, 응답 수, 인용, 미응답 처리, 공유 판은 바꾸지 않는다. 결과와 배지의 양쪽 이름 및 부재 설명을 함께 검증하고, 잘못된 이름이나 진위 표현을 다시 주입했을 때 검사가 실패하는지 확인한다. 전체 관문과 브라우저 재검증은 상위 작업에서 수행한다.

후속 제안까지 실제 문항 판을 전달하는 선택적 `questionVersion` 필드를 쓴다. 글자만 있는 예전 데이터에서는 해당 필드가 없으므로 기존 문구를 유지한다. C 후속 제안은 함께 고를지 부모님께 맡길지, 일마다 누가 최종 선택할지를 확인하는 내용이다. 이 제안은 이미 부모님과 갈등이 있거나 기한이 있다고 단정하지 않는다.

## 이번 담당 범위 검증 결과

- 결과·글자·기존 개인 요약·배지·페이지의 관련 5개 파일, 95개 검사 통과.
- 새 결과 테스트는 세 가상 응답의 20개 인용·축별 집계·코드 보존과 서비스 정보/가족 참여 설명을 함께 확인한다.
- 잘못된 C 명칭, A 진위 의심, 후속에서 문항 판 무시, 배지에서 판별 이름 무시, 셈에서 판별 이름 무시를 주입한 5개 변형을 모두 잡았다. 도구가 원본 MD5 복원을 확인했다.
- 전체 검증 관문·최종 빌드·브라우저 재확인은 상위 작업에서 별도 기록한다. 이 부분 검사만으로 전체 완료를 말하지 않는다.
- 실제 소비자의 문항 이해도·몰입도, 실제 커플 대화 유용성은 아직 검증하지 않았다.

## 코드 뜻 조회 화면 보완 gate

독립 통합 검수에서 `/wedding-code/c/[code]`가 여전히 구판의 개인 응답 설명을 그대로 노출하는 것을 확인했다. 이 주소에는 문항 판과 실제 답이 없는데도 V를 `적힌 내용이 사실인지`, F를 `가족과 하객 사정을 앞에 둔 답을 더 많이 골랐어요`로 읽어 주었다. v1.2에서 서비스 정보를 확인하거나 부모님께 최종 선택을 맡긴 사람이 같은 글자를 조회하면 결과와 다른 설명을 보게 된다.

두 안을 비교했다.

1. 코드 조회도 현재 v1.2의 결과 문구로 바꾼다. 주소에 판 정보가 없어서 옛 코드를 현재 문항의 답으로 해석하는 오류가 생긴다. 채택하지 않는다.
2. 글자 유효성 검사와 코드 표기는 유지하고, 조회 화면만 판에 공통되는 주제 범주를 설명한다. **채택.** 비용·서비스 조건 / 분위기·경험, 함께 살피기 / 맡아서 하기, 둘의 선택 / 가족 참여, 마음 / 할 일을 중립적으로 설명한다. 누구의 답을 세었다거나 특정 상황에서 무엇을 골랐다고 말하지 않는다.

조회 화면에는 코드만으로 어떤 문항에 답했는지 알 수 없으며, 정확한 풀이와 고른 답은 함께 받은 결과 링크에서 확인한다는 안내를 넣는다. C는 문항에 따라 가족 의견을 듣는 순서와 마지막 선택 참여자를 다르게 묻는다는 범위를 짧게 알린다. 검색 설명도 특정 판의 문항 수나 개인 답을 아는 것처럼 쓰지 않는다. 구판의 실제 결과 링크, 공통 글자 파서, 결과 프로필은 수정하지 않는다.

검사 기준은 16개 코드 조합에서 공통 범주·양쪽 글자·선택 방향을 보존하고, 개인의 응답을 단정하는 구판 문장이나 현재 판의 문항 수가 조회 설명으로 다시 들어오지 않는 것이다. 실제 응답 결과를 조회 페이지가 대신할 수 없음을 화면과 검색 설명에서 모두 확인한다. 이는 내부 카피·집계 gate이며, 사용자 이해도를 측정한 결과가 아니다.

조회 페이지 관련 8개 검사가 통과했다. 구판 개인 응답 설명을 다시 출력하는 변형 1개와 화면·검색 설명의 문항 판 한계 안내를 없애는 변형 1개를 주입해 두 경우 모두 검사 실패를 확인했다. `prove-guard`는 원본 MD5 복원을 확인했고 `.verification/guard-proofs.json`에 기록했다. 실제 브라우저 확인과 전체 검증 관문은 상위 작업에서 수행한다.

## 커플 결과의 같은 편·다른 답 누락 gate

브라우저에서 두 응답 `ACABDCBAAAABCABABABA`와 `CDACDCDCCCBBCBBABBAA`를 비교했다. 20장면 중 서로 다른 답이 11개였지만, 펼친 ‘둘이 해 볼 것’ 카드는 10개였다. B2의 ‘상담을 하나씩 맡아서 각자 듣는다’와 ‘두 상담 모두 상대가 혼자 다녀온다’가 같은 집계 방향이라는 이유로 빠졌다. 추천 후보에 `splits`만 넣고 같은 편의 서로 다른 답인 `shared`를 빼면서 ‘답이 갈린 장면마다’라는 화면 설명과 실제 카드 수가 어긋났다.

수정안 두 가지를 검토했다.

1. 카드 내용은 그대로 두고 설명을 ‘반대쪽 답을 고른 장면’으로만 좁힌다. 같은 편이어도 실제 역할 담당자가 다른 B2의 유용한 대화 지점을 빠뜨리므로 채택하지 않는다.
2. **v1.2에서만 서로 다른 모든 답을 추천 후보로 사용한다.** 기존 `splits`의 우선순위와 첫 카드의 축 분산은 유지한다. 세 카드에 빈자리가 있으면 `shared`에서 아직 없는 축을 먼저 채우고, 모두 펼치면 같은 편의 다른 답까지 빠짐없이 보여준다. 채택한다.

구판의 추천 후보와 기존 집계·코드·공유 형식은 바꾸지 않는다. ‘서로 다른 답’과 ‘반대쪽 답’은 계속 구분하며 추천에서만 누락을 없앤다. 검사는 B2의 같은 편·다른 답 한 쌍에서도 실제 인용과 다음 대화가 나오고, 위 혼합 사례에서 처음 세 카드의 순서는 유지되면서 펼친 카드 11개가 실제 서로 다른 11문항과 일치하는지 확인한다. 이 수정은 내부 비교의 완전성을 고치는 것이며 대화 유용성에 대한 사람 검증을 대신하지 않는다.

수정 후 `WeddingCodeComparison.regression.test.tsx`와 `page.test.tsx`의 36개 검사가 통과했다(`.verification/logs/v12-all-different-recommendations.log`). 혼합 사례의 첫 카드는 기존 `A1 → B3 → C1`을 유지하며 8개 더 보기를 누르면 11개가 모두 나온다. v1.1의 같은 편·다른 답은 기존처럼 전체 비교 목록에만 남고 새 추천을 추가하지 않는다. 변형 검증·전체 관문·브라우저 재확인은 상위 작업에서 이어간다.

이후 `shared`를 추천 후보에서 다시 빼는 변형을 주입해 회귀 검사가 실패하고 원본 해시가 복원되는 것을 확인했다
(`.verification/logs/v12-all-different-prove-guard.log`). 최종 빌드의 브라우저에서도 두 응답 링크를 새로고침해,
처음 세 카드·8개 더 보기·펼친 11개 카드와 B2의 실제 답·대화 제안을 확인했다. 코드와 답의 집계는 그대로였다.

전체 웹 검사에서는 통합 UI 검사의 옛 기대값 1개를 놓친 것이 드러났다. v1.2의 실제 칩은 ‘부모님도 참여’인데
`WeddingCodeV06Client.interaction.test.tsx`가 ‘가족·하객까지’를 기대했다. 다른 16,388개 검사는 통과했지만
이 실행은 실패다(`.audit-output/consumer-audit-20260920/full-web-stale-expectation.log`). 화면 코드나 비교 조건을
우회하지 않고 해당 검사의 정확한 기대 문구만 교정했으며, 이 파일의 18개 검사가 다시 통과했다
(`.verification/logs/v12-interaction-copy-green.log`). 최종 전체 관문은 이 교정 이후 다시 실행한다.
