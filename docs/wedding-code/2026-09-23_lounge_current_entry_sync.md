# 라운지와 공개 웨딩코드의 최신 진입 통일

2026-09-23 · 구현·로컬 검증 기록 · 전체 검사 및 운영 배포 완료를 뜻하지 않음

## 문제와 선택

사용자는 라운지의 ‘우리의 준비 스타일’이 공개 웨딩코드와 달라 보인다고 지적했다.
원인은 이름만의 차이가 아니었다. 공개 `/wedding-code`는 v3.1의 **기본 23문항 → 결과 →
선택 9문항**을 사용했지만, 라운지 `/preparation-style`은 `PreparationStyleHub`에서
v1.2의 **20개 장면형 질문**을 별도로 실행했다. 공개 설문을 수정해도 라운지에는 적용되지 않았다.

대안은 세 가지였다.

| 대안 | 판단 |
|---|---|
| 메뉴 이름만 ‘웨딩코드’로 변경 | 같은 이름으로 서로 다른 질문을 제공하므로 원인을 해결하지 못함. |
| v3.1 응답의 계정 저장·파트너 공유까지 한 번에 이관 | 기존 API·DB·동의·권한 계약을 함께 바꿔야 하므로 이번 진입 통일보다 범위가 큼. |
| 공개 진입 컴포넌트를 라운지에서도 재사용 | 선택. 문항·결과·브라우저 이어하기를 같은 구현으로 제공하고 기존 계정 기록은 별도로 보존. |

이는 제품·구현 판단이며, 소비자 만족도나 전환율 개선을 검증한 결과는 아니다.

## 구현과 보존 경계

- 라운지 카드, 사이드바, 상단 제목과 바로가기를 **웨딩코드**로 통일한다. 기존
  `/preparation-style` 및 `/wedding/preparation-style` 주소는 유지한다.
- 기본 페이지는 `LoungeWeddingCode`와 공용 `WeddingCodeEntryClient`를 사용한다.
  최신 문항·결과를 라운지용으로 복제하지 않는다. 카드의 기본·선택 문항 수는
  `v31Flow`의 실제 배열 길이에서 읽는다.
- `embedded` 모드는 라운지의 탐색과 본문 틀을 유지하고 공용 클라이언트의 중첩
  `<main>`과 별도 공개 탐색을 제거한다. 질문 전환 시 고정 헤더 아래로 이동한다.
- `?view=previous`는 이전 v1.2 계정 기록을 당시 질문·결과로 조회하고, 기존 권한에 따라
  공유·공유 중단·삭제할 수 있는 화면이다. 구판 질문을 새로 시작하는 버튼은 제공하지 않는다.
  조회 실패를 ‘저장한 답 없음’으로 표시하지 않는다.
- 이전 커플 비교는 두 사람이 이전에 저장한 답을 각각 공유했을 때 가능하다. 한 사람에게
  이전 답이 없다면 최신 웨딩코드에서 새로 답하도록 안내한다. 이전 답 삭제는 복구할 수 없고,
  최신 답을 작성해도 그 기록에 합쳐지지 않는다.
- 기존 query·fragment 링크는 공용 판별기로 해당 판의 의미를 유지한다. 구판 query 응답을
  fragment로 바꿀 때도 라운지 안에서는 현재 경로를 유지한다. 공개 공유 링크 주소는 그대로다.

최신 v3.1의 저장·공유 계약은 바꾸지 않는다. 직접 작성하거나 명시적으로 불러온 본인 답은
**같은 브라우저에 자동 저장**하며, 마지막 실제 저장부터 30일 동안 이어 할 수 있다.
계정별 저장이나 다른 기기 동기화가 아니다. 저장 끄기·삭제·탭 간 충돌 보호를 유지한다.
공개 v3.1 화면과 라운지는 같은 출처와 저장 키를 사용하므로 같은 브라우저의 v3.1 답을 이어 볼 수 있다.
라운지와 키를 함께 쓰는 공개 경로는 v3.1(`?v=v3.1-preferences`)뿐이다. 맨 `/wedding-code`(main은 36문항, wc64 반영 뒤에는 64문항), `?v=36`, `?v=likert-preferences-alpha.1`은 다른 키를 써서 라운지에서 이어지지 않는다(2026-10-16).

최신 커플 비교는 동의 후 만든 **답이 담긴 공개 fragment 링크**로 진행한다. 로그인 계정에
답을 저장하거나 연결된 파트너와 자동으로 비교하지 않는다. 링크 소지자는 답을 볼 수 있고
이미 보낸 링크는 회수할 수 없다. 받은 상대 답과 공유 동의는 본인의 브라우저 저장에 넣지 않는다.
특정 파트너에게 철회 가능한 공유를 제공하는 구판 계정 계약과 이 계약을 섞지 않는다.
v3.1 응답을 v1.2 전용 API로 전송하거나 구판 답을 새 응답으로 변환하지 않는다.

## 적대적 검수와 수정

독립 코드 검수에서 두 결함을 찾아 수정했다.

1. 이전 기록 화면에 남아 있던 ‘각자 이 화면에서 답을 저장’ 안내를 제거했다. 구판 재응답을
   막은 화면에서 수행할 수 없는 작업이었으며, 삭제 뒤 재작성 가능 범위도 최신 설문으로 명시했다.
2. 구판 query 링크 정규화가 라운지 주소를 공개 `/wedding-code`로 바꾸던 경로를 수정했다.
   `embedded`일 때는 현재 pathname과 변환된 fragment를 사용한다.

## 2026-10-16 덧붙임: 맨 라운지는 wc64

파운더 요청("라운지도 64문항으로 옮겨줘")에 따라 맨 라운지(쿼리와 해시 없음)는 wc64(64문항)를 앱 안(`embedded`)으로 연다.
판 선택은 공개 `/wedding-code`와 같은 `weddingCodeReleaseTarget`이고, 판정이 wc64가 아니면(옛 판 쿼리, `#v=` 해시 링크,
`?ct=`, `?v=36`, likert) 위 본문대로 `WeddingCodeEntryClient`가 맡는다. 계약 정본은
[wc64 계약](./2026-10-16_wc64_report_contract.md)이다.

- 라운지 카드의 문항 수는 `v31Flow`가 아니라 `WC64_ITEM_COUNT`에서 읽는다. 되돌리기 상수(`WEDDING_CODE_BARE_TARGET`)를
  `"36"`으로 바꾸면 카드는 이번 변경 전 v3.1 문구로 돌아간다(`LoungeWeddingCodeCard`).
- 라운지 안의 문항과 계산은 공개 맨 주소와 같다. 식 계획에서 '식 없이 하려고 해요'를 고르면 식을 전제한 문장 27개(EYES·WEIGHT
  여덟 문장 전부 포함)를 묻지 않고 결과는 PACE·BOND 두 글자다(계약 §2). 글자 장의 할 일 제목은 '앱에서 바로 해 볼 것'이고 공개 결과의
  아모라 소개와 로그인 링크는 두지 않는다(DEC-3). 할 일 문장은 공개와 같아서 웹 라운지에서 보더라도 웹과 모바일 앱에 모두 있는
  기능만 말한다(일정은 '담당' 칸 대신 제목에 맡은 사람 이름을 적게 한다, 계약 §2.4).
- wc64 저장 키 `hanbang:wedding-code:wc64:r1:draft`는 같은 출처의 공개 맨 주소와 함께 쓴다. 그래서 위 44행의
  「라운지와 키를 함께 쓰는 공개 경로는 v3.1뿐」은 이제 v3.1 갈래에만 맞다.
- 두 사람 답은 링크가 아니라 사용자가 복사한 답 코드로 본다. 로그인해 있어도 답을 계정이나 아모라에 넘기지 않는다.
  이 변경 전 라운지 v3.1의 '함께 보기'는 초대 링크 하나로 두 사람 답을 서버에 7일 보관했고(위 46~50행의 답이 담긴 링크와는 다른 길이다), wc64는
  서로 코드를 주고받고 아무것도 보관하지 않는다. 앱이 두 사람을 이미 연결한 라운지에서도 같다. 2026-10-16 파운더 결정 DEC-4로
  이 방식을 유지한다(계약 §7.1. 서버 비교는 처리방침·동의·삭제 흐름이 필요한 별도 PR).
- 라운지에서 v3.1은 `?v=v3.1-preferences`, 답이 든 v3.1 해시 링크(`#v=v3.1-preferences&a=…`), 초대 `?ct=…`로 열린다.
  `?ct=`는 이번 변경 전처럼 `WeddingCodeEntryClient`의 기본 입구라 v3.1 소개(「기본 14페이지 · 로그인 없이 시작」)가 나온다.
  `#wc-likert=`가 아닌 해시도 모두 `WeddingCodeEntryClient`가 맡아, 답이 든 옛 링크면 그 판의 화면을, 읽을 수 없는 해시면
  「이 링크는 열 수 없어요」를 연다. 위 본문의 기본 페이지 줄(26~28행), v3.1 저장 문단(40~44행),
  커플 링크 문단(46~50행)은 이 v3.1 갈래에만 해당한다. 이 브라우저의 v3.1 진행 기록에 고른 답이 있으면 wc64 시작 화면에
  「이전 웨딩코드 이어 하기」(결과 화면 기록이면 「이전 웨딩코드 결과 다시 보기」) 버튼을 둔다.
- wc64 화면의 지우기 버튼 「이 브라우저의 64문항 답 지우기」와 자동 저장 끄기는 wc64 키만 지운다(`clearWc64Draft`). 이 브라우저의
  v3.1 진행 기록(`hanbang:wedding-code:v3.1:progress`)과 위 「이전 웨딩코드 이어 하기」 버튼은 남고, v3.1 답은 v3.1 화면의
  「이 브라우저의 답 지우기」로 따로 지운다. 예전 이름 「이 브라우저의 답 모두 지우기」는 v3.1 기록을 남기면서 모두 지운다고 읽혀
  2026-10-17 상품 심사 M3에서 범위를 이름에 적었다(처리방침 제3조 64문항 항목도 같은 이름이고, 다른 판 답은 지우지 않는다고 적는다).
- `?view=previous`(이전에 계정에 저장한 답 보기)는 그대로다. 라운지 두 경로(`/wedding/preparation-style`,
  `/preparation-style`)는 이 화면까지 포함해, 머무는 동안 페이지 조회·흐름 이벤트·오류·누른 요소·화면 측정을 Sentry·PostHog로
  보내지 않는다(`isWeddingCodeLikertPath`). 다른 화면으로 넘어가는 동안에는 새 화면을 불러온 기록(경로, 걸린 시간, 화면이
  멈춘 시간)이 나갈 수 있고 답과 문항 정보는 들어가지 않는다(처리방침 제3조·제8조와 같은 말). 로그인·온보딩 화면 주소의
  `?redirect=`에 든 라운지 주소는 PostHog가 막지 않는다(그 화면의 이벤트다. 판 `v`·화면 `view` 밖의 쿼리가 붙으면 막는다).
- wc64 답은 로그인해 있어도 계정이 아니라 이 브라우저에 저장되고 로그아웃해도 남는다. 같은 브라우저를 쓰는 사람은 다른
  계정으로 로그인해도 그 답과 v3.1 이전 판 버튼을 볼 수 있다. 2026-10-16 파운더 결정 DEC-11로 지금은 가리지 않고 화면과 처리방침에
  밝힌다(계정 id를 붙인 라운지 키는 이후 판, [wc64 계약](./2026-10-16_wc64_report_contract.md) §6).
