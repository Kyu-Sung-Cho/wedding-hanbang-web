# 우리의 준비 스타일 — 통합 확인

## 제공 범위

라운지의 커뮤니티 탐색을 초기 출시 메뉴에서 숨기고, `/wedding/preparation-style`에 ‘우리의 준비 스타일’을 연결한다. 공개 커뮤니티 URL과 견적 확인 도구는 제거하지 않는다. 네이티브 앱은 이번 변경 범위가 아니다.

현재 공개 웨딩코드의 20문항·보기·점수 계산을 그대로 사용한다. 개인 결과는 실제로 고른 답을 네 주제로 정리하고, 두 사람 비교는 같은 문항에서 고른 보기 원문을 나란히 보여준다. 같은 집계 방향이어도 보기가 다르면 다른 답으로 센다. 미응답 장면은 비교하지 않는다. 성격 진단, 궁합, 갈등 예측, 실제 예산 산출, 자동 의사결정은 하지 않는다.

공개 결과 링크를 계정의 답으로 가져오지 않는다. 로그인한 이용자가 직접 답하고 저장에 동의해야 보관하며, 연결된 두 사람 모두 각자 공유에 동의한 현재 답만 비교한다. 공유 중단·새 답 저장·연결 변경 시 기존 공유 승인은 무효화된다. 같은 답을 다시 저장할 때는 현재 공유 상태를 유지하며 화면도 그 실제 상태를 설명한다.

결과를 지우면 원문·문항 판·저장 시각·저장 동의·공유 기록을 제거한다. 뒤늦은 최초 저장 요청을 거절하기 위한 계정 ID와 확인 번호만 남기며, 계정 삭제 요청 때는 이 기록도 제거한다. 이 경계는 개인정보 처리방침에 공개한다. 새 화면은 방문·세션 기록 분석 대상에서 제외한다.

## 실제 화면에서 확인한 것

로컬의 서명된 체험 모드로 라운지 → 메뉴 → 20문항 → 결과 확인 → 개인 결과 → 가상의 상대 비교까지 직접 조작했다. 체험 데이터는 실제 계정·상대에게 저장하지 않는다.

- 네 비교 주제와 실제 보기 원문, 같은 답·다른 답 수, 같은 이유라고 단정하지 않는 설명을 확인했다.
- 375px 모바일 화면에서 가로 넘침 없이 질문, 개인 카드, 주제 선택과 두 사람 답을 읽을 수 있었다. 1024px에서 상단 바로가기 글자가 줄바꿈되던 문제를 수정하고, 1024px·1280px에서 다시 확인했다.
- 결과로 이동할 때 고정 헤더 아래에 제목이 보이도록 여백을 수정하고 새로 불러온 화면에서 확인했다.
- 한 문항만 답하고 나머지를 건너뛴 결과에서 미응답 주제에 해석이 생기지 않고, 저장 전에는 다른 도구로 이동하는 링크가 나타나지 않는 것을 확인했다.
- 최신 체험 화면의 저장 전 안내가 계정 저장을 주장하지 않는 것을 확인했다. 해당 점검의 브라우저 오류 기록은 비어 있었다.
- 전체 검사에서 제목의 무효 글자 크기·굵기·줄높이 클래스와 공통 버튼 미사용을 발견해 수정했다. 이후 공통 버튼으로 20문항 전체, 긴 보기 줄바꿈·선택 표시·비교 주제 전환을 모바일 화면에서 다시 확인했다. 가로 넘침과 브라우저 오류는 없었다.

## 회귀 검사에서 확인한 경계

UI는 계정·상대가 바뀌면 이전 초안과 늦은 응답을 버린다. 서버 성공 응답만으로 완료를 표시하지 않고 요청한 상태가 실제로 돌아왔는지 검사한다. 저장 응답 유실이나 확인 번호 충돌 때는 작성한 답을 보존하고, 현재 계정 상태를 확인한 뒤 어느 답을 남길지 선택할 수 있게 한다. 새로 불러온 상태와 맞지 않는 이전 성공 안내도 제거한다.

최종 구현 commit `873a64a12c4f574938ffcf3c666745c403064819`에서 웹 16,505개, 저장소 944개, 타입·lint, 배포용 빌드를 통과했다. 중복 검사를 병렬 실행했을 때 기존 역사 계약 검사 한 건이 15초 제한을 272ms 넘겼지만, 동일 기준의 단독 8개 검사와 최종 전체 재실행이 모두 통과했다. 시간 제한이나 assertion은 바꾸지 않았다. 중단 요청 뒤 남아 있던 중복 검사도 종료되어 전체 웹 통과를 확인했고, 최종 재실행에는 해당 결과를 대체 증거로 사용하지 않았다.

공유·공유 중단·삭제는 현재 확인 번호와 대조한다. 삭제 후 옛 최초 저장 요청이 도착하거나, 연결 해제 후 같은 상대를 복원한 뒤 옛 공유 승인이 도착해도 거절하는 SQL 회귀를 별도로 실행했다. 새로운 검사들은 정상 코드의 통과와 의도적으로 잘못 바꾼 코드의 실패를 확인한 뒤 원복했다. 전체 검증 결과의 최종 기준은 `.verification/verification-receipt.json`과 각 proof 영수증이다.

## 아직 별도로 확인해야 하는 것

실제 소비자 대상 이해도·유용성 조사는 수행하지 않았다. 로컬 체험 화면과 합성 계정 DB 검사는 실제 운영 계정 두 개를 이용한 종단 간 테스트를 대신하지 않는다. 운영 적용 여부는 DB 릴리스 영수증, 배포 commit, 운영 화면 확인으로 따로 판단한다.

DB 적용 절차와 실패 시 복구 경계는 [준비 스타일 릴리스 문서](../operations/PREPARATION_STYLE_RELEASE_2026-09-20.md)를 따른다.
