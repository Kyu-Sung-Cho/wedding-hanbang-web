# 랜딩에서 웨딩코드 찾기

## 확인한 문제

2026-09-21 운영 `/landing`을 직접 확인했다. `/wedding-code` 링크는 아래쪽에 있었지만 첫 화면과 상단 메뉴에는 없었다. 아래쪽 이름도 ‘둘이 갈리는 장면 보기’, ‘둘의 준비 방식 살펴보기’여서 웨딩코드라는 이름으로 찾기 어려웠다.

## 선택한 수정

- 메뉴만 추가하면 모바일에서 메뉴를 열어야 발견할 수 있다.
- 별도 소개 섹션을 추가하면 첫 화면의 문제를 해결하지 못하고 페이지가 더 길어진다.
- 기존 첫 화면 보조 버튼을 ‘웨딩코드 해보기’로 바꾸고 데스크톱·모바일 메뉴에도 같은 이름으로 연결한다. 이 방식을 선택했다. 기존 아모라 가입 버튼과 디자인은 유지한다.

아모라는 계정이 필요하고 웨딩코드는 가입 없이 시작할 수 있다는 안내를 구분했다. 아래쪽 카드에는 혼자 답해도 자기 결과를 볼 수 있음을 덧붙였다. 두 사람 비교, 점수·궁합을 매기지 않는다는 안내, 공유 링크에 답이 담긴다는 안내는 유지했다. 문항·점수화·결과 생성·계정 연결 동작은 변경하지 않았다.

직접 이동하는 헤더 링크에는 기존 클릭 기록 컴포넌트를 적용했다. 모바일 링크는 클릭 기록을 유지하면서 메뉴를 닫는다. `landing_header`는 기존 집계 단위여서 목적지별 전환율을 분리해서 증명하지 않는다.

## 참고와 검증 범위

[Lazyweb 참고 패턴](https://www.lazyweb.com/agentic-search/e1847783-4728-4bbe-9b8e-5eff5e36d1d6)의 Typeform 랜딩 설명에서 이름이 분명한 진입 버튼 패턴을 참고했다. 경쟁 화면 이미지를 직접 검수하거나 전환율 개선을 입증한 것은 아니다.

기존 관련 검사 26개 파일, 228개 항목을 통과했다. 바뀐 목적지와 이름에 맞춰 기존 기대값만 수정했고 기존 고지 검사를 유지했다. 독립 코드 검수에서 확정 회귀는 발견하지 못했다.

로컬 브라우저에서 첫 화면 버튼과 데스크톱·모바일 메뉴가 공개 웨딩코드 소개로 연결되고, 가입 없이 첫 문항이 시작되는 것을 확인했다. 모바일 메뉴로 이동 후 돌아오면 메뉴가 닫혀 있다. 320·375px 모바일 및 1024px 화면을 확인했고 320·1024px의 문서 가로 넘침은 없었다. 실제 기기 검사는 아니다.

전체 검증·빌드·운영 배포 증거는 해당 변경 PR과 검증 영수증에 남긴다. 실제 소비자의 랜딩 발견률·전환율, 실제 iOS·Android 기기는 이번 검증에 포함되지 않는다.

## 배포 검사에서 발견한 시간 초과

첫 수정본의 로컬 전체 검증은 통과했지만 원격의 글자 색상 검사에서 전체 웹 소스를 변환하는 첫 호출이 15초 제한을 넘었다. 동일 소스로 원격 실패 잡을 한 번 재실행해도 같은 항목만 시간 초과했고 색상 위반 assertion은 보고되지 않았다.

해당 검사 묶음의 준비 단계에서 웹 소스를 한 번 변환하고 두 검사가 같은 결과를 읽도록 바꿨다. 전체 소스 준비에만 60초를 허용하며, 검사 대상·주석 제거 방식·최소 파일 수·색상·대비·예외 기준·개별 검사 제한은 유지한다. 준비 단계가 실패하면 검사도 실패한다.

수정 후 기존 26개 항목이 통과했다. `prove-guard`로 랜딩 헤더의 읽기 어려운 글자색 위반을 심었을 때 실패했고 원본 복구도 확인했다. 독립 검토에서 같은 파일 집합을 재사용하는 이 변경이 검사 범위를 줄이지 않음을 확인했다. 최종 판정은 새 커밋의 전체 로컬 검사와 원격 CI 결과로 한다.
