# 5점 선호 문항 은행의 로컬 계약

상태: LOCAL PROTOTYPE / UNVALIDATED. 사람 응답과 실제 전문가 검토는 0건이다. 이 문서는 새 로컬 후보의 문구와 구현 범위를 기록하며, 심리적 타당도·궁합·결혼 결과·상품 성과를 입증하지 않는다.

정본은 `apps/web/src/lib/weddingCode/likert/bank.ts`의 `ITEMS`와 각 문항이 참조하는 장면이다. 타입은 같은 디렉터리의 `types.ts`를 따른다. 구판 원문과 답은 이 은행으로 변환하지 않는다. 문구 또는 의미 있는 장면 전제를 바꾸면 새 문항 ID와 은행 revision을 부여한다.

## 현재 공개 계약과 승인 범위

- `AGENTS.md`, `PRINCIPLES.md` 및 `docs/wedding-code/README.md`의 현재 공개 계약을 확인했다. `DESIGN.md`의 기본 원칙과 WeddingCode 표현 지침도 확인했다.
- 이번 범위는 사용자가 승인한 별도 로컬 prototype이다. retired 문서의 문항 수나 예전 인간 게이트를 새 은행의 채택 기준으로 재사용하지 않는다.
- 문구 논리 검토와 코드 검증은 인간 인지면담 또는 실제 전문가 검토가 아니다. 로컬 구현은 공개 배포나 연구 수집 승인으로 확대되지 않는다.
- 이 은행은 서버·연구 수집·운영·연락 기능을 추가하지 않는다.

## 응답과 해석 계약

응답은 `1 전혀 그렇지 않다 / 2 그렇지 않다 / 3 보통이다 / 4 그렇다 / 5 매우 그렇다`다. `모름`, `비해당`, 건너뛰기는 유효한 동의 점수와 구분한다. 이 값을 3점이나 0점으로 대체하지 않는다.

모든 문항은 해당 상황에서 바라는 행동 또는 수용하는 방식 하나를 묻는다. 실제로 그 역할을 맡았다는 사실이나 상대가 그 행동을 해 주었다는 사실을 묻지 않는다. 낮은 동의는 다른 문항의 동의를 뜻하지 않는다. 한 장면에서 여러 욕구가 함께 높거나 낮을 수 있다. facet를 역채점 관계로 취급하지 않으며, 네 글자는 별도 모델의 응답 표현이지 검증된 양극 성격 척도가 아니다.

| 도메인 | 긍정 개념 | 별도 해석 제한 |
|---|---|---|
| money | C: 기본 구성 보강에 추가 예산을 배정하려는 욕구 / E: 원하는 기념 경험에 추가 예산을 배정하려는 욕구 | 수입·절약·소비 성격을 추론하지 않는다. 구체적인 옵션 취향이 포함된 지출 우선순위 단서다. |
| process | J: 후보 자료를 직접 비교하려는 욕구 / T: 함께 정한 기준 안에서 한 사람이 초기 후보를 추려 공유하는 방식의 수용도 | 함께 일하기와 혼자 일하기의 역쌍이 아니다. 수행자·위임 욕구·실제 시간·능력·책임감·최종 권한을 직접 추론하지 않는다. 누가 후보를 추릴지는 따로 상의한다. |

T의 실제 문항에 있는 '한 사람'은 응답자와 상대 중 수행자를 지정하지 않는다. 동의는 함께 정한 기준 안에서 한 사람이 초기 후보를 추려 공유하는 방식을 받아들일 수 있다는 응답이다. 이 응답만으로 본인이 후보를 추리고 싶다는 욕구나 상대에게 맡기고 싶다는 욕구를 구분하지 않는다. 수행자와 실제 역할은 별도로 상의한다. J의 직접 비교 욕구와 T의 방식 수용은 함께 높거나 낮을 수 있다.

## 장면 범위와 후보 수의 근거

현재는 돈·과정·가족에서 서로 다른 세 결정을, 도움에서는 서로 다른 세 작업 직후와 네 요청을 다룬다. 이에 따른 후보는 30개이며 채택 목표 수가 아니다. 각 장면의 항목은 하나의 동일한 `context`를 공유한다. 장면 목록은 `SCENES`에 있고, 개별 문항에는 `sceneId`, `sceneTitle`, `context`, `construct`, `resultUse`가 함께 저장된다.

돈 장면의 '같은 추가 비용'은 장면 안에서 옵션 간 비용 차이를 줄이는 가정이다. 절대 가상 가격은 아직 고정하지 않았으므로 비용 크기 통제가 완료됐다고 부르지 않는다. 복잡한 예산 수식이나 생활비·예비비의 실제 금액 입력을 요구하지 않는다.

## 역쌍·중복·편향 검토 결과

- 동일 금액의 '쓰기 / 남기기'는 제외했다. 미지정 예산 몫 문항도 현재 은행에 넣지 않았다. 돈은 지출 대상의 구체적인 우선순위로 한정한다.
- 과정의 '둘이 함께 작업 / 한 사람이 작업' 역쌍을 제외했다. 직접 자료 비교 욕구와 한 사람이 기준 내 초기 후보를 추려 공유하는 방식의 수용은 동시에 있을 수 있다. 수용도에서 수행자나 위임 욕구를 직접 추론하지 않는다.
- 가족의 '먼저 묻기 / 먼저 정하기' 순서 역쌍을 제외했다. 가족 생각 확인과 둘의 기준 정리는 독립된 긍정 앵커다.
- 경청·실무 정리·함께 쉬기·혼자 쉬기는 각각 한 요청이다. 쉬기 두 요청이 같은 순간에 실행상 충돌할 수 있어도 점수를 서로 뒤집지 않는다.
- '현명하게', '책임 있게', '배려해서', '존중해서' 같은 도덕적 수식과 불필요한 부정·역문항을 넣지 않았다. 동의형 문구의 동의 편향과 사회적 바람직성 위험은 여전히 남는다.
- 장면마다 같은 표현을 쓰는 문항은 표현 중복이 있다. 실제 장면별 정보가 구별된다고 검증한 것은 아니다. 현재는 방문·비교·연락 뒤의 요청 차이를 확인할 후보로 남기며, 차이가 없으면 장면 또는 문항을 줄인다.
- 위치 효과와 반복 응답의 영향은 미확인이다. 현재 고정된 장면·facet 순서를 균형 배치가 검증된 것으로 표현하지 않는다.

## 구현 확인과 남는 확인

`ITEMS`와 개별 문항, `SCENES`와 장면 객체는 실행 시 동결한다. `getItem`, `getItemsByDomain`, `getItemsByScene`은 은행의 실제 문항을 조회한다. 은행의 ID 유일성·타입·장면 공유·facet 연결은 코드 검사 대상이다. 검사 결과는 실행 영수증으로 따로 보고하며 이 문서는 통과를 선행 주장하지 않는다.

2026-10-08 T 해석 제한 수정은 세 T 문항의 `construct`와 `resultUse`, 이 문서의 해석 설명에 한정한다. 실제 문항의 `id`, `text`, `context`, 장면과 응답·계산 규칙은 바꾸지 않는다. `BANK_REVISION`은 `preferences-20261008-r2`, `MEASUREMENT_VERSION`은 `likert-preferences-alpha.1`을 유지한다. 은행의 T 메타데이터와 여덟 글자 설명에서 수용 응답을 '맡기고 싶은 욕구'로 확대하지 않는다. 표현 버전과 이전 표현 버전의 링크 호환성은 은행 문항 계약과 별도로 확인한다.

남는 확인은 문항 이해, 장면 현실성, 반복 장면의 추가 정보, 응답 안정성, 완주 부담이다. 현재 계수·절단점·정확도·전문가 승인·인간 검증을 제시하지 않는다. 4글자와 형용사·동물 캐릭터는 요청된 놀이 표현이며 사람의 고정된 유형을 뜻하지 않는다.
