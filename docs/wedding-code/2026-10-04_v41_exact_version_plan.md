# 웨딩코드 문항 교체의 exact-version 분리 계획

작성: 2026-10-04 · 상태: **로컬 작업 트리의 기본 입구와 명시 입구에 연결 / 사람 검증 전 / 미배포**

현재 로컬 구현은 bare `/wedding-code`와 `?v=v4.1-depth`에서 전체 새 문항 은행을 연다. 질문만 공유하거나 v4.1에서 다시 시작한 URL에는 판 태그를 명시한다. 기존 `?v=v4.0-tendency`와 `?v=v3.1-preferences`, 그 판들의 답이 든 링크는 각 판으로 열린다. v4.1 공유 답 코드 `a`, `b`는 첫 글자 `2/3`, 짐작 코드 `ga`, `gb`는 첫 글자 `2`로 v4.0 코드와 구분한다. 따라서 URL의 버전만 바꾸거나 판이 다른 필드를 섞은 링크는 거절한다. v4.1 진행·기록·자동 저장·글자 고르기는 별도 저장 키와 `v4.1-depth` 봉투를 쓰며, v4.0과 v3.1의 진행·기록 키를 지우지 않는다. 이전 판에서 자동 저장을 꺼 둔 선택만 첫 방문에 따른다. **실제 사람의 문항 이해도와 재검사 결과는 아직 확인되지 않았다.**

> 진행 메모: `2026-10-04_v41_items.json`이 현행 68문항 원본이다. `2026-10-04_v41_item_revisions.json`의 열 문항은 초기 후보 기록으로 남아 있으며 런타임은 읽지 않는다. 문안 검수 상태는 [`v4.1 문항 은행 검수 기록`](./2026-10-04_v41_item_bank_review.md)을 따른다. 아래 표와 순서는 exact-version 분리의 설계 기록이다. 위 로컬 연결 상태와 사람 검증·배포 상태는 구분한다.

## 왜 새 판이 필요한가

현재 `v4.0-tendency` 공유 코드의 68개 응답 글자는 문항 순서와 보기 위치를 담는다. URL의 `v4.0-tendency`가 같은 채로 보기 문장을 바꾸면 과거 응답이 **당시 보지 않은 문장**으로 복원되고, 결과 인용도 바뀐다. 채점 방향이나 ID를 그대로 유지해도 이 문제는 생긴다. `2026-10-04_v41_item_revisions.json`은 [문항 깊이 감사](./2026-10-04_v40_item_depth_audit.md)의 열 문항에 대한 **새 판 후보**다. v4.0 원본, 생성 파일, 기존 링크는 건드리지 않는다.

| 경계 | 현행 고정 지점 | 새 판의 최소 변경 |
|---|---|---|
| 문항 | `docs/wedding-code/2026-09-29_v40_items.json` → `scripts/build-wedding-code-v40-bank.mjs` → `apps/web/src/constants/weddingCodeV40Bank.ts`; `v40/bank.ts`가 v4.0 태그와 배치를 검사 | 후보 열 문항을 포함하는 **새 전체 JSON**과 새 생성 파일을 만들고, 생성기·검사기에 태그/출력 경로를 명시. v4.0 원본 해시와 생성 결과는 회귀 고정. 공통 배치를 재사용하더라도 새 은행 객체는 별도. |
| 링크 값 | `v40/codec.ts`의 `encodeCode`·`decodeCode`는 받은 은행의 순서와 형식을 읽음 | 68개 ID·형식·보기 수·배치가 유지된다면 값 인코더는 재사용 가능. 새 판의 골든 코드는 별도 고정. 문항 문구가 바뀌어도 같은 코드를 구판 결과에 가져오지 않음. |
| 링크 판별 | `v40/codec.ts`의 `assembleShareUrl`, `buildQuestionOnlyUrl`, `parseShareHash`가 `v4.0-tendency`를 직접 사용; `v40/guess/guessLink.ts`도 같은 판을 요구 | 공유 URL을 만드는 계층에 **명시적인 버전 인자**를 주거나 새 판 전용 래퍼를 만듦. 디코더는 `v`가 은행의 exact-version과 같을 때만 열어야 함. v4.0 함수의 기본값을 새 판으로 바꾸지 않음. |
| 저장 | `v40/storage.ts`의 진행·기록·글자 고르기 키와 봉투 버전, `letterGuessEnvelope.ts`의 버전이 v4.0에 고정 | 진행, 기록, 글자 고르기의 **별도 키와 버전 필드**를 사용. 예전 진행 상태를 새 문항의 답으로 자동 복원하지 않음. 자동 저장 설정만 재사용하려면 별도 이용자 선택·문구가 필요. |
| 화면과 흐름 | `WeddingCodeV40Client.tsx` 모듈 전역의 `WEDDING_CODE_V40_BANK`, reducer, 공유 생성, 이벤트 버전, 다시 시작 판; `QuestionScreen`·`ResultScreen` 등은 주로 props를 받음 | 새 판 클라이언트가 새 은행·정확 버전·새 저장 포트를 한 세트로 사용. 흐름의 순수 함수와 화면 컴포넌트는 은행/결과를 인자로 받을 수 있는 부분만 재사용. v4.0 클라이언트 내부의 전역 bank를 교체하는 방식 금지. |
| 입구 | `app/wedding-code/entry.ts`의 `v40` 분기·`V40_LINK_BANK`, `WeddingCodeEntryClient.tsx` lazy import, `page.tsx` 메타데이터 | `?v=v4.1-depth`와 `#v=v4.1-depth&a=…`를 새 분기로 엄격 판별. v4.0의 `v40` 분기는 유지. 다른 판의 `a`와 `b` 또는 `ga`·`gb`가 섞이면 거절. 로컬 bare `/wedding-code`는 v4.1을 열지만, 운영 배포는 사람 검증 관문 뒤 별도로 결정. |

## 최소 구현 순서

1. 문안 후보를 인지면접에 쓰고, 한 선택지에 여러 행동·감정·결과가 묶이지 않는지 확인한다. 특히 회상 문항의 “그런 일이 없어요” 비율을 확인한다. 현재 후보는 기초 정적 검사만 통과했고, 축 의미·응답 가능성·재검사 안정성을 입증하지 않는다.
2. `v4.1-depth`를 후보가 아닌 **정확한 판 태그**로 확정한다. 기존 v4.0의 문항, 생성 파일, checksum, 결과 인용에 대한 골든 테스트를 보존한다. 새 전체 JSON의 68개 항목과 생성 파일에 별도 SHA를 둔다.
3. 링크 코덱을 값 부분과 판 태그 조립·검사로 분리한다. v4.0과 v4.1 양쪽의 정상·손상·교차 판 링크를 검증한다. 잘못된 판의 공유 코드는 결과를 일부 복원하지 않고 오류로 끝낸다.
4. 저장 포트를 판별된 버전으로 만든다. 두 판의 진행/기록/짐작 키가 충돌하지 않는지, 재시작과 자동 저장 끄기가 **자기 판의 키만** 지우는지 확인한다.
5. 새 클라이언트와 입구를 연결한다. 두 사람 비교는 양쪽이 동일한 exact-version일 때만 계산한다. 질문만 링크, 내 답이 담긴 링크, 두 사람 결과 링크의 문구와 재전송 흐름을 새 판에서 다시 검사한다.
6. 모바일 화면에서 처음부터 끝까지 완주하고, 장시간 응답·중단·이어하기·공유·상대 결과 받기를 실제로 확인한다. 사람 검증이 끝나기 전에는 `정확한 성향`, `심리검사`, `궁합` 같은 주장을 하지 않는다.

## 필수 회귀 테스트

- 옛 `v4.0-tendency` 링크의 68개 응답이 **옛 문항 원문과 옛 결과 인용**으로 복원된다. 새 문안을 한 글자도 읽지 않는다.
- 새 `v4.1-depth` 링크는 새 문항과 새 결과 인용으로 복원되며, v4.0 파서·저장소에서는 열리지 않는다.
- URL의 `v`만 바꾸거나 `a`, `b`, `ga`, `gb`를 서로 다른 판에서 옮긴 링크는 완전 거절된다. 공유 URL은 응답을 쿼리에 노출하지 않는다.
- 새 판의 문항 순서, 형식, 극, 강도, 채점과 질문 번호·진행 표시가 은행과 일치한다. 새 문안의 정적 검사는 경고와 오류가 모두 0이다.
- `v4.0` 저장 진행과 기록이 `v4.1` 시작·재시작·자동 저장 조작으로 바뀌거나 지워지지 않는다. 새 판도 같은 조건으로 격리된다.
- 두 판 각각의 처음부터 결과까지 실제 모바일 화면을 검사하고, 한 사람/두 사람/오류/공유 화면을 확인한다.

`scripts/tests/wedding-code-v41-item-draft.test.mjs`는 후보 열 문항을 옛 배치에 **시험용으로만** 덮어 정적 검사와 배치 불변성을 확인한다. 런타임에서 v4.0 응답에 덮는 코드가 아니다. 이 시험이 통과해도 인지면접과 새 exact-version의 링크·저장·입구 검증을 대신하지 않는다.
