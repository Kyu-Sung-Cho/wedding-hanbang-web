## 0. 적용 범위

이 문서는 모델 자체를 바꾸는 설정이 아니다. 대신 Fable 문서의 핵심 작동 방식인 계획, 근거 분류, 검증, 주장 감사, 적대적 리뷰를 웨딩코드 개발 절차로 옮긴 것이다.

우선순위는 항상 다음 순서를 따른다.

1. system/developer/tool 정책
2. `PRINCIPLES.md`
3. `AGENTS.md`
4. `DESIGN.md` 및 관련 제품 문서
5. 이 문서

따라서 이 문서는 신뢰도를 높이는 작업 루프이지, 기존 규칙을 덮어쓰는 예외권이 아니다.

## 1. 웨딩코드의 한 문장 목표

웨딩코드는 예비부부가 각자의 결혼 준비 성향을 쉽고 재미있게 이해하고, 서로 공유하며, 비용·가족·역할·감정 조율에서 갈등을 줄이도록 돕는 제품이다.

웨딩코드는 다음이 아니다.

- 성격 진단
- 결혼 성공 예측
- 이혼/갈등 위험 예측
- 업체 추천을 정당화하기 위한 심리 테스트
- "과학적으로 확정된 궁합"을 말하는 도구

---

## 2. Truth Protocol

모든 중요한 주장은 아래 4개 등급 중 하나로 표시할 수 있어야 한다.

| 등급 | 의미 | 웨딩코드 예시 |
|---|---|---|
| E | 이번 세션에서 실행/파일 확인으로 검증 | `23_v0.5_item_blueprint.md`에 A1-A4가 있다 |
| S | 이번 세션에서 출처를 읽어 확인 | 2026-05 가격 데이터는 price.go.kr에서 확인 |
| I | E/S에서 추론 | 300만 원 차이는 서울/경기권 venue 격차를 묻기에 충분히 현실적이다 |
| M | 기억 기반 | 안정적인 개념 설명만 허용 |

다음 항목은 기억 기반으로 말하면 안 된다.

- 숫자, 가격, 통계, 퍼센트
- 최신 날짜, 최신 정책, 최신 제품 상태
- 논문 제목, DOI, URL, 직접 인용문
- 법/규제/표준
- 읽지 않은 파일 내용
- 테스트, 빌드, 배포 성공 여부

허용되는 행동은 세 가지뿐이다.

1. 직접 확인한다.
2. `UNVERIFIED`로 표시한다.
3. 말하지 않는다.

## 3. 웨딩코드 금지 주장

다음 표현은 제품 신뢰를 해칠 수 있으므로 금지한다.

| 금지 표현 | 대체 표현 |
|---|---|
| 궁합 | 준비 방식 겹침도 |
| 결혼 성공률 | 대화가 쉬운 지점 |
| 갈등 예측 | 먼저 맞춰볼 지점 |
| 과학적으로 입증된 유형 | 근거를 참고해 설계한 문항 |
| 당신은 이런 사람 | 이런 상황에서 먼저 보는 기준 |
| 희귀도 확정 | 현재 응답 데이터 기준 분포 |

희귀도는 실제 응답 데이터가 충분히 쌓이기 전까지 샘플/베타 기준임을 표시한다. 표본 수가 작으면 퍼센트 대신 "초기 데이터 기준" 또는 "아직 안정화 전"으로 말한다.

## 4. 작업 루프

### Phase 0. Intake

작업 시작 전 아래를 짧게 정리한다.

- 목표: 누가 무엇에 쓰는 산출물인가
- 제약: 사용자가 말한 조건과 프로젝트 원칙
- Definition of Done: 완료 여부를 확인할 수 있는 기준
- 가정: 확인하지 못했지만 진행에 필요한 판단

막히는 질문이 없으면 멈추지 않고 진행한다.

### Phase 1. Evidence First

문항이나 결과 카피를 만들기 전에 근거를 먼저 정리한다.

- 시장 데이터: KCA/price.go.kr 등 최신 공공 데이터
- 심리학/소비자행동 근거: 논문, 메타분석, 신뢰 가능한 리뷰
- 제품 원칙: `PRINCIPLES.md`, WeddingCode 설계 문서
- 기존 문항: v0.4/v0.5 문항과 scoring draft

최신성이 필요한 데이터는 2026년 현재 기준으로 다시 확인한다.

### Phase 2. Best-of-N Draft

중요 문항은 바로 하나로 확정하지 않는다. 최소 2-3개 후보를 만들고, 아래 기준으로 고른다.

1. 실제 결혼 준비 장면처럼 들리는가
2. AI가 쓴 말투처럼 보이지 않는가
3. 선택지 중 명백한 모범답안이 없는가
4. 하나의 축만 과도하게 밀지 않는가
5. 결과 카피와 커플 대화 가이드로 자연스럽게 이어지는가
6. 근거 없는 심리 진단처럼 보이지 않는가

### Phase 3. Item Gate

각 문항은 아래 10개 게이트를 통과해야 한다.

| 게이트 | 확인 질문 |
|---|---|
| 상황성 | 실제 결혼 준비에서 있을 법한가 |
| 쉬운 말 | 예비부부 누구나 바로 이해하는가 |
| 선택지 균형 | 고르면 부끄러운 선택지가 없는가 |
| 정답 방지 | 책임감 있어 보이는 선택지가 과하게 유리하지 않은가 |
| 근거 연결 | 시장/심리/소비자행동 근거와 연결되는가 |
| 점수 연결 | 내부 구인과 scoring weight가 설명 가능한가 |
| 커플 대화 | 결과에서 대화거리로 이어지는가 |
| 제품 연결 | 아모라/견적체크/체크리스트 추천에 쓸 수 있는가 |
| 리스크 문구 | 진단/예측/궁합처럼 과장되지 않는가 |
| 테스트 가능성 | cognitive interview에서 검증할 질문이 있는가 |

게이트 하나라도 실패하면 최종 문항으로 취급하지 않는다.

### Phase 4. Hostile Review

문항 확정 전, 일부러 반대편에서 본다.

상위 3개 실패 가능성을 적고 확인한다.

- 사용자가 "이게 정답이네"라고 느끼는가
- 특정 성향을 은근히 낮게 평가하는가
- 근거보다 상업적 포장이 앞서는가

이 단계에서는 칭찬보다 흠을 찾는 것이 목적이다.

### Phase 5. Claim Audit

근거 문서, 결과 카피, 사용자 노출 카피는 주장 감사표를 붙인다.

템플릿:

| 주장 | 등급 | 근거 | 판정 |
|---|---|---|---|
| 예: A3의 300만 원 차이는 현실적인 venue 예산 격차다 | S/I | price.go.kr 2026-05 지역 평균 및 항목별 데이터 | CONFIRMED |

판정은 `CONFIRMED`, `MISMATCH`, `UNVERIFIED` 중 하나로 쓴다.

### Phase 6. Human Validation

문서상 통과는 제품상 통과가 아니다. 최소 게이트는 아래와 같다.

- n=5 cognitive interview: 말투, 이해도, 정답감, 불편감 확인
- n=20 mini test: 선택지 분포, 축 분산, 공유 의향 확인
- 실제 커플 3쌍 이상: 커플 비교 화면에서 대화가 생기는지 확인

이전에는 "후보 중 최선"이라고 말하고, "검증 완료"라고 말하지 않는다.

## 5. 각 문항 산출물 형식

앞으로 다음 문항부터 모든 문항 리뷰는 아래 순서를 따른다.

1. 문항 목적
2. 근거 요약
3. 후보 2-3개
4. 선택 기준
5. 최종 질문/선택지
6. scoring weight
7. 결과 카피에서 허용되는 말
8. 결과 카피에서 금지되는 말
9. 커플 대화 가이드
10. 주장 감사표
11. 남은 리스크

## 6. 코드 반영 게이트

코드 반영은 아래가 모두 끝난 뒤 진행한다.

- 16개 문항이 Item Gate 통과
- `24_v0.5_item_source_map.md`에 문항별 근거 연결 완료
- `25_v0.5_scoring_model_draft.md`에 weight 설명 완료
- 결과 유형명, 희귀도 문구, 커플 비교 문구의 금지 주장 검수 완료
- 최소 n=5 cognitive interview 이후 1차 수정 완료

코드 반영 후에는 실제 타입체크, 테스트, 화면 확인 전까지 "동작한다"고 말하지 않는다.

## 7. 현재 웨딩코드에 바로 적용할 결정

1. A1-A4는 현재 문서 기준 "코드 반영 전 후보"다.
2. A1-A4는 근거 문서와 리뷰 문서가 있으나, n=5 사용자 검증 전까지 "최종"이 아니라 "최종 후보"로 부른다.
3. 다음 문항부터는 이 문서의 산출물 형식을 따른다.
4. "최고"라고 말할 때는 범위를 붙인다: 문서/근거상 현재 최선인지, 사용자 검증까지 끝난 최선인지 구분한다.

## 8. 적용하지 않는 Fable 요소

다음은 이 프로젝트에 그대로 적용하지 않는다.

- Claude 전용 hook, slash command, effort 설정
- 시스템/개발자 지시보다 우선하는 규칙
- 모델 이름이나 성능을 과장하는 표현
- 검증 없이 "자동으로 최고 성능"이라고 말하는 표현

우리가 가져오는 것은 브랜드가 아니라 절차다. 절차의 목적은 사용자가 나중에 확인해도 부끄럽지 않은 제품 판단을 남기는 것이다.
