Date: 2026-07-08

Run only after: 5-person cognitive interview pass or scoped copy fixes

## Purpose

This is a small operating test, not a psychometric validation.

The goal is to decide whether WeddingCode v0.5 is safe and useful enough for a larger 100-person smoke test.

Primary questions:

- Do people finish the 16-question flow?
- Do they recognize their own preparation style without feeling judged?
- Does the partner invite/couple report create curiosity?
- Are any questions strongly biased toward a "good" answer?
- Are there stigma, blame, diagnosis, or compatibility-score risks?

## Stop Conditions Before Launching This Mini Test

Do not recruit 20 people if any of these remain unresolved after the 5 interviews:

- A repeated phrase makes the result sound like relationship prediction.
- A repeated phrase makes the couple result sound like compatibility scoring.
- Two or more interviewees flagged the same question as strong right-answer risk.
- Two or more interviewees flagged the same question as strong stigma/blame risk.
- The phrase "준비 방식 겹침도" is not understood by at least 3 of 5 interviewees.

## Sample Plan

Target: 20 completed responses.

Run in two waves:

- Wave 1: 10 responses, then pause and inspect.
- Wave 2: another 10 only if Wave 1 has no safety blocker.

Recommended composition:

| Segment | Target n | Notes |
|---|---:|---|
| Friend/direct warm testers | 5 | Fast read on comprehension and obvious friction |
| Wedding-preparing community | 8 | Stronger realism and vendor/quote relevance |
| Venue or vendor-experience users | 4 | Tests quote, contract, and decision wording |
| Couples willing to send partner link | 3 pairs or 6 people max | Tests pair completion without forcing it |

Good enough rule: if exact quotas are hard, prioritize people currently near a real wedding decision.

## Metrics

Primary pass bar:

| Metric | Query source | Pass bar |
|---|---|---|
| Completed responses | rows in `wedding_code_responses` | at least 20 |
| `feels_like_me` average | `feedback` JSON | >= 4.0 |
| `scenario_realism` average | `feedback` JSON | >= 4.0 |
| `clarity` average | `feedback` JSON | >= 4.0 |
| Strong stigma/evaluation signal | `stigma_feedback_score >= 4` | <= 1 response and no repeated theme |
| Strong confusion signal | `confusing_question_score >= 4` | <= 2 responses and no repeated item |
| Partner invite interest | `partner_invite_interest >= 4` | at least 30% |
| Couple report interest | `couple_report_interest >= 4` | at least 30% |
| Option concentration | `answers` distribution | no item option > 80% without clear reason |
| Pair completion | `couple_token` groups with 2 rows | baseline only; do not require pass yet |

Interpretation rule: safety metrics override growth metrics. High invite interest does not compensate for stigma or diagnosis-risk language.

## SQL Checks

Set the start timestamp before running queries.

```sql
-- Replace timestamp with mini-test start time.
WITH cohort AS (
  SELECT *
  FROM wedding_code_responses
  WHERE form_version = 'v0.5-candidate.1'
    AND created_at >= TIMESTAMPTZ '2026-07-08 00:00:00+09'
    AND utm_campaign = 'wc_v05_mini20_20260708'
)
SELECT
  count(*) AS n,
  round(avg((feedback->>'feels_like_me')::numeric), 2) AS feels_like_me,
  round(avg((feedback->>'scenario_realism')::numeric), 2) AS scenario_realism,
  round(avg((feedback->>'clarity')::numeric), 2) AS clarity,
  round(avg((feedback->>'stigma_feedback_score')::numeric), 2) AS stigma_avg,
  round(avg((feedback->>'confusing_question_score')::numeric), 2) AS confusing_avg,
  round(avg(duration_ms) / 1000.0, 0) AS avg_seconds
FROM cohort;
```

```sql
WITH cohort AS (

  FROM wedding_code_responses
  WHERE form_version = 'v0.5-candidate.1'

SELECT
  count(*) FILTER (WHERE (feedback->>'stigma_feedback_score')::int >= 4) AS stigma_high,
  count(*) FILTER (WHERE (feedback->>'confusing_question_score')::int >= 4) AS confusing_high,
  count(*) FILTER (WHERE (cta_interest->>'partner_invite_interest')::int >= 4) AS invite_high,
  count(*) FILTER (WHERE (cta_interest->>'couple_report_interest')::int >= 4) AS couple_report_high,
```

```sql
-- Option distribution. Flag any item where one option is above 80%.
WITH cohort AS (
  SELECT *
  FROM wedding_code_responses
  WHERE form_version = 'v0.5-candidate.1'
    AND utm_campaign = 'wc_v05_mini20_20260708'
),
dist AS (
  SELECT key AS item, value AS option, count(*) AS n
  FROM cohort, jsonb_each_text(answers)
  GROUP BY 1, 2
),
totals AS (
  SELECT item, sum(n) AS total
  FROM dist
  GROUP BY 1
)
SELECT
  dist.item,
  dist.option,
  dist.n,
  round(dist.n * 100.0 / totals.total, 1) AS pct
FROM dist
JOIN totals USING (item)
ORDER BY dist.item, pct DESC;
```

```sql
-- High-risk free-text inspection.
SELECT
  id,
  created_at,
  utm_source,
  utm_content,
  feedback->>'stigma_feedback_score' AS stigma,
  feedback->>'confusing_question_score' AS confusing,
  free_text
FROM wedding_code_responses
WHERE form_version = 'v0.5-candidate.1'
  AND utm_campaign = 'wc_v05_mini20_20260708'
  AND (
    (feedback->>'stigma_feedback_score')::int >= 4
    OR (feedback->>'confusing_question_score')::int >= 4
    OR free_text::text ILIKE '%궁합%'
    OR free_text::text ILIKE '%진단%'
    OR free_text::text ILIKE '%평가%'
    OR free_text::text ILIKE '%상처%'
  )
ORDER BY created_at DESC;
```

```sql
-- Pair baseline. Counts tokens that actually have both sides.
WITH cohort AS (
  SELECT *
  FROM wedding_code_responses
  WHERE form_version = 'v0.5-candidate.1'
    AND utm_campaign = 'wc_v05_mini20_20260708'
    AND couple_token IS NOT NULL
)
SELECT
  couple_token,
  count(*) AS response_count,
  min(created_at) AS first_response_at,
  max(created_at) AS second_response_at
FROM cohort
GROUP BY couple_token
ORDER BY first_response_at;
```

## Wave 1 Pause Checklist

After 10 responses:

- Read all high-stigma or high-confusion free text.
- Check whether any one option exceeds 80% on an item.
- Check whether people are using partner invite without being pushed.
- Review at least 3 result pages manually if possible.
- Decide: continue / copy patch / stop.

## Decision After 20

Proceed to 100-person smoke test only if:

- Primary pass bar is met or misses are clearly explainable and fixed.
- No unresolved safety language issue remains.
- Option distribution does not show a systematic right-answer pattern.
- Couple-report interest is directionally positive.

Revise first if:

- One or two items have concentration or confusion problems.
- Partner invite interest is low but result copy is otherwise safe.
- "준비 방식 겹침도" needs explanation but not replacement.

Stop and redesign if:

- People describe it as diagnosis, compatibility scoring, or relationship prediction.
- Partner comparison is perceived as blame material.
- Multiple items feel like moral grading.
