# 랜딩 발견·실기기 검증 준비와 측정 보완

## 확인한 사실과 범위

2026-09-21 사용자 요청은 랜딩 수정 뒤 남은 실제 소비자 발견률·전환율과 실제 iOS·Android 검증이다. 운영 랜딩 진입 개선은 PR #436으로 반영됐지만 그것으로 사람 검증까지 끝났다고 할 수 없다.

- 실제 소비자 관찰 기록은 아직 없다. 사용자는 휴대폰만 준비할 수 있다고 답했다. 첫 방문 소비자를 대신 연기한 AI 검토는 소비자 발견률로 세지 않는다.
- 이 작업 환경의 연결 기기 목록과 도구에서 제어 가능한 휴대폰을 확인하지 못했다. 실제 휴대폰의 기종·브라우저·실행 결과를 받기 전까지 실기기 통과라고 말하지 않는다.
- 운영 환경 변수 이름만 조회해 PostHog 공개 수집 키 설정은 확인했다. 비밀 값은 조회하거나 기록하지 않았다. 집계 읽기 연결과 실제 수신 데이터는 확인하지 못했다.
- `analyticsPrivacy.ts`의 시작·완료 등 웨딩코드 흐름 통계는 2026-09-24 00:00 KST 적용일까지 차단된다. 처리방침 고지·적용일·일반 페이지뷰 억제를 유지한다. 날짜 도래만으로 정상 수신이나 실제 고객 전환율이 증명되는 것은 아니다.

## 재현한 결함

PostHog는 유휴 시점에 초기화된다. 그 전에 랜딩 버튼을 눌러 `/wedding-code`로 이동하면 기존 `before_send`가 이동 후 경로를 보고 원래 랜딩의 클릭과 지연된 페이지뷰를 버릴 수 있었다. 실제 소스를 메모리에서 실행하고 외부 전송 없는 수신기로 재현했다. 클릭 1회 중 유지 0회였고, 초기화 후 랜딩에서 보낸 대조군은 1회였다. 페이지뷰 분모도 누락될 수 있어 오차 방향은 단정하지 않는다.

상단의 웨딩코드와 가입 버튼은 `landing_header`, 무료 도구 네 카드는 `landing_now_card`를 공유했다. 따라서 이 둘의 기존 합계를 웨딩코드 클릭 수라고 읽을 수 없었다.

SDK 원문에서는 `properties` 밖 최상위 `$set_once`에도 최초 방문 주소를 붙이는 것을 확인했다. 기존 웨딩코드 정리는 속성 안 주소만 처리해 이 경로를 놓쳤다. 웨딩코드 흐름 전송은 위 적용일까지 차단돼 있으며, 이번 발견을 이미 운영 답이 유출됐다는 증거로 해석하지 않는다.

## 선택한 수정

링크 이동을 분석 완료까지 기다리게 하면 사용자가 느리게 이동하고 측정 실패가 기능을 막는다. 일반 웨딩코드 페이지뷰 차단을 풀면 답이 담긴 주소를 내보낼 수 있다. 두 방법 대신 랜딩에서 발생한 관측만 좁게 보존한다.

1. 실제 `/landing`에서 호출될 때 원래 경로·시각·고정된 버튼 자리만 잡는다. SDK 로드를 기다리는 동안 답이나 URL 쿼리를 보관하지 않는다.
2. SDK `capture` 호출 직전에 메모리 표식을 등록한다. 동기 `before_send`에서 관측한 이벤트·경로·자리와 일치할 때 한 번 소비하고, 호출 뒤에는 성공 여부와 무관하게 지운다. 표식을 임의로 붙이거나 재사용하면 차단한다. 표식은 전송하거나 브라우저 저장소에 남기지 않는다.
3. 안전한 SDK 식별·세션·기기 속성만 허용하고 `$current_url`, `$pathname`, `$host`는 원래 랜딩으로 고정한다. 최초 방문 원문·리퍼러·UTM·임의 속성·답·최상위 개인 속성은 버린다. 관측 시각은 SDK timestamp 옵션으로 전달한다.
4. 웨딩코드 상단·모바일 메뉴·무료 도구 카드에 각각 `landing_header_wedding_code`, `landing_mobile_wedding_code`, `landing_now_wedding_code`를 부여한다. 기존 가입과 다른 도구 이름은 유지한다.
5. 웨딩코드 흐름 정리도 최상위에서 event·uuid·timestamp·properties만 남긴다. 고지일, 허용 흐름 이벤트, 일반 억제 경로와 연구 수집 경계는 변경하지 않는다.

랜딩의 두 안전 이벤트는 원래 경로만 남기므로 기존 UTM·리퍼러 기반 채널 보고서와 직접 비교하지 않는다. 변경 전 혼합 source를 새 위치로 소급 분리하지 않는다. 푸터는 별도 클릭 측정 대상이 아니므로 추적된 버튼 클릭률은 전체 웨딩코드 진입률과 다르다. 추적 차단·초기화 실패·페이지를 완전히 닫는 행동까지 100% 측정을 보장하지 않는다.

## 실제 측정 방법

발견률은 이름이나 위치를 먼저 알려주지 않은 첫 방문 소비자 관찰로 별도 확인한다. 클릭률은 알아차림·기능 이해·실제 결혼 준비 소비자 여부를 증명하지 않는다. 진행자 가이드와 빈 기록지는 `.verification/landing-consumer-validation/`에 준비했으며 결과를 만들어 채우지 않는다.

9월 24일 이후 수신 확인을 마친 다음에만 같은 운영 호스트·질문 판·세션에서 순서를 묶는다. 실제 세션 속성 저장을 확인하지 못하면 세션 기반 수치라고 말하지 않는다.

- 추적 버튼 클릭률: 랜딩 페이지뷰 뒤 웨딩코드 전용 자리 클릭이 있는 세션 / 랜딩 페이지뷰 세션.
- 소개→시작률: 소개 뒤 시작이 있는 세션 / 소개 세션.
- 시작→결과 도달률: 시작 뒤 완료 이벤트가 있는 세션 / 시작 세션. 건너뛰기도 결과 도달에 포함돼 전 문항 응답률과 다르다.
- 랜딩→결과 도달률은 동일 세션의 페이지뷰→소개→시작→완료 순서를 기준으로 보되, 직접 공유 링크 진입은 별도 분리한다. 클릭 경유 경로만 셀 경우 분자 이름에 그 조건을 명시한다.

이벤트 건수를 나누어 재시작·중복 방문을 여러 사람으로 세지 않는다. 세션은 사람 수가 아니다. localhost·미리보기·팀원과 QA 트래픽을 분리하지 못하면 실제 소비자 성과라고 말하지 않는다. QA는 시간대를 기록하고, 사용자 답·공유 주소를 집계용 기록에 복사하지 않는다. 지연 완료를 관찰할 같은 창을 정하고 미성숙 코호트와 비교하지 않는다.

## 검증 및 남은 조건

관련 기존·회귀 검사 5개 파일 42개 항목을 통과했다. 지연 초기화 후 이동, 원래 시각과 순서, 일회 표식 재사용 차단, 출발 경로 위조, 고정 자리 밖 값, SDK 부가 정보 제거, 일반 페이지뷰와 고지일 차단을 검사했다. 실제 DOM의 세 웨딩코드 링크와 가입 버튼을 눌러 자리 구분도 확인했다.

최종 수정본의 전체 검사·변이 검증·빌드·독립 검토·운영 반영 여부는 릴리스 PR과 해당 커밋의 검증 영수증을 따른다. 이 문서 작성이나 모의 SDK 통과를 실제 PostHog 수신·소비자 발견률·실기기 통과로 바꾸어 말하지 않는다.

남은 조건: 실제 소비자의 랜딩 발견률·전환율; 실제 iOS·Android 기기; PostHog 운영 수신·집계; 9월 24일 이후 웨딩코드 흐름 수신. 기존 전역 출시 판정과 보호 규칙은 그대로다.
