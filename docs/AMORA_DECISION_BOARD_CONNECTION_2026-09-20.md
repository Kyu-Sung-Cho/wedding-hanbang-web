## 구현한 계약

1. `add_decision_record`로 문구·상태·메모·분야만 제안한다. `미정`, `논의 중`, `확정`을 구분한다. 임의 날짜·예산·일정·할 일로 바꾸지 않는다.
2. 서버가 발급한 실제 확인 카드에서 공유 범위를 확인하고 승인해야 저장한다. 말로 “응”이라고 하는 것, 산문 미리보기, 모델의 저장 성공 문구만으로는 실행하지 않는다.
3. 기존 카드의 같은 상태를 말로 재확인하면 같은 action ID·입력·만료·revision을 유지한 카드를 다시 제시한다. 상태 변경·취소·새 지시는 이 승낙으로 해석하지 않는다.
4. 저장은 현재 커플/멤버·공유 대화·최신 메시지·승인 입력·revision을 다시 검증하는 기존 원자 실행 경로를 통과한다. `decision_nodes`와 실행 결과 원장이 한 트랜잭션으로 저장된다.
5. DB의 `INSERT ... RETURNING`으로 만든 식별자·상태·문구·메모·분야·생성 시각만 저장 영수증으로 인정한다. 모델이나 호출자가 준 가짜 성공 메시지/영수증은 사용하지 않는다.
6. 같은 승인의 재시도는 같은 저장 결과를 반환한다. 다른 기록을 덮어쓰거나 재삽입하지 않는다. 결과 불명은 실패/성공으로 단정하지 않고 결정 기록 조회로 안내한다.
7. 웹 전체 대화·사이드패널·스트리밍은 같은 결과 카드를 사용한다. `/wedding/chat/board?view=decisions`로 연결하며 공유 할 일/북마크로 연결하지 않는다.
8. 모바일은 같은 영수증을 표시하고 명시적 버튼으로 웹 결정 기록을 연다. 웹에서 같은 계정 로그인이 따로 필요할 수 있음을 알린다. 네이티브 결정 보드 신설은 이번 범위가 아니다.
9. `get_decision_records`는 보드와 동일한 파서/정리 규칙을 사용한다. 다른 커플·비공개·자동 기억·대체된 기록을 제외하고 읽기 전후 멤버 구성이 같은지 확인한다. 일반 체크리스트 진행 이력은 결정 개수와 분리한다.
10. 명확한 현재 결정 기록 조회 요청은 모델이 조회를 생략하더라도 서버가 실제 조회를 수행한다. 실패는 확인 불가, 부분 조회는 최근 최대 30개로 표시한다. 동명 기록·이전 값의 이력을 합치거나 최신 예산/일정·공동 합의로 과장하지 않는다.

## 검증 중 추가 발견·수정

- 민감정보 검사를 JSON 문자열 전체에 적용하면 줄바꿈이 이스케이프되어 원문 줄 기반 검사를 놓칠 수 있었다. 기존 정규식을 유지하고 실제 문자열 필드별로 검사하도록 수정했다.
- 새 제품 이름만 붙인 프로그래밍 자료 저장 요청이 웨딩 권한으로 확대되는 회귀를 별도 코퍼스로 찾아 새 분기 안에서 차단했다.
- 결과 불명(`TOOL_EXECUTION_UNCERTAIN`), 처리 중(`TOOL_EXECUTION_IN_PROGRESS`), 기존 실행 결과 판독 불가(`TOOL_LEDGER_RESULT_INVALID`) 및 `requires_state_review` 응답을 웹·모바일이 “저장 실패”로 단정하던 표시를 중립 상태로 수정했다. 성공 플래그와 영수증 모양의 데이터가 함께 와도 결과 불명이 우선하며, 무조건 다시 저장하도록 유도하지 않는다.
- “남편이 때려서 무서워. 결정보드에 저장해줘”의 폭력 활용형 누락을 발견했다. 관련 보호 경로·비유/인용 대조군은 별도 안전 검증 기록을 따른다.
- 새 저장 함수의 `couple → profile` 잠금이 기존 커플 초기화/가입 함수의 `profile → couple` 잠금과 역순인 것을 발견했다. 기존 커플 행 잠금·클라이언트 소속 변경 방어·양방향 소속 무결성을 확인한 뒤 마지막 프로필 행 잠금만 제거했다. 소속/역할 재조회와 승인 검증은 유지한다. PGlite의 잠금·소속 방어 검사에 더해, 별도 로컬 PostgreSQL 17.10에서 실제 claim/apply/reset RPC를 두 세션으로 실행했다. 이전 잠금을 복원한 DB 내 SQL 복사본은 양방향 대기와 `40P01` 교착을 재현했고, 현행 SQL은 저장과 커플 초기화가 완료됐다. 결정 1행·완료 원장 1행·반환 영수증 일치를 확인했다. 임시 합성 DB 2개는 종료·삭제를 확인했다. 전체 Supabase 환경·모든 interleaving·실제 join RPC 자체의 증거는 아니다.
- 전체 모바일 검사가 실제 화면 연결 누락을 발견했다. 새 카드 모델/컴포넌트만 준비됐고 `chat.tsx`의 실제 결과 표시 필터에 도구 이름이 빠져 있었다. 해당 필터를 수정하고 실제 `renderMessage → 모델 → 카드` 경로를 검사하도록 보완했다. 카드 단독 검사만으로 화면 연결까지 완료라 할 수 없었던 부분이다.
- 전체 검사에서 이전 릴리스 SQL 목록을 현재 checkout에 그대로 적용하던 양성 fixture도 실패했다. 검토된 과거 릴리스 fixture와 현재 미등록 SQL 차단 검사를 분리했다. 현재 checkout의 새 SQL이 여전히 `NEW_MIGRATION_NOT_REVIEWED`로 차단되는 것을 확인하며, 운영 release manifest·서명·허용 목록은 바꾸지 않았다. SQL wrapper 도입으로 옮겨진 기존 예산 실행기의 위임·실제 생성/수정/CAS 거절도 재검사했다.
