# 아모라 묶음 예산과 다중 요청 후속 배포

## 제품 변경

사용자가 확정한 묶음 이름과 금액은 `apply_budget_plan`의 `custom` + `label`로 보존한다. 현재 메시지에 완결된 금액 목록과 명시적 저장 요청이 있으면 서버가 원문을 해석해 확인 카드를 만든다. 모호한 금액·단위·예시·취소는 이 해석 경로를 통과하지 않는다. 범위 판정, 단일 항목 확인, 원장, 실제 저장 시점의 커플·구성원·여정 리비전 검증은 유지한다.

이름이 같은 기존 예산 항목은 그 키를 재사용한다. 지출·분담자·체크리스트·상태·메모와 미지정 항목은 보존한다. 이름 충돌이나 총액 초과는 전체 배분을 거부하며 일부 항목만 저장하지 않는다.

여러 일정·할 일 요청은 최대 10개의 검증된 입력으로 보존하고 한 번에 한 건씩 확인한다. 저장 성공 뒤 최신 여정을 조회해 다음 확인 카드를 발급한다. 결과 불명·진행 중·실패는 새 식별자로 자동 재시도하지 않는다. 다음 조회가 실패하면 남은 제목·날짜·금액을 본문에도 남겨 사용자가 요청을 이어갈 수 있게 한다.

실제 준비 경로 `/wedding/budget`과 기존 별칭의 열린 화면은 누락된 실시간 이벤트를 다시 조회해 복구한다. 숨겨진 화면·오프라인·무관한 설정 화면은 주기 조회하지 않는다. 소유자 변경, 늦게 도착한 낮은 리비전, 입력 중인 예산 초안이 최신 상태를 덮지 않게 한다.

검색 카드의 요청 수·표시 수·실제 정렬 근거·조회 날짜와 미확인 조건을 표시한다. 모바일 AI 본문은 표·인용·강조를 읽을 수 있게 렌더한다. 화면 정리 안내는 삭제 전 대화 맥락과 유지되는 실제 준비 데이터의 범위를 구분한다. 저장 실패를 계획 철회로 요약하지 않도록 대화 계약도 보완한다.

## 운영 전환 계약

운영 대상은 `hanbang.ai`, Vercel `wedding-hanbang-web`, Supabase `slrtobkksjmxgzatjyqb`다. 기존 214개 이력 위에 `20260907085111_amora_budget_plan_named_allocations.sql` 하나만 적용한다. 정본은 별도 `supabase/release-contracts/amora-named-budget-hotfix-v1.json`이며 이전 8개 SQL 계약과 과거 이력은 유지한다.

공식 진입점은 `corepack pnpm supabase:release:apply -- --amora-named-budget-hotfix`다. `--check-only`, `--apply`, `--finalize` 각각의 실제 커밋·원문 SHA·현재 운영 관측·암호화 원본 백업·복구 decode·별도 PostgreSQL 시험·동시 실행·CLI dry-run·웹 및 DB 쓰기 차단 증거가 필요하다. 이번 함수 변경은 모든 기존 public 행을 그대로 보존하며 커뮤니티 `hot_rank`도 지문에 포함한다.

운영 환경 빌드가 준비되면 쓰기를 잠시 차단하고, 동일 소유자 lease 안에서 정확한 SQL·이력·전후 조건을 원자적으로 적용한다. 실제 도메인과 배포 커밋을 검증한 뒤 같은 소유자의 finalizer로 차단을 해제한다. 응답 유실 시 적용 요청을 자동 재전송하거나 임의 해제하지 않는다.

이 문서는 절차와 구현의 설명이다. 실제 배포 및 모델·화면 검사 성공 여부는 해당 실행의 원본 결과와 별도 완료 보고서로 판단한다. Vercel 웹 배포는 네이티브 앱스토어 배포를 뜻하지 않는다.
